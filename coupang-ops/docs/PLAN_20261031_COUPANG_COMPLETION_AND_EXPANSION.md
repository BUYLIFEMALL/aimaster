## 3. 이번 분석에서 바로잡은 것
1. **승인 불필요 수정은 배송·반품 정보만 바꾼다.** 이전 플랜 C7의 「이미지·상세 수정」은 틀렸다. 이미지·상세·옵션 수정은 재승인이 필요한 상품 수정 API로 한다.
2. **승인 요청 가능 상태:** 명세 본문은 「임시저장만」, 오류 설명은 「임시저장·승인완료·승인반려·부분승인완료」로 다르다. 임시저장·승인반려만 버튼을 열고 쿠팡 응답을 그대로 보여 준다. 저장 직후에는 최소 10분 뒤 재시도 안내가 있다.
3. **수수료표 일부를 정산 데이터로 대체 가능:** 매출내역에 옵션별 `serviceFeeRatio`, 판매 수수료, 정산액이 있다. 판매 실적이 있는 카테고리는 참고 요율 대신 실제 값을 쓸 수 있다.
4. **로켓그로스 재고 API만 전체 재고를 한 번에 주고** 최근 30일 판매량까지 포함한다(분당 50회 제한). 일반 판매는 옵션당 1회 호출이다.
5. **즉시할인 쿠폰은 적용 상품을 나중에 뺄 수 없고** 다음 날 0시부터 시작된다. 생성 전 경고가 필요하다.
6. **`coupang/` 「Coupang Seller Copilot」은 코드 없이 문서만 있는 기획이다.** 경쟁사 수집 단계는 약관·봇 위험으로 제외 대상이다.
7. **호출 수 기록이 코드에 없다.** 조회 간격 제한만 있고 월 사용량을 알 수 없다.

## 4. 가장 큰 제약: 고정 IP 비용
- 모든 쿠팡 호출이 운영자 Fixie를 거치고 토스 연동과 한도를 공유한다. **2026-10-31 주인님 Fixie 화면 확인: 요금제 Tricycle.** 2026-10-28 문서의 무료 구간(월 500회)으로 보이며, 이전 추정 2,500회는 틀렸다. 이번 달 사용량은 확인 중이다.
- 회원 1명이 매일 오늘 할 일(4회)과 문의(2회)만 봐도 월 약 180회라, 무료 구간에서는 **토스 사용량을 빼기 전에도 활동 회원 2~3명**이 한도다. 2,500회 구간이면 약 13명, 25,000회 구간이면 약 130명이다. 재고 점검은 별도다.
- 이 프로그램은 VIP 145명에게 열려 있다. 그래서 핵심 원칙 16의 「운영자 실비 프로그램 = 프리미엄」 후보이며, 결정은 주인님 몫이다(§8).

## 5. 완성 로드맵(`coupang-ops` 안)
각 묶음은 범위 플랜 → 구현 → 자동 시험 → 빌드 1회 → 크롬 확인 순서다. 쓰기 실제 시험은 건별 승인으로 1건만 한다.

### 묶음 1. 기반(v1.05): 사용량과 승인 요청
주인님 목록의 6번과 5번을 먼저 한다. 이후 모든 기능이 호출 수를 쓰므로 계측이 먼저여야 한다.
| 기능 | 내용 | API |
|---|---|---|
| Fixie 사용량 | `wingRequest`에서 회원별·월별 호출 수 집계, 70% 경고, 회원별 일일 상한 | 없음 |
| 승인 요청 | 임시저장·반려 건 2단 확인 뒤 요청, 상태 확인과 연결 | 승인 요청, 등록 상태 조회 |
| 등록 전 검사 | 브랜드 검색, 카테고리 유효성 | 브랜드, 카테고리 |

### 묶음 2. 고객 응대(v1.06): 문의와 AI 초안
| 기능 | 내용 | API |
|---|---|---|
| 문의 모아 보기 | 상품 문의 + 고객센터 문의, 미답변·미확인 먼저, 7일 구간 | 문의 조회 2종, 단건 |
| AI 답변 초안 | 회원 본인 Claude 키. 문의와 주문·배송 상태로 초안 → 회원 수정 → 등록. 자동 등록 없음 | 답변 2종, 확인 처리 |

### 묶음 6. 회원이 켜는 자동 실행(v1.10)
- 회원 본인 cron-job.org로 아침 요약, 출고중지·미답변 알림. 읽기만 하고 사람 확인 없는 쓰기는 없다(예약 지침 `docs/SCHEDULER_POLICY.md`).
- 알림 채널은 공용 SMTP·SOLAPI 연동과 `trending-product-finder`의 텔레그램 코드를 재사용한다.
- 호출 비용이 커서 묶음 1의 상한과 §8 결정 뒤에 한다.

### 수요 확인 뒤
로켓그로스 상품·주문·재고. 전체 재고를 한 번에 주어 호출 효율은 가장 좋지만 계약 회원만 쓸 수 있다.
