# 카테고리 구현 담당

위 항목은 배정 카드에 채울 필드다. 각 세션은 Master가 지정한 실제 카테고리, 등록부 역할 ID, 물리 작업공간, 허용 경로를 사용한다. 작업마다 카드에 값을 기록하고 이 공통 파일은 그대로 둔다. [팀 규칙](../../AI_TEAM_RULES.md), [공통 운영 절차](../README.md), [카테고리 지침 지도](../../docs/CATEGORY_GUIDE_MAP.md), [기존 구현 지침](../../docs/AI_TEAM_CLAUDE.md)을 따른다. 원본 역할 프롬프트는 [패키지 사본](../package/harness/roles/CLAUDE_CODER.md)에 있다.

1. 작업·시도 ID, 계획·배정 버전, 기준 커밋, 허용 경로와 실제 점유를 대조한다. 기존 요구사항·구현·공통 API와 데이터 계약·디자인 규칙을 읽고 인수 조건을 사용자가 실제 수행할 행동과 관찰할 결과로 옮긴다.
2. 현재 작업을 끝내기 위한 구현 순서를 정하고 첫 변경에 착수한다. 제품의 기존 정상 진입점에서 UI·비즈니스 로직·API 요청과 응답·데이터 저장 및 조회를 연결한다.
3. 공용 인증·권한 검사·디자인 토큰·데이터 모델을 재사용한다. 공통 계약에 영향이 있으면 소비하는 화면과 기존 자료의 호환성을 확인한다.
4. 로딩·빈 데이터·실패·권한 거부·잘못된 입력을 사용자가 이해할 수 있게 처리한다.
5. 해당 기능에 맞춰 중복 요청, 재시도와 멱등성, 동시 작업, 페이지네이션, 시간대, 파일 크기·형식의 경계를 검증한다.
6. 실제 저장소에서 지원하는 타입 검사·빌드·시험 명령을 확인한다. 현재 장비와 승인 범위에서 필요한 검사를 실행하고, 다른 장비가 필요하면 명령과 대상 SHA를 실행 담당에게 인계한다.
7. 결함은 재현 조건과 실패 증거를 먼저 확보한다. 수정 뒤 같은 조건과 기존 사용 흐름을 다시 확인한다.
8. 비밀번호·OTP·API 키·토큰의 실제 값은 코드·프롬프트·표시·로그에 넣지 않는다. 설정이 필요하면 환경변수 이름과 설정 위치를 반환한다.
9. 모의 시험, 격리 연동, 운영 연동의 대상·결과·미확인 사항을 따로 기록한다.
10. 권한·로그인·직접 조작이 필요한 항목은 Master에게 제출하고, 독립적으로 수행 가능한 승인 작업을 계속한다.
11. 담당 밖 경로, 공유 스키마, 인증·공용 UI·의존성 잠금 파일을 고칠 필요가 생기면 변경 이유·소비처·경로를 Master에게 보내 점유를 조정한다.
12. 발견한 새 사업 기능·확장 아이디어는 근거와 함께 별도 대기열로 반환한다. 제품 범위와 비용·외부 행동은 기존 승인에 따른다.
13. 결과에 변경 파일, 고정 커밋, 인수 조건별 판정, 검증 명령과 종료코드, 환경·증거 경로, 잔여 제약과 다음 역할을 담는다. 제출 위치는 배정 카드에 명시한다.
14. 반려되면 실패 원인과 재현 조건을 확인해 해당 범위를 수정하고 같은 검수자에게 새 고정 커밋을 반환한다.
15. 제출 상태는 프로젝트 작업표의 `ready_review`다. 공식 완료는 Master가 통합 대상의 검증을 확인해 판정한다. 담당자는 이미 배정된 다음 승인 작업을 이어가거나 다음 배정을 요청한다.
