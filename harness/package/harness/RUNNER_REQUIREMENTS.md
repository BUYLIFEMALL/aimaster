# 상시 실행기 구현 요구사항
아래는 구현할 프로그램의 설계 명세입니다. 이 Markdown이나 config.example.json만 복사한다고 실행기가 설치되거나 구동되지는 않습니다.

## 1. 책임의 분리
Master는 목표 해석·우선순위·배정·판단을 담당합니다.
Runner/Controller는 작업 큐, 프로세스 호출, 입력 수신, 결과 수집, 중앙 기록, 재시작을 담당합니다.
Supervisor는 Controller 자체가 종료되었을 때 재시작하고 최근 체크포인트로 복구합니다.
Recorder는 저장된 사건에서 터미널 로그와 보고서를 생성합니다. 별도 모델 호출을 기본으로 하지 않습니다.

## 2. 실제 연결부터 확인
Codex, Claude Code, AGY 각각에 대해 실행·작업 입력·출력 수집·세션 식별·재개·취소 기능을 설치 버전에서 확인합니다.
Codex는 공식 문서에 codex exec, SDK, app-server가 설명되어 있습니다.
Claude Code는 공식 문서에 비대화형 -p와 구조화·스트리밍 출력이 설명되어 있습니다.
특정 ORCA 구성이나 AGY 버전이 해당 호출 경로를 제공한다고 가정하지 않습니다.
아직 지원하지 않는 어댑터는 UNAVAILABLE로 기록하고 연결 구현 작업을 등록합니다.
자격증명·브라우저 동의·운영체제 승인처럼 사람이 필요한 초기 설정은 한 묶음으로 요청합니다.

## 3. 명령·결과 흐름
관리자 터미널/입력창 → 등록된 입력 어댑터 → command_id 부여 → 중앙 사건 기록 → Master에 전달 → 영향 분석 → 새 배정 → 작업자 수신 확인.
한 입력을 중복 수신해도 command_id로 한 번만 적용합니다.
작업 입력과 결과는 도구가 지원하는 구조화 채널 또는 별도 파일로 교환합니다.
JSON stdout에 사람이 읽는 로그를 섞지 않습니다. stderr도 임의로 완전한 JSON이라고 가정하지 않습니다.
긴 명령이 실행 중이어도 Controller의 입력·로그 수집 루프는 살아 있어야 합니다. 단일 블로킹 실행으로 관리자 지시 전달을 막지 않습니다.
중간 지시를 즉시 주입할 수 없는 도구는 다음 안전 지점에서 반영하고 지연 상태를 표시합니다. 긴급 중지는 신규 배정 차단 후 지원되는 취소 경로를 사용합니다.

## 4. 단일 작성자와 중복 방지
프로젝트 단위로 Controller 소유권 잠금/lease를 확보하며 동시에 두 Controller가 쓰지 못하게 합니다.
중앙 파일은 Controller만 작성하고, 작업자는 실행별 별도 결과 파일/전송 채널을 사용합니다.
하나의 중앙 파일 기반 설계라면 임시 파일 작성 후 원자적 교체, 이벤트 추가 기록, 프로세스 잠금을 적용합니다.
분산 실행에서 공유 파일 잠금이 검증되지 않았다면 네트워크 파일시스템 위의 잠금을 신뢰하지 말고 단일 호스트 Controller 또는 서버형 큐를 사용합니다.
task_id + attempt_id + assignment_revision으로 결과를 식별합니다. 외부 부작용 작업은 별도 멱등 키와 실제 실행 결과 확인이 필요합니다.
오래된 결과는 격리·유효성 검토 후 수용하거나 반려합니다. 단순 plan_revision 차이만으로 무관한 완료 결과를 폐기하지 않습니다.
heartbeat 만료만으로 같은 작업을 중복 배정하지 않습니다. 이전 프로세스와 쓰기 권한을 확인하고 격리한 후 재배정합니다.

## 5. 상시 실행 상태
| 상태 | 의미 | 동작 |
|---|---|---|
| RUNNING | 실행 가능한 승인 범위 작업 있음 | 다음 작업 자동 배정 |
| RUNNING_WITH_HUMAN_PENDING | 사람 대기와 독립 작업 공존 | 독립 작업 계속·요청 묶음 표시 |
| WAITING_HUMAN | 남은 모든 유용한 작업이 사람에게 의존 | 서비스 유지·답변 감시·선택 항목만 재개 |
| MONITORING | 현재 승인 범위의 준비된 작업 소진 | 서비스 유지·새 입력/변경 감시 |
| RECOVERING | 장애 복구 중 | 제한된 재시도·독립 작업 계속 |
| PAUSED_BY_ADMIN | 관리자가 명시적으로 중지 | 새 작업 중지·재개 입력 감시 |

MONITORING은 프로그램 종료가 아닙니다. 쉬지 않는 운영을 불필요한 모델 호출·소스 변경과 혼동하지 않습니다.
PC 전원·절전·인터넷·인증·요금제 한도·서비스 장애 때문에 실행 불능이 될 수 있습니다. 이를 숨기거나 영구 무중단을 보장하지 않습니다.
프로세스를 데몬/서비스로 등록하는 구체적 방법은 실제 Windows/macOS/Linux 실행 환경을 확인한 뒤 선택합니다.

## 6. 로그와 보고
실행 이벤트를 민감정보 제거 후 수집하고 events.jsonl에 추가합니다. 의미 있는 사건마다 master.log를 출력하고 flush합니다.
중앙 이벤트 최소 필드: event_id, timestamp, received_at, actor, event_type, task_id, attempt_id, plan_revision, assignment_revision, command_id, summary, evidence_ref.
시각은 시간대가 포함된 형식으로 저장하고 관리자 화면은 Asia/Seoul로 표시합니다. 다른 PC의 시계가 어긋날 수 있으므로 중앙 수신 순서도 기록합니다.
로그는 공개 가능한 행동·명령·결과·결정 요약입니다. 비공개 내부 추론이나 비밀 원문을 복제하지 않습니다.
에이전트 실행이 조용해도 Runner 생존 신호는 별도입니다. 실제 작업 진척이 없으면 "진행 중"으로 꾸미지 않습니다.
STATUS는 예시로 5분마다 및 중요한 사건 직후 갱신합니다. 시간 주기는 설정과 실동작 시험으로 확인합니다.
보고서는 마일스톤 완료, 관리자 요청 묶음, 장애·복구, 일자 변경, 릴리스 후보 시점에 생성합니다.
중간 이벤트를 잃지 않도록 파일 크기 기준 순환과 보존·백업을 정의합니다. 민감정보는 보존 대상에서 제외합니다.
터미널 출력만 남기지 말고 재시작 후 읽을 수 있는 파일을 유지합니다.

## 7. 재시도와 비용
자동 재시도는 원인별로 제한합니다. 같은 오류 반복은 간격을 늘리고 진단 작업으로 바꿉니다.
호출 제한이 발생하면 이미 허가된 다른 작업·도구를 활용하되 비용·계정·모델 제공자를 무단으로 바꾸지 않습니다.
현재 허가된 계정·요금·API 예산을 기록합니다. 추가 과금 또는 한도 확대가 필요하면 관리자 묶음 요청에 넣습니다.
정확한 사용량을 제공하지 않는 도구는 비용을 추정으로 명시합니다.

## 8. 작업공간
한 실행 PC: 작업별 worktree와 별도 빌드/캐시/포트를 사용합니다.
여러 실행 PC: PC별 clone + Git 기반 동기화와 중앙 작업 전송을 권장합니다.
공유 SMB 폴더를 여러 PC의 동일 쓰기 작업공간으로 사용하지 않도록 구성합니다.
중앙 보고서의 읽기 공유와 소스 작업공간의 동시 쓰기는 구분합니다.
git worktree lock은 편집 소유권 잠금이 아닙니다.

## 9. 완료의 실제 의미
구현 결과 제출 → 독립 검수 → 통합 → 통합 대상 검증 → Master 판정의 증거가 연결되어야 합니다.
해당 작업이 완료되면 다음 작업이 실제로 호출되는지 시험합니다.
모든 작업이 사람 대기라면 관리자가 답했을 때 해당 작업이 실제 재개되는지 시험합니다.
새 관리자 지시가 이전 배정·이전 결과와 충돌할 때 재배정과 오래된 결과 격리가 동작하는지 시험합니다.
