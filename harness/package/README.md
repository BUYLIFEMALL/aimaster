# 바이브코딩 하네스 프롬프트 패키지 v1.0
작성 기준: 2026-11-20 · 한국어 · Codex Master 중심

## 이 패키지의 목적
관리자 마스터 플랜을 받아 디자인·코딩·테스트·검수·통합을 연속 수행하고, 사람만 처리할 결정과 직접 작업을 모아 요청합니다. 중간 관리자 지시를 반영하면서 터미널·이력·보고서를 유지합니다.

이 파일들은 운영 규칙·역할 프롬프트·양식·실행기 요구사항입니다. 이미 실행 중인 프로그램이나 설치 완료된 하네스는 아닙니다. 사용자의 PC·ORCA·CLI 연결은 이 작성 과정에서 설치하거나 검증하지 않았습니다.

## 가장 빠른 적용 순서
1. 현재 프로젝트의 기존 AGENTS.md, CLAUDE.md와 Git 변경을 확인합니다. 이 패키지를 기존 파일 위에 그대로 덮어쓰지 않습니다.
2. AGENTS.md의 공통 규칙을 기존 규칙과 통합하고, harness 폴더를 프로젝트에 둡니다.
3. Claude Code는 기존 CLAUDE.md가 있다면 공통 규칙 참조를 통합합니다. 새 파일은 제공한 CLAUDE.md를 사용할 수 있습니다.
4. Codex Master에 harness/START_MASTER.txt를 붙여 넣고 실제 마스터 플랜을 이어 붙입니다.
5. 각 역할 세션에 START_WORKER.txt와 해당 역할 파일·배정 정보를 제공합니다.
6. Master가 실제 세션 호출·결과 수집 기능을 점검하게 합니다. 미연결 부분은 RUNNER_REQUIREMENTS.md에 따라 첫 구축 작업으로 처리합니다.
7. SCENARIO_ACCEPTANCE.md의 실동작 확인을 마친 뒤 연속 운영에 사용합니다.

공통 규칙을 매 작업마다 전부 붙여 넣을 필요는 없습니다. 기본 지침을 한 번 적용하고, 개별 작업에는 해당 역할·관련 결정·현재 작업 카드만 제공합니다.

## 역할 배치
| 역할 | 책임 | 운영 방식 |
|---|---|---|
| Codex Master | 우선순위·배정·관리자 소통·최종 판정 | 프로젝트당 하나 |
| AGY Design/UI | 공통 디자인·화면·접근성 | 해당 작업이 있을 때 |
| Claude 카테고리별 | SNS·Blog·쇼핑몰 등 기능 구현 | 독립 작업만 병렬 |
| Codex Analyst | 구조·문제 분석 | 필요한 분석에 배정 |
| Codex Planner | 개선 제안·백로그 | 새 제안 필요 시 |
| Codex Tester | 독립 테스트·검수 | 구현자와 분리 |
| Codex Debugger | 재현·원인·수정 | 결함 발생 시 |
| Architect | 공통 API·인증·DB 계약 | 초기 및 계약 변경 시 |
| Integrator | 브랜치 통합·릴리스 후보 | 통합 작성자 하나 |
| Security/Data Reviewer | 권한·비밀정보·데이터 검수 | 관련 변경 시 |
| Runner/Supervisor | 호출·감시·재시작·로그·입력 전달 | 상시 프로세스 |
| Recorder | 사건에서 터미널·보고서 생성 | 실행기 기능으로 우선 구현 |

역할 수와 동시에 실행할 AI 수는 다릅니다. 초기에는 Master 외 작업자 3~4개 정도를 가정하고 실제 자원·속도·사용량을 확인하며 조정하는 방식이 적절합니다. 이는 제안값이며 제품 한도가 아닙니다.

## 기존 구성에서 보완할 점
- 디자인 담당과 기능 담당이 같은 파일을 동시에 고치지 않도록 작업별 소유권이 필요합니다.
- 도표의 B2BMall이 두 개라면 같은 책임인지 확인합니다. 구분할 목적이 있다면 B2B-Supplier와 B2B-Buyer처럼 명확히 이름을 정합니다.
- 공통 인증·권한·DB·디자인 토큰·의존성 파일은 여러 카테고리가 각각 새로 만들지 않도록 담당자를 지정합니다.
- 기록 전담 AI를 상시 추가하기보다 실행기에서 사실 기반 로그와 보고서를 자동 생성합니다.
- 서로 다른 프로그램의 창을 열어 놓는 것만으로 세션 간 작업 전달이 연결되지는 않습니다. 실제 CLI·SDK·메시지·상태 수집 어댑터를 확인합니다.

## 파일 배치 원칙
프로젝트 저장소에는 공통 프롬프트·역할·계약·템플릿을 둡니다.
실시간 중앙 상태는 각 작업 브랜치 밖의 CONTROL_ROOT 한 곳에 둡니다.
경로 예시는 D:/AIMaster-Control/프로젝트ID 입니다. 실제 프로젝트 경로와 실행 PC를 확인해 정합니다.

CONTROL_ROOT의 역할:
- PLAN.md: 현재 계획
- STATE.json: 공식 작업 상태와 배정
- ADMIN_COMMANDS.jsonl: 관리자 지시 이력
- DECISIONS.jsonl: 결정·승인 이력
- HUMAN_REQUESTS.json: 관리자 대기 요청
- events.jsonl: 중앙 사건 원장
- master.log: 사람이 보는 누적 로그
- STATUS.md: 최신 상태
- checkpoints/: 재개 자료
- reports/: 마일스톤·일일·릴리스 보고서
- inbox/: 관리자 및 작업자 제출
- assignments/: 작업별 배정 패킷
- runs/: 작업별 결과·민감정보 제거 로그·증거

중앙 기록은 단일 Controller가 관리합니다. 각 역할이 자신만의 CONTROL_ROOT를 만들거나 여러 PC가 하나의 JSON 상태 파일을 동시에 수정하면 안 됩니다.
