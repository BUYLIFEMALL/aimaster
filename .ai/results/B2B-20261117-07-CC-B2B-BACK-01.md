## 수정안(코드 전, 승인 요청)
1. **승인 뒤 처리 전체를 안쪽 예외 블록으로**: toss_call 반환 이후의 응답 해석·결제 기록 갱신·교환 반영(mark_paid)을 `begin … exception when others` 안에 둔다. 오류가 나면 안쪽 변경만 되돌리고, 바깥(토스 호출 전에 넣은) 결제 기록을 `unknown` + 오류 문구(「토스 응답 처리 중 오류 — 관리자 확인」)로 남겨 **결제 키 보존**, 함수는 오류 대신 `{ok:false, unknown:true}` 반환. 교환은 waiting 그대로 → 다음 승인은 「확인 중」(토스 호출 0), 직원 다시 확인으로 복구.
2. **응답 값은 형식 검사 뒤에만 변환**: totalAmount는 `^\d{1,12}$`일 때만 숫자로, 아니면 「완료 판정 불가」= unknown(0·기본값으로 채우지 않음). approvedAt은 안쪽 블록에서 변환, 실패하면 unknown(완료로 처리하지 않음).
3. **다시 확인(recheck)도 같은 보호** + **결제 키 없이 복구하는 길**: 기록이 없거나 결제 키가 비어 있으면 토스 주문 번호(`exfee-<교환 id>`)로 조회(`GET /v1/payments/orders/{orderId}`)해 기록을 다시 만든다(같은 교환·금액 일치만, 직원만). 응답 처리 오류는 unknown 유지·직원에게 문구로 알림.
4. **구조적 한계(그대로 밝힘)**: 토스 승인은 SQL 함수 안의 외부 HTTP라 DB 트랜잭션과 원자적으로 묶이지 않는다. 안쪽 예외 블록은 「응답을 받은 뒤 함수 안에서 난 오류」만 막는다. **토스가 DONE을 돌려준 뒤 DB 연결 끊김·문장 시간 초과·서버 중단으로 커밋 전에 끝나면 결제 기록까지 전부 되돌려지고 돈은 나간 상태가 될 수 있다** — 이건 예외 처리로 해결되지 않는다. 남는 정합성 장치: (a) 토스 승인 멱등 키 `exfee-confirm-<결제 키>` — 같은 결제 키로 성공 주소를 다시 열면 토스가 같은 결과를 돌려주고 이중 청구 없음, (b) 토스 주문 번호가 교환마다 고정(`exfee-<교환 id>`) — 이미 DONE인 주문 번호로 새 결제 승인은 토스가 받지 않는 것으로 알고 있음(**토스 문서로 확인 필요, 미확인**), (c) 위 3번 주문 번호 조회 복구. 화면(단계2)은 승인 오류 뒤 바로 「다시 결제」를 띄우지 않고 「확인 중 — 쇼핑몰이 확인」으로 안내.
5. **시험(수정 뒤)**: F19·F20·F21 초록(unknown·결제 키 보존·재승인 토스 0·다시 확인 done/paid), F22 기록이 통째로 사라진 상태(연결 끊김 흉내) → 직원 다시 확인이 토스 주문 번호 조회로 done/paid 복구, F23 응답 처리 오류 중 무통장 확인·거절·금액 변경 막힘(unknown이라 기존 지킴), 기존 F1~F18 회귀.
