### 4-1. 공식 문서 확인(읽기만, 외부 호출 0)
- 출처: https://developers.google.com/apps-script/guides/triggers/events (2026-11-18 읽음).
- **시트 「양식 제출 시」 이벤트 필드는 `authMode`·`namedValues`·`range`·`triggerUid`·`values`뿐 — 응답 ID 칸이 없다.** `range` = 「수정된 셀 범위」(제출이 기록된 행). `namedValues` 예시에 `Timestamp`가 있지만 항상 있다는 보장 문구는 없다. `triggerUid` = 「이벤트를 만든 **트리거**의 ID」(이벤트별 ID 아님).
- **폼 「양식 제출 시」 이벤트**: `response`(FormResponse)·`source`·`triggerUid`. `FormResponse.getId()` = 「응답 ID, 제출 전이면 null」 — 유일성·불변 보장 문구는 문서에 없음(같은 응답 객체의 ID라는 점만 확인).
- 같은 이벤트가 두 번 오는지(재전송)에 대해 문서는 아무 말도 하지 않는다 — 그래서 중복은 「같은 이벤트 식별값이 두 번 온다」만 막고, 값이 우연히 같은 두 응답은 막지 않는 것이 목표다.
- 근거: `range.getRow()`(행 위치), `range.getSheet().getSheetId()`(시트 ID), `SpreadsheetApp.getActive().getId()`(파일 ID) — 시트 방식에서 「그 제출이 기록된 자리」를 가리키는 값.

### 4-2. 명시적 본문 형식과 신뢰 경계
- **새 스니펫(v2)이 보내는 본문**: `{ v: 2, kind: "sheet", eventKey: "<파일ID>:<시트ID>:<행번호>", values }` (폼에 직접 붙인 경우 `{ v: 2, kind: "form", eventKey: "<응답ID>", values }`). 서버는 **모양을 추정하지 않고** `v`·`kind`로만 판단한다.
- **신뢰 경계**: 웹훅 토큰이 「어느 회원의 어느 폼 연결인지」만 보장한다. `eventKey`는 그 스크립트가 주장하는 값이므로 **중복 범위를 `form_source_id` 안으로 묶는다**(다른 회원·다른 폼의 행과 절대 충돌·간섭하지 않음). 토큰을 가진 사람이 키를 바꿔 보내면 중복 방지만 피할 수 있을 뿐 남의 자료는 못 건드린다(가짜 대량 접수는 개선 원장 #2 「크기·횟수 제한」 몫).
- 검증: `eventKey`는 1~200자·허용 문자(영숫자 `:` `_` `-`)만, 아니면 400(저장·발송 0). 본문 64KB 초과 413(#2와 같은 값).
- **기존 스크립트(v 없음, UUID 또는 폼 응답 ID)는 호환 처리만 한다**: 지금처럼 저장·발송(동작 그대로), `dedupe_key`는 NULL, 접수 행에 「구버전 스크립트 — 중복 방지 안 됨」 표시. 내용 해시로 합치지 않는다.

### 4-3. 원자 선점과 발송 상태(자동 재시도 0)

2. 선점한 행은 바로 `status = 'dispatching'`으로 저장한 뒤 발송.
3. 채널마다 결과(성공·실패·모름)를 따로 기록(`error_message`에 채널별 요약 또는 `channel_results jsonb` 1칸). 최종 상태: 전부 성공 `notified` / 일부만 `partial` / 전부 실패 `failed` / 응답 시간 초과 등 결과 불확실 `unknown`.
4. 함수가 중간에 죽으면 행은 `dispatching`으로 남는다 → 화면에 「확인 필요」로 보이고 **자동으로 다시 보내지 않는다**. 「다시 보내기」(#8)는 `failed` 채널만, 사람이 확인 창을 거쳐 누를 때만(`partial`·`unknown`·`dispatching`은 보낸 채널이 있을 수 있어 그대로 다시 보내지 않고 채널별로 고른다).
