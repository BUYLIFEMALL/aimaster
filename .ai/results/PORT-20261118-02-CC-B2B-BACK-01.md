1. **U1 — 웹훅 수신부만(발송 로직 그대로)**: `await req.text()` → `checkWebhookBodyBytes`(413) → `JSON.parse`(400) → 토큰으로 source(지금처럼, `user_id` 포함) → `classifyWebhookBody(source.id, body)` — invalid 400(저장·발송 0) / legacy → 지금 흐름 그대로(`dedupe_key` NULL) / v2 → **선점 insert**(`user_id = source.user_id`, `form_source_id = source.id`, `dedupe_key`)를 **일반 insert + 오류 코드 23505면 중복**으로 처리 → 중복이면 발송 없이 `200 { ok: true, duplicate: true }`. (주의: f066의 유니크는 **부분 인덱스**라 supabase-js `upsert(onConflict)`로는 대상 지정이 안 될 수 있음 — 그래서 upsert 대신 insert + 23505. DDL 변경 불필요.) 이 단계도 v2 본문은 스니펫 배포 전까지 오지 않으므로 운영 효과는 크기 제한·형식 거절뿐.
2. **U2 — 상태 전이와 채널 분류**: 선점(또는 legacy insert)을 `status = 'dispatching'`으로 넣고 발송 → 채널 결과로 최종 `notified`(전부 성공)/`failed`(전부 확정 실패)/`partial`(일부 성공)/`unknown`(하나라도 불명 + 성공 확정 아님). 최종 update 실패·함수 중단이면 행은 `dispatching`으로 남음 → 화면 「확인 필요」, 팔로우업 보류. **자동 재시도·재발송 0**. 불명 분류: `NetworkError`·`ServerError`·`ResponseSchemaMismatchError`·`UnexpectedDefectError`·`UnhandledExitError`·`DefaultError`·모르는 예외 = 불명 / `ApiKeyError`·`BadRequestError`·`ClientError`·`InvalidDateError`·`VariableValidationError`·`MessageNotReceivedError` = 확정 실패. 텔레그램·SMTP: HTTP 응답 받은 뒤 거절 = 실패, 연결 오류·시간 초과 = 불명.
3. **U3 — v2 스니펫·안내**: 주인님 시험 폼·시트에서 「첫 칸 = 제출 시각 Date」 확인 뒤에만. 확인 못 하면 스니펫이 v 없는 구버전으로 보내 보호 없음 경계 유지. 기존 회원은 스크립트 재복사 안내.

### 21-3. 시험 계약(U1·U2 구현 때, 실제 route·실제 dispatch, 가짜 DB·가짜 발송)
- 원래 1회 발송: 정상 v2 1번 → 행 1·발송 1·`notified`. legacy 1번 → 지금과 같음.
- 중복 v2 수신: 같은 본문 2번(순차·동시) → 행 1·발송 1·두 번째 `duplicate`. 같은 키·다른 source / 같은 회원·다른 폼 → 각각 1회.
- 회원·source 경계: 토큰의 source.user_id로만 넣음, 다른 회원 source id를 본문에 넣어도 무시(본문엔 source가 없음).
- 선점 뒤 중단: 발송 도중 예외·함수 중단 → 행 `dispatching` 남음·재호출해도 재발송 0(중복 키) · legacy는 재호출 시 새 행(보호 없음 — 명시).
- DB 실패: source 조회 실패 404/500·발송 0, 선점 insert의 23505 아닌 오류 → 500·발송 0, 최종 update 실패 → 발송은 됐고 행 `dispatching`(확인 필요로 보임).
- 외부 응답 불명: SOLAPI 불명 오류 → `unknown`·재시도 0 / 확정 실패 → `failed` / 일부 성공 → `partial`.
- 크기·형식: 64KB 초과 413, 잘못된 JSON 400, v2 형식 오류 400 — 저장·발송 0.
- 팔로우업과의 연결: 새 상태 행은 기존 팔로우업 보류 시험대로 보류(이미 있음), 접수 확인 발송은 팔로우업 보류와 무관하게 1회만.
