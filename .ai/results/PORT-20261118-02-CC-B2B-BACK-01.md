  기대: dedupe_col 0 · dedupe_idx null · status 검사 제약 정확히 1개(정의 `CHECK ((status = ANY (ARRAY['received'::text, 'notified'::text, 'failed'::text])))`) · by_status에 received·notified·failed만. 다르면 적용하지 않음(초안의 사전 확인도 자동 멈춤).
- 잠금 영향: 칸 추가(NULL·기본값 없음)는 메타데이터만이라 짧음. 유니크 인덱스(비동시 생성)와 CHECK 제약 추가는 표를 잠그고 전체를 한 번 읽음 — 접수 표 크기에 비례(사전 읽기 total_rows로 판단). 적용 중 웹훅 insert는 잠금 대기, 5초 넘으면 DDL 쪽이 취소(웹훅 쪽 대기는 짧음). 접수 적은 시간대 권장.
- 중복 영향: 기존 행은 `dedupe_key` NULL이라 유니크에 걸리지 않음 — 기존 중복 데이터가 있어도 적용 성공.
- 롤백(새 코드 배포 **전**에만, 새 상태 값이 생기기 전): `drop index public.crm_submissions_dedupe_uq; alter table public.crm_submissions drop column dedupe_key;` + status 제약을 같은 이름으로 기존 3값 정의로 되돌림. **새 코드 배포 뒤에는 dispatching·partial·unknown 행이 있을 수 있어 제약 되돌리기 불가 → 롤백 대신 이전 배포로 되돌리기(코드)만, DDL은 유지**(새 칸·새 상태는 옛 코드와 호환: 옛 코드는 칸을 쓰지 않고 received·notified·failed만 씀).
- 멈춤 조건: 사전 읽기 기대와 다름 / 적용 SQL이 `[멈춤]`·lock timeout으로 끝남(같은 SQL 바로 재실행 0, 사전 읽기 다시) / 사후 대조 실패.
