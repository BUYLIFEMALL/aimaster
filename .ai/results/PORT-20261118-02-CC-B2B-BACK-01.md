## 4. 중복 방지 최소 플랜(구현은 범위 지시 뒤)
1. **DDL(운영 DB, 주인님 SQL 편집기 또는 지시된 경로)**:
   `alter table public.crm_submissions add column if not exists dedupe_key text;`
   `create unique index if not exists crm_submissions_dedupe on public.crm_submissions (form_source_id, dedupe_key);`
   — 기존 행은 `dedupe_key`가 NULL이라 유니크에 걸리지 않음(채우기 0, 기존 자료 변경 0). 새 표·권한 변경 없음.
2. **서버 중복 키(코드)**: `responseId`가 구글폼 응답 ID 모양이면 `r:<responseId>`, UUID 모양(시트 트리거의 임의 값)이거나 없으면 `h:` + sha256(`form_source_id` + 질문 이름순으로 정렬한 `namedValues` JSON). 시트 트리거의 `namedValues`에는 제출 「타임스탬프」가 들어 있어 같은 제출은 같은 키, 다른 제출은 다른 키.
3. **insert를 「있으면 무시」로**: supabase-js `upsert(…, { onConflict: "form_source_id,dedupe_key", ignoreDuplicates: true }).select()` — 행이 안 돌아오면 중복으로 보고 **발송 없이** `200 { ok: true, duplicate: true }`(Apps Script가 다시 보내지 않게 200). 동시에 두 요청이 와도 유니크 인덱스가 하나만 통과시킨다.
4. (선택, 새 회원) Apps Script 안내 코드에 시트 행 번호를 함께 보내기 — 기존 회원 스크립트는 그대로 두고 서버 키로 막는다.
5. 알려진 절충: 첫 요청이 접수만 저장하고 발송 전에 죽으면 재시도도 중복으로 무시된다(그 행은 `received`로 남음) — 유료 발송은 「최대 1번」을 우선. 남은 `received` 건은 개선 원장 #8 「실패 건 다시 보내기」로 처리.
