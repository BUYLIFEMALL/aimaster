## 1. 두 앱 분석

### 1-1. 공통 구조
- 단일 페이지 앱: 날짜·서울 날씨 줄 → **기능 선택 버튼 7~8개** → (자동완성은 검색엔진 선택) → 키워드 입력 → 결과 영역. 오른쪽 사이드바: **실시간 트렌드 도구 링크 9개** + **프롬프트 라이브러리 50개**(3카테고리: 키워드 리서치 15·블로그 주제 20·타겟별 15). 설정(앱 A만)·도움말 모달, 푸터 크레딧.
- AI: `@google/genai`, 모델은 `gemini-2.5-flash` 하나. 실시간 분석은 `tools: [{ googleSearch: {} }]`(구글 검색 그라운딩) + 응답 텍스트에서 JSON 추출, 단순 생성은 `responseSchema`. 키는 AI Studio가 주입(`process.env.API_KEY`).
- 서버 저장·기록·내보내기 없음(새로고침하면 소실), 결과 복사 버튼만 있음.

### 1-3. 앱 A가 앱 B보다 나은 점 → 통합 때 채택
1. 공식 Naver 검색 API(블로그·뉴스): HTML 구조가 바뀌어도 깨지지 않고 차단 위험이 없음.
2. 뉴스 기반 전략, 카테고리 트렌드 분석 기능.
3. 자체 서버 프록시(공개 CORS 프록시 의존 제거).

### 1-4. 앱 B가 앱 A보다 나은 점 → 통합 때 유지
1. **키 없이도 쓸 수 있는 기능 범위**(네이버 API 키 미등록이어도 ①②④⑤⑥ 사용 가능) — 우리도 "Naver 키는 선택"으로 두어 진입 장벽을 낮춘다.
2. 더 단순한 구성(7개 기능)과 도움말이 정돈되어 있음(상세 매뉴얼 11KB).

### 1-5. 두 앱 공통 결함·한계 (통합 버전에서 해결)
1. **"검색량/경쟁도 점수"는 AI 추정치**다(구글 검색 그라운딩 결과를 요약해 숫자를 만듦). 화면은 "검색 관심도 지수"로만 표기해 실측처럼 보인다. → "AI 추정"을 명시하고, 회원이 네이버 검색광고 키를 등록하면 **실제 월간 검색수(PC/모바일)**를 함께 보여 준다.
2. **공개 CORS 프록시**(앱 B)와 **키 난독화 저장**(앱 A): 제3자 서버에 검색어가 노출되고 키가 사실상 평문. → 서버 경유 + `user_api_keys` 저장.
3. **Naver 트렌드 스크래핑은 로그인 벽**으로 실제로는 동작이 불안정(앱 A도 `LOGIN_REQUIRED` 오류 처리). → 공식 **데이터랩 검색어 트렌드 API**(같은 Naver 앱 키)로 교체.
4. **응답 JSON을 정규식으로 추출**(그라운딩 호출): 형식이 깨지면 실패. → 서버에서 검증·1회 재시도, 가능한 곳은 responseSchema 사용.
5. **상태 초기화 코드 중복**(앱 A: setter 15개를 여러 곳에서 반복) → 단일 상태 머신/리듀서.
6. **결과 보관·재사용 없음**: 새로고침 시 소실, 같은 키워드를 다시 분석해야 함. → 기록(100건)·즐겨찾기·Markdown/CSV 내보내기.
7. **날씨 호출**: 접속마다 AI 호출. → 제거(날짜만 표시).
8. 연도: 일부 프롬프트는 오늘 날짜를 주입하지만 일부는 없음. → 모든 프롬프트에 당해 연도·오늘 날짜 주입(핵심 원칙 8번).
9. 어두운 고정 테마·크레딧 하드코딩 → AIMaster 흰색 표준 UI.
10. 앱이 서로 다른 시점의 코드라 **같은 기능의 프롬프트가 미세하게 다름** → 더 상세한 쪽(앱 A)을 기준으로 통일.

## 3. 기능 범위 (v1.01)
1. **분석 8종**: ① 자동완성(Google/Naver) + 주제 만들기 ② AI 연관검색어·PAA·콘텐츠 갭 + SERP 전략 ③ 상위 블로그 + 1위 공략 ④ 키워드 경쟁력(+실측 검색수) ⑤ 오늘의 전략 키워드 ⑥ 다각도 주제 발굴 ⑦ 뉴스 기반 전략 ⑧ 카테고리 트렌드(데이터랩 검색어 트렌드 + 상위 블로그 빈출 키워드).
2. **연결 흐름**: 결과의 키워드를 클릭하면 같은 화면에서 다음 분석으로 이어짐(앱의 `handleKeywordClick` 계승), 제안 카드에서 [복사]·[Markdown 저장].
3. **프롬프트 라이브러리 50개**(재작성): 변수 입력 → 실행 → 보고서 형식 표시.
4. **트렌드 도구 링크 9개**(실시간 검색어·시그널·creator-advisor·데이터랩·정책포털·금융위·기재부·KDI·수익화 전략) 패널.
5. 기록 100건·즐겨찾기·내보내기(Markdown/CSV), 오류 분류(키 없음/한도/형식 오류/네이버 인증 실패), 취소.
6. 설정: Gemini 키 + Naver 검색 API 키(연결 테스트) + (선택) 검색광고 키, 연동 매뉴얼 팝업, 사용 매뉴얼.

## 4. 아키텍처
- Next.js 16 App Router + TS, 순수 CSS. `reverse-prompt`·`thumbnail-master` 골격(접근 판정·사이드바·키 관리·`/open`·SSO 쿠키) 재사용.
- `src/lib/kwf/`(순수 로직, 단위 테스트): `types`, `prompts`(기능별 프롬프트·연도/날짜 주입), `parse`(JSON 추출·검증·인용 코드 제거), `naver`(응답 정리·HTML 태그 제거), `autocomplete`(ㄱ~ㅎ 확장·중복 제거), `library`(프롬프트 50개), `links`(트렌드 링크), `export`(Markdown/CSV).
- 서버 API(전부 `checkProgramAccessApi` + `force-dynamic`): `POST /api/analyze`(기능별 분기: autocomplete·serp·blogs·competition·recommend·sustainable·news·trend, 필요 시 Naver 키 조회), `POST /api/strategy`(2단계 전략 리포트·주제 만들기), `POST /api/prompt`(라이브러리 실행), `GET/PATCH/DELETE /api/history`, `/api/keys`(Gemini·Naver·검색광고), `POST /api/keys/test`(Naver 연결 테스트).
- DB: `keyword_fighter_reports(id, user_id, feature, keyword, params jsonb, result jsonb, model_used, favorite, created_at)` + RLS owner-only(서버는 service role + `user_id` 필터), 최대 100건. `user_api_keys` 기존 provider(`gemini`, `naver_client_id`, `naver_client_secret`, `naver_ads_*`)를 그대로 사용 — **새 제약 변경 없음**.

## 7. 리스크
1. **구글 검색 그라운딩 응답 변동**: PAA·문서 수 등은 검색 결과 요약이라 정확도가 일정하지 않음 → "AI 추정" 표기, 형식 검증·재시도, 점수는 참고용으로 안내.
2. **Naver API 한도/약관**: 검색 API 일 25,000건, 데이터랩 일 1,000건(앱 단위) → 회원 본인 키 사용·한도 초과 오류 안내. 자동완성 엔드포인트는 비공식이므로 실패 시 건너뛰고 일부 결과만 표시.
3. **데이터랩 사용 설정**: 같은 Naver 개발자 앱에서 "검색어 트렌드" API를 추가해야 함 → 매뉴얼에 단계별 안내, 미설정 시 해당 기능만 안내.
4. **비용**: 기능 1회 = Gemini 1~2회(+그라운딩) — 회원 본인 키 사용량, 프롬프트 라이브러리는 1회.
5. **유사 프로그램 중복**: `longtail-keyword-expander`·`competitor-analysis`와 역할이 일부 겹침 → 카탈로그 설명에서 "키워드 리서치 + 제목·공략법·오늘의 이슈·뉴스·트렌드를 한 화면에서 이어가는 올인원"으로 구분.
6. **원본 저작권·브랜드**: 코드·UI 문구를 그대로 복제하지 않고 기능 구조만 참고해 새로 작성, 크레딧·로고·채널 링크는 쓰지 않는다.
