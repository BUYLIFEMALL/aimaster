# BLOG 자동화 개선 — 클로드 인수인계

작성일: 2026-10-10. 주인님 지시: **BLOG는 클로드 담당, 네이버 블로그 에이전트는 Codex 담당.** 이 문서는 공용 인수인계이며 Codex는 `ai-auto-blog/`의 코드·프로젝트 문서를 수정하지 않습니다. 작업 시작 시 최신 HEAD와 BLOG 버전을 다시 확인합니다.

## 1. 주인님이 원하는 동작

“문서를 최종 검수해서 확장프로그램으로 보내면 이후 확장프로그램이 발행전단계까지 자동으로 진행”하는 흐름을 BLOG에도 적용합니다.

목표: **웹에서 원고 최종 검수·저장 → 확장으로 보내기 → 본인 네이버 계정·대상 블로그 확인 → 빈 편집기 준비 → 제목·본문·이미지 자동 입력 → 카테고리·태그 등 설정 → 전체 입력 검증 → 발행 준비 완료 안내 → 회원이 최종 발행.** 보내기 후 사이드패널에서 같은 원고를 다시 선택하고 입력 시작을 누르는 절차를 줄입니다. 최종 발행 버튼을 자동으로 누르는 것은 이번 BLOG 목표에 포함하지 않습니다.

현재 에이전트는 최종 발행까지 자동 실행하는 경로가 있습니다. “에이전트 방식”을 적용한다는 이유로 이 마지막 클릭까지 그대로 복사하지 않습니다. 준비 완료·서버 기록 완료·실제 발행 완료는 각각 다른 상태입니다.

## 3. 지금 확인된 구조

| 항목 | 현재 BLOG | 참고할 에이전트 구조 |
|---|---|---|
| 웹 원고 | Google News RSS 자료 → 선택 AI 본문 → Gemini 이미지 → HTML → `blog_posts` 저장 | 역할별 기획·본문·윤문·검수, 이미지 별도 생성 |
| 전달 | `extension_handoff_at`으로 최근 20건 사이드패널 목록에 올림 | 회원·blogId별 작업 조회, queued 상태 조건부 선점 |
| 실행 | 회원이 패널에서 글 선택 후 시작; CDP 문자 입력·DOM 이미지 업로드 | background worker가 자동 진행, 단계별 문서 비교 |
| 상태 | in_progress/completed/publish_ready/failed는 입력 상태 | activeTask·authoringCheckpoint·pendingResult 로컬 보관 |
| 결과 | 회원이 네이버 최종 발행 | 기존 에이전트 경로는 최종 클릭 후 게시글/예약 목록 확인 |

웹 내부 등록은 네이버 발행 성공이 아닙니다. PC Chrome·확장·본인 네이버 로그인 세션이 필요합니다. Vercel의 매일 정리 Cron은 30일 보관 정리이며 네이버 입력 스케줄러가 아닙니다. CDP가 DOM보다 빠르거나 성공률이 높다는 실측 결론은 아직 없습니다.

## 4. 문제와 수정 순서

| 순서 | 확인된 문제 | 수정·검수 기준 |
|---|---|---|
| 1 | `getNaverBlogTab()`에서 대상 blogId 확인 부족, 제목 끝에 입력; 기존 제목 혼합·본문 중복도 포함 검사 통과 | 본인 blogId·편집기 프레임 확인, 빈 문서 안정 확인, 기존 내용은 보존하고 중지. 제목 정확성·본문 순서·이미지 수/순서·중복을 검증 |
| 2 | 입력 중 전역 `active`와 목록 선택이 바뀔 수 있음 | 시작 시 원고 ID/내용/이미지/설정/회원/탭을 고정. 목록·연결 변경 잠금, 동시에 같은 작업을 시작하지 못하도록 선점 설계 |
| 3 | 보내기 후 패널에서 다시 선택·시작해야 함 | 승인된 검수 원고만 자동 작업으로 전달. worker가 패널 표시와 독립적으로 실행. 옛 확장에는 기존 API 호환 또는 업데이트 안내 |
| 4 | `reportInputResult()`의 `.catch(()=>{})`가 보고 실패를 버림 | 결과 선보관 → 서버 실제 DB 반영 확인 → 로컬 완료 정리. 실패 시 보고만 재시도. 입력/업로드 재시도와 분리 |
| 5 | 이미지 변경 명령이 `allFrames:true` | 읽기로 대상 프레임을 찾고 변경은 한 프레임만. 고유 자산 이름, 업로드 완료 확인, AI 활용 표시 적용·검증 |
| 6 | 동적 연도 방어 누락, 글자수 입력을 단어수로 처리 | 당해 연도 동적 주입·과거 연도 출력 검사. 목표 길이 단위를 화면/API/프롬프트/검증에서 통일 |
| 7 | 뉴스 출처 수 기반 값을 SNS 언급 지표처럼 표시, 자료 0건도 50점 | 추정값임을 명시, 데이터 없음은 없음. 실제 SNS 조회·검색 성과와 구분 |

1·2는 자동 시작 범위를 확대하기 전에 해결합니다. 서버 저장 확인도 3과 함께 적용해 잘못된 완료 표시를 방지합니다. 각 기능 단위로 검수·문서·버전·커밋·푸시·배포·운영 확인 후 다음 단위로 진행합니다.

## 5. 재사용할 코드와 적용 주의

- `naver-blog-agent/extension/writer.js`: 입력 전후 스냅샷·순서 검증. BLOG HTML 변환과 추천 링크 기능을 먼저 목록화하고 손실 없이 변환합니다.
- `extension/background.js`: 탭 닫힘/교체 처리, 작성 중 재시작 안전 중지, 결과 선보관·보고만 재시도. 재시작 시 빈 편집기로 무조건 이동하거나 최종 클릭을 반복하지 않습니다.
- `extension/editor.js`: 본인 편집기 확인, 단일 프레임 변경, 이미지 AI 표시·설정 검증. 네이버 화면에서 실제 확인한 기능만 완료라고 기록합니다.
- `src/app/api/extension/finish/route.ts` v1.64 개선: DB 오류·0행·소유자·상태 조건을 확인, 동일 결과 재보고는 최초 시각 보존. BLOG의 입력 완료와 네이버 발행 완료 상태에 맞게 바꿔 사용합니다.
- 임대 만료나 PC 단절을 단순 queued 재전환으로 복구하지 않습니다. 이미 입력/발행됐을 가능성이 있으므로 실행 ID·로컬 기록·화면 확인이 필요합니다. 새 실행 식별자에 스키마 변경이 필요하면 승인 대상입니다.

## 6. 완료 판정과 남은 실제 검수

- 실제 함수 모의 검사: 기존 내용 혼합·중복·순서 뒤바뀜·선택 변경·다중 프레임·DB 오류/0행·응답 유실·탭 닫힘·worker 재시작·회원/블로그 불일치.
- 실제 회원 Chrome: 별도 빈 네이버 글에서 웹 최종 검수 후 보내기만으로 제목·마지막 문장·선택한 이미지 전부·카테고리·태그·AI 표시까지 적용되는지 확인합니다. 보내기한 원고와 실행한 원고의 ID/내용 일치, 원본 지문 보존을 확인합니다.
- 준비 완료 때 **최종 발행 클릭이 발생하지 않았음**을 확인합니다. 서버 publish_ready 기록만으로 외부 발행 성공을 주장하지 않습니다.
- 배포 전 `npm run build` 및 의미 있는 회귀 검사. 프로그램/manifest/ZIP/DB 버전 동기화 후 `node scripts/check-extension-release.mjs <실제 BLOG slug>`로 라이브 ZIP을 검증합니다.
- 이번 비교는 코드 조사·실제 검증 함수 모의 실행·일부 회원 화면·라이브 자산 확인입니다. BLOG 전체 입력/최종 발행 성공률의 실제 E2E 검수는 미실행입니다.

클로드는 구현 후 BLOG 프로젝트 문서에 변경 사항·검사 근거·커밋·배포·남은 일을 기록하고 이 공용 문서는 필요할 때 진행 상태만 갱신합니다. Codex는 BLOG 외부 메시지 전송이나 별도 에이전트 호출을 하지 않았습니다.
