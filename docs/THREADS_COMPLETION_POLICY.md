# 쓰레드(Threads) 자동화 완성 기준

> **상태: 초안(2026-10-24, 작성 claude-win-dotori [역할: analysis-planning]) — 담당 세션 확인 전.** 이 문서는 블로그 완성 기준(`BLOG_AUTOMATION_COMPLETION_POLICY.md`)의 형식을 따라 쓰레드 카테고리용으로 새로 쓴 초안이다. 아래 기준은 주인님 확정 지시가 아니라 **지금 코드·결정 기록에서 정리한 제안**이며, 주인님 확인과 쓰레드 담당 세션의 검토 뒤에 「확정」으로 바꾼다.
>
> 근거: [쓰레드 통합 분석](analysis-threads-consolidation-20261023/REPORT.md)(§8 주인님 결정 포함), [예약 기능 지침](SCHEDULER_POLICY.md)(기준 구현 `threads-content-ops`), [회원 연동 정보](MEMBER_INTEGRATIONS.md), 루트 `CLAUDE.md` 핵심 원칙 4(회원 본인 Meta 앱 — 2026-09-16 감사 이력), 5개 프로그램 현재 코드(기준 시점 2026-10-24).

## 적용 범위와 목표

쓰레드 카테고리 5개 프로그램 — `threads-easy-planner`(기획), `auto-threads-posting`(폴더 `threads/`, 포스팅), `threads-comment-reply`(댓글), `threads-affiliate-poster`(쇼핑제휴), `threads-content-ops`(운영) — 의 신규 개발·업그레이드·병합 비교에 적용한다.

완성 목표는 **글감 입력/수집 → 글(500자 이내)·이미지 완성 → 회원 검토 → 회원 본인 Meta 앱·계정으로 Threads 공식 API 게시 → 게시 결과 확인·기록**까지 이어지는 흐름이다. Threads는 공식 게시 API(`threads_publish`)가 있으므로 블로그처럼 크롬 확장으로 편집기에 입력하지 않고 **서버가 회원 토큰으로 직접 게시**하는 것이 기본이다. 글 생성·복사까지만 되는 상태는 전체 자동화 완료와 구분해 남은 단계를 적는다.

예외 — **기획 전용 프로그램**: `threads-easy-planner`는 주인님 결정(2026-10-23, 「기획만 하는 자동화 프로그램은 그냥 유지」)으로 게시 기능 없이 독립 유지한다. 이 프로그램은 「기획·초안 완성 → 복사」까지가 완성 범위이며, 게시가 필요한 회원은 `threads-content-ops`(같은 기획 기능을 v2.15에서 이식함)로 안내한다. 기획 앱에 게시 기능을 새로 넣을지는 주인님 결정 사항이다.

## 끝났다고 말할 조건 (글을 게시하는 프로그램)

아래를 모두 만족하고 각각의 검수 증거가 있어야 「완성」으로 보고한다.

1. **웹에서 완성** — 본문(500자 제한 안내·검사)·이미지·첫 댓글 등 게시할 내용을 프로그램 안에서 완성하고, 회원이 보관함에서 최종 확인·수정할 수 있다. 서버 저장(회원별 RLS)이며 브라우저 저장소에만 두지 않는다.
2. **회원 본인 연결로 게시** — 회원 본인 Meta 앱(App ID/Secret)·본인 Threads 계정 토큰으로만 게시한다. 연결은 공용 `member_platform_accounts`를 쓰고 한 번 연결하면 다른 쓰레드 프로그램이 재사용한다.
3. **회원이 고른 방식으로만 게시** — 아래 「회원이 고르는 항목」의 방식 중 회원이 고른 것만 실행한다.
4. **결과 기록** — 게시 결과(Threads 게시물 ID·permalink·게시 시각·실패 사유)를 글 기록에 남기고 화면에 보여 준다.
5. **중복 게시 방지** — 예약 실행은 상태를 `scheduled → publishing`으로 먼저 가져간 실행만 게시하고(조건부 update), `publishing`에 오래 머문 글은 실패로 돌릴 뿐 **자동으로 다시 게시하지 않는다**(Threads에 이미 올라갔을 수 있음). 기준: `threads-content-ops/lib/scheduledDispatch.ts`.
6. **30일 정리** — 회원이 만든 글감·초안·이미지는 생성일 기준 30일 뒤 자동 정리한다(예약 대기·게시 기록은 남김 — 기준 `threads-content-ops/lib/contentCleanup.ts`). 정리는 `cleanup-usage-log` 사본으로 회원별 기록을 남긴다.
7. **실제 화면 검수** — Claude Code는 메인 크롬, Codex는 엣지, agy는 웨일 실제 창에서 연결 → 생성 → 보관함 → 게시(승인된 시험 계정·비공개에 가까운 시험 글) → 결과 기록까지 확인한다. 모의 시험·예약 등록·실제 게시를 구분해 적는다.

## 회원이 고르는 항목

- **게시 방식(글 게시 프로그램)**: ⓐ **보관만**(초안 저장·복사, 게시 버튼은 회원이 누름) ⓑ **즉시 게시** ⓒ **예약 게시**. 원고마다 고를 수 있어야 하고, 회원이 고르지 않은 방식으로 게시하지 않는다. 현재 포스팅·쇼핑제휴·운영 3개는 세 방식이 코드에 있다([기능 비교표](THREADS_FEATURE_MATRIX.md) §2-4).
- **예약 실행 방식**: AIMaster 기본 Vercel / 회원 본인 cron-job.org 중 회원이 고른다(공용 `member-scheduler`, [예약 지침](SCHEDULER_POLICY.md)). 회원 cron-job.org에는 사이트 비밀값이 아니라 회원 전용 토큰(해시 저장)을 넣는다.
- **댓글 답글 게시(댓글자동화)**: 기본은 회원이 「답변승인」을 눌러야 게시한다. **자동 게시는 위험 안내에 동의한 회원만 켜는 선택**(설정 「⚡ 자동 게시(선택, 고급)」)이며 기본은 꺼짐이다. 댓글 자동 수집도 회원이 켜고 끄며 주기를 고른다(2026-10-23 주인님 결정 「고객이 본인이 선택하게 해줘」, v1.26).
- **이미지**: AI 생성(회원 본인 키) / 무료 사진(회원 본인 Pixabay·Pexels 키, 공용 `free-photo-search`) / 내 사진 / 없음 중 선택.
- **AI 공급사·모델**: 회원이 등록한 본인 키 중에서 고른다.

## 하지 않을 것

- **운영자 공용 Meta 앱을 회원이 함께 쓰게 하지 않는다.** 2026-09-16 감사에서 `threads/`·`threads-affiliate-poster`가 운영자 공용 앱(`THREADS_APP_ID`/`THREADS_APP_SECRET`, 개발 모드·테스터 1명)을 써서 다른 회원 연동이 「앱 ID를 인식할 수 없다」로 실패했고, 회원별 앱 등록 방식(`threads-comment-reply`)으로 전환했다. 새 쓰레드 기능도 처음부터 회원별 앱을 쓴다.
- 운영자·다른 회원의 AI 키·Threads 토큰으로 대신 처리하지 않는다(키가 없으면 「본인 키를 등록해 주세요」 안내).
- 결과가 불확실한 게시를 자동으로 다시 시도하지 않는다.
- 회원이 고르지 않은 게시 방식(예: 보관만 고른 글을 즉시 게시)으로 실행하지 않는다.
- 댓글 답글을 회원 동의 없이 자동 게시하지 않는다(Meta 정책·스팸 위험).
- 생성 데이터(글감·검색 캐시·초안·이미지)를 회원끼리 공유하지 않는다 — 현재 쇼핑제휴의 네이버 검색·트렌드 캐시가 회원 공유 상태로 남아 있다(작업표 THC-05).
- 외부 계정 비밀번호를 평문으로 저장하지 않는다 — 현재 포스팅의 NewsBlur 비밀번호가 평문 저장 상태로 남아 있다(작업표 THC-06).
- Meta 삭제·해제 콜백 주소, 회원 Meta 앱에 등록된 OAuth 콜백 주소를 지우거나 바꾸지 않는다(회원 연결이 끊김 — `threads/src/lib/oauthRedirect.ts`, 쇼핑제휴 `/api/threads/delete`·`/api/threads/uninstall`).
- AI 지시문은 Threads 맥락으로 쓴다(다른 플랫폼 지시문을 복사해 남기지 않음 — 댓글자동화 v1.26에서 유튜브 지시문을 고친 사례).

## 개발·비교·완료 보고

1. 플랜과 [프로그램 비교표](PROGRAM_CAPABILITY_MAP.md)·[쓰레드 기능 비교표](THREADS_FEATURE_MATRIX.md)에 게시 방식 세 가지, 예약 실행 방식, 결과 기록, 30일 정리의 구현 여부를 적는다.
2. 기능이 이미 있는 프로그램이 있으면 [기능 비교표](THREADS_FEATURE_MATRIX.md) §4 기준 코드를 가져다 쓴다(공용 기준 코드는 사본을 직접 고치지 않고 `node scripts/check-shared-modules.mjs --sync`).
3. 완료 보고에는 게시 방식 세 가지 각각의 구현·검수 상태, 실제 게시 시험 여부(계정·글 수), 결과 기록 확인, 비용 리포트를 적는다.
4. 인수인계에는 생성/편집, 보관함 저장, 게시(즉시·예약), 결과 기록, 정리의 검수 결과를 각각 남기고 확인하지 못한 단계는 미검수로 적는다.

## 이번 문서의 반영 상태

**초안 등록은 기능 구현이나 주인님 확정을 뜻하지 않는다.** 이 문서를 쓰면서 운영 코드·DB·권한·배포는 바꾸지 않았다. 확정 전 확인할 것: ① 위 기준을 쓰레드 메인 지침으로 확정할지 ② 기획 앱 예외(게시 없음) 유지 ③ 「보관만」을 게시 방식 ⓐ로 보는 것이 맞는지 ④ 쓰레드 담당 역할 지정(현재 [카테고리 지침 지도](CATEGORY_GUIDE_MAP.md)상 담당 없음).
