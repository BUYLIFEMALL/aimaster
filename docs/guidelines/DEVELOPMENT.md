# 개발 관련 지침 요약

[분야별 색인](README.md) · 기능 개발·보완·분석 작업 전에 해당 원문까지 확인합니다.

## 작업 전

1. [공통 원칙](COMMON.md)·[CLI 협업](COLLABORATION.md)을 확인하고 대상 프로그램의 최신 문서를 읽습니다.
2. [공통 아이디어 표](../PROGRAM_IDEA_BACKLOG.md), [역량 지도](../PROGRAM_CAPABILITY_MAP.md), [공용 기능 지도](../SHARED_FEATURE_MAP.md)에서 기존 기능·제안·기준 코드를 찾습니다.
3. 코드 수정 전에 문제·범위·순서·검수 방법·비용·버전/배포·인수인계 산출물을 담은 플랜을 주인님께 보고하고 해당 프로그램 `docs/PLAN_YYYYMMDD_*.md`에 남깁니다. 범위가 바뀌면 플랜도 갱신합니다.

## 구현 원칙

- **먼저 생각하기:** 가정과 불확실성을 드러내고, 해석이 여럿이면 차이·영향을 설명합니다.
- **단순하게 만들기:** 요청을 충족하는 최소 변경을 합니다. 미래를 가정한 기능·불필요한 추상화를 추가하지 않습니다.
- **필요한 곳만 수정하기:** 기존 스타일과 다른 CLI의 작업을 보존하고 관계없는 정리·리팩터링을 섞지 않습니다.
- **검증 가능한 목표로 진행하기:** 재현 조건과 통과 기준을 정하고 수정 결과를 확인합니다. 위 네 원칙은 루트 원문의 karpathy 지침을 요약한 것입니다.
- 한 작업을 검수·기록·결과 보고까지 종결한 뒤 다음 작업으로 넘어갑니다. 작은 수정의 배포 대기는 [비용·배포](COST_AND_DEPLOY.md)에 따라 명시합니다.

## 공용 부품과 AI 기능

- 검증된 기준 코드는 안정성 → 유지보수 용이성 순서로 선택합니다. 기준 파일을 수정하고 `node scripts/check-shared-modules.mjs --sync`로 사본에 반영합니다. 사본을 직접 고치지 않으며 프로그램별 차이는 호출부에서 처리합니다.
- 영향받는 모든 프로그램을 검사하고 프로그램별 결과와 미배포 목록을 남깁니다. 공용화는 코드 재사용이며 회원 생성 데이터 공유를 뜻하지 않습니다.
- 이미지 모델·주소·호출·대기·결과 수신은 `ai-image-studio` 기준을 따릅니다. 프롬프트 내용과 스타일은 각 프로그램 고유로 유지합니다. 인물 기본 묘사·해외 맥락 예외는 [이미지 프롬프트 규칙](../IMAGE_PROMPT_RULES.md)을 확인합니다.
- 현재 연도는 동적으로 주입합니다. 과거 사실과 현재 정보의 연도 표기를 구분해 기존 `year-policy` 등 검증된 부품과 대상 프로그램 규칙을 확인합니다.
- `timeoutMs × (retries+1)`과 앞뒤 작업을 합해 실행 시간 한도를 검토합니다. 유료 생성의 자동 재시도는 중복 과금 가능성을 확인합니다.

## 분석·검수·기록

- 레퍼런스 URL이 주어지면 화면뿐 아니라 HTML·JS 번들·설정·API·전체 문구를 조사해 근거와 구현 플랜을 남깁니다. 미확인 부분은 추측과 구분합니다.
- 소스가 없는 EXE·앱·확장 분석은 [REA 지침](../REA_REVERSE_ENGINEERING.md)을 따릅니다. 원본을 보존하고 출처 불명 실행 파일은 정적 분석합니다. 참고 자료는 `D:\PDS`, 분석 원본은 `D:\PDS\Program_dev`에서 먼저 찾습니다.
- 변경 영향에 맞는 시험·타입 검사·필요한 로컬 빌드를 하고, 실제 회원 화면과 운영 검증을 구분합니다. 오류는 [에러 처리](ERROR_HANDLING.md), 종료 기록은 [서브프로그램](SUBPROGRAMS.md)을 따릅니다.
- 기능 안정화가 우선이며 검증된 기능을 점진적으로 레퍼런스화합니다. 아이디어는 개발·디자인·창의적 자동화 관점과 안정성·적용성·편의성 기준으로 기록하고 제안/구현/운영 완료를 구분합니다.
