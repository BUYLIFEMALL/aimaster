2026-10-16 주인님 지시: 「기존 키값으로도 새로 등록하는 키값으로도 정상 운영」, 「어느 정도 안정화되면 기존 값을 삭제」, 「메인 지침과 인수인계 문서에 기록」.

## 기본 원칙

기존 이름으로만 등록되어 있어도 정상 운영하며, 새 이름으로만 등록해도 정상 운영해야 합니다. 두 이름이 함께 있으면 **새 이름을 우선**합니다. 새 항목이 없거나 공백이면 기존 항목을 사용합니다. 설정된 키가 인증에 실패했다고 다른 키를 자동으로 재시도하지 않습니다.

| 용도 | 새 이름(우선) | 기존 이름(호환 유지) |
|---|---|---|
| 브라우저·회원 세션용 공개 키 | `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| 서버 전용 관리자 키 | `SUPABASE_SECRET_KEY` | `SUPABASE_SERVICE_ROLE_KEY` |

- 변수 이름과 값의 형식은 별개입니다. 기존 `ANON_KEY` 변수에도 현재 Publishable key가 들어갈 수 있습니다. 기존 `SERVICE_ROLE_KEY` 변수에도 현재 Secret key가 들어갈 수 있습니다. 실제 레거시 JWT 키는 Supabase에서 유효한 동안 사용할 수 있습니다.
- 공용 프로젝트 URL은 기존 `NEXT_PUBLIC_SUPABASE_URL`을 사용합니다. 키와 URL은 같은 Supabase 프로젝트의 값이어야 합니다.
- 공개 키 선택과 서버 키 선택은 따로 처리합니다. 서버 키를 공개 키의 대체 값으로 사용하지 않습니다. 비밀 키를 `NEXT_PUBLIC_` 변수에 넣지 않습니다.
- 브라우저가 읽는 공개 변수는 Next.js 빌드 시 들어가므로 **변수 등록·변경 후 재배포가 필요**합니다. 코드는 `process.env.NEXT_PUBLIC_...`를 직접 참조해야 하며 동적 변수 조회로 바꾸지 않습니다.
- 이것은 AIMaster 플랫폼 DB 연결 설정입니다. 회원 본인 AI API 키·외부 계정 규칙을 바꾸거나 운영자 AI 키를 회원에게 제공하는 변경이 아닙니다.

## 안정화 기간에는 삭제하지 않습니다

1. **기존 Vercel 환경변수와 로컬 설정 값을 유지**합니다. 새 이름 추가는 선택이며 기존 값을 그대로 둬도 운영됩니다.
2. **Supabase 대시보드에서 기존 키 삭제·폐기·레거시 키 비활성화·JWT 비밀 변경을 하지 않습니다.** Vercel 변수 이름 정리와 실제 키 폐기는 다른 작업입니다.
3. 안정화는 단순히 날짜가 지났다는 이유로 판단하지 않습니다. 로그인·세션 갱신·회원 권한·DB/파일 접근·관련 확장 기능이 운영에서 정상이고, 전환 대상의 모든 배포 환경을 확인해야 합니다.
4. 안정화 확인 후 주인님과 삭제 시점을 확정하고 기존 항목 정리 작업을 따로 진행합니다. 그 전에는 기존 변수나 키를 자동 삭제하지 않습니다. 코드의 기존 이름 호환 처리도 유지합니다.

## 주인님이 Vercel에서 하실 일

**지금 필수로 하실 작업은 없습니다. 기존 항목을 그대로 두시면 됩니다.** 새 이름도 등록해 두고 싶으실 때만 다음 순서로 진행합니다.

2026-10-16 실제 Vercel 목록 확인: **메인 `aimaster` Production에는 새·기존 공개 키 이름과 새·기존 서버 키 이름이 이미 함께 등록**되어 있습니다. 메인은 중복 추가할 필요가 없습니다. 이후 주인님이 `blog-content-maker` Production에도 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 추가했고, 기존 공개 키와 같은 값임을 확인했습니다. 블로그는 공개 키의 새·기존 이름 공존, 서버 키는 기존 `SUPABASE_SERVICE_ROLE_KEY` 유지 상태입니다. 아래는 새 이름이 없는 프로젝트에 적용할 안내입니다. Vercel Secret 항목의 로컬 다운로드 대체 문자열은 실제 키가 아니므로 그것을 인증 검사에 사용하지 않습니다.

1. Vercel에서 **`aimaster` 프로젝트 → Environment Variables**를 엽니다.
2. 기존 `NEXT_PUBLIC_SUPABASE_ANON_KEY`의 값을 복사합니다. 기존 항목은 수정·삭제하지 않습니다.
3. 환경변수 추가에서 이름을 **`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`**, 값은 방금 복사한 Publishable key로 넣습니다.
4. 적용 환경은 기존 항목과 같게 선택합니다. 기존 항목이 `All Environments`이면 새 항목도 같은 환경들에 적용합니다.
5. 저장하면 공개 키의 기존 이름·새 이름 두 항목이 함께 있어야 합니다.
6. 서버 키도 새 이름으로 등록하려면 기존 `SUPABASE_SERVICE_ROLE_KEY` 값을 새 항목 **`SUPABASE_SECRET_KEY`**에 복사합니다. 공개 키와 혼동하지 않습니다. 기존 서버 키 항목도 유지합니다.
7. 등록 후 에이전트에게 등록한 프로젝트 이름을 알려줍니다. 에이전트가 해당 프로젝트 재배포·로그인·DB 연결·버전 확인을 진행합니다. 키 값 자체는 대화에 붙이지 않습니다.
8. `blog-content-maker`도 새 이름으로 등록하고 싶다면 **그 프로젝트를 선택해 별도로** 같은 작업을 합니다. `aimaster`에 등록한 값이 다른 프로젝트에 자동 적용되지는 않습니다.

## 현재 적용 범위·재개 방법

- 이번 코드 적용 대상은 **메인 AIMaster**와 **`blog-content-maker`**입니다. 다른 독립 서브프로그램까지 일괄 전환한 것으로 보고하지 않습니다.
- 공통 클라이언트/서버/미들웨어, 블로그 설정 준비 판정과 검수 도구까지 같은 우선순위를 사용합니다. 서버 키 선택 모듈은 `server-only`로 브라우저 접근을 차단합니다.
- 다른 서브프로그램을 전환할 때는 그 폴더 지침을 먼저 읽고 브라우저·서버·미들웨어·설정 준비 판정·검수 스크립트의 직접 참조를 모두 확인합니다. 자체 배포 폴더 안에서 구현하고 해당 프로그램을 별도로 검수·버전 관리·배포합니다.
- 공통 설정 회귀 검사: `node --test scripts/test-supabase-env-compat.cjs`.
- 새 이름만 있는 경우의 브라우저·서버 검수는 영구 환경변수를 변경하지 않고 검수 프로세스에만 값을 전달합니다. 기존 운영 값의 삭제로 시험하지 않습니다.
