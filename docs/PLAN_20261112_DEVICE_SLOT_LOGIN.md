- 작성: 음악 담당 `claude-win-20261024-music` [역할: music]. 실행은 메인 사이트 담당 세션이 맡고, 운영 DB 적용은 메인 PC 세션이 합니다.
- 주인님 결정(2026-11-12 채팅): 「나로 해 플랜세워줘」. 같은 계정은 **PC 1곳 + 모바일 1곳**까지 동시에 접속합니다. 같은 종류끼리는 1곳만 허용합니다.
- 이 플랜이 `docs/REQUEST_20261112_MAINSITE_SCOPED_SIGNOUT.md` 3절의 「로그인 때 `scope: "others"`」를 **대신합니다**. 「로그아웃은 이 기기만」 부분은 그대로 유효합니다.
- 배경: `free-music-studio/docs/IMPROVEMENTS.md` 2026-11-12 「2차 조사」

## 1. 목표 (완료 기준)

| 상황 | 결과 |
|---|---|
| PC A에서 쓰다가 PC B에서 같은 계정으로 로그인 | A는 메인 사이트와 **모든 하위 프로그램**에서 로그아웃됩니다. B는 남습니다 |
| PC A를 켜 둔 채 휴대폰에서 같은 계정으로 로그인 | **A와 휴대폰 모두 남습니다** |
| 휴대폰 1에서 쓰다가 휴대폰 2(또는 태블릿)에서 로그인 | 휴대폰 1만 로그아웃됩니다 |
| 어느 곳에서든 로그아웃 버튼 누름 | 누른 곳(그 브라우저)만 로그아웃됩니다 |
| 확장 프로그램·서버 예약 작업 | 영향 없습니다(확장 10개는 전용 연결 토큰, 2026-11-12 확인) |

## 2. 지금 구조에서 확인한 사실

1. 로그인 화면이 **메인 사이트 한 곳이 아닙니다.** 하위 프로그램 60여 개가 각자 로그인 화면을 갖고 있습니다. 그래서 메인 로그인 화면만 고쳐서는 규칙이 지켜지지 않습니다.
2. 모든 로그인은 같은 Supabase 로그인 기록 표 `auth.sessions`에 한 줄씩 생깁니다. 이 표에는 `user_agent`(기기 정보) 칸이 있습니다(Lab DB에서 칸 구조 확인, 운영도 같은 Supabase Auth).
3. 하위 프로그램 중 30여 개(`src/lib/actions/auth.ts`처럼 서버 액션으로 로그인하는 곳)는 **서버가 대신 로그인합니다.** 이 경우 `user_agent`에는 휴대폰·PC가 아니라 서버 정보가 찍힐 가능성이 큽니다. 0단계에서 운영 기록으로 확인합니다.
4. 메인 사이트의 `user_sessions` + heartbeat(60초)는 메인 사이트만 봅니다. 지금은 새 로그인 때 **기기 종류와 상관없이** 예전 줄을 모두 지웁니다(`app/api/session/create/route.ts`).
5. 범위 없는 `signOut()`은 그 계정의 모든 기기를 끊습니다. 그래서 「세션 만료」 화면이 방금 로그인한 새 기기까지 끊습니다(요청서 2절).

## 3. 설계

### 3-1. 판정은 DB 한 곳에서 (핵심)
`auth.sessions`에 새 줄이 생길 때 실행되는 트리거 함수 `public.enforce_login_device_slot()`(security definer)를 둡니다.

- 기기 종류는 `user_agent`로 나눕니다.
  - `mobile`: `Mobi`, `Android`, `iPhone`, `iPad`가 들어 있으면 모바일입니다. 태블릿도 모바일로 봅니다.
  - `pc`: 그 밖의 브라우저(`Mozilla/`로 시작)입니다.
  - `other`: 브라우저가 아닌 경우(서버·데스크톱 앱 등)입니다. 이 경우에는 아무것도 끊지 않습니다.
- 새 줄이 `pc`나 `mobile`이면, **같은 사용자·같은 종류의 예전 줄을 `auth.sessions`에서 지웁니다.** 갱신 토큰(`auth.refresh_tokens`)은 연쇄 삭제됩니다. 그 결과 예전 기기는 모든 프로그램에서 다음 확인 때 로그인이 풀립니다.
- `site_settings.concurrent_login_policy`가 `force_logout`일 때만 동작합니다.
- **예외 계정(결정 2, 2026-11-12 주인님 확정 「관리자 계정과 테스트 계정은 1인 1PC정책에서 예외로 지정해」)**: 관리자·시험 계정은 동시 접속 제한을 받지 않습니다. 기준은 DB 한 곳 `profiles.concurrent_login_exempt = true`이며, 코드에 이메일을 적지 않습니다(`retention_exempt`와 같은 방식). 마이그레이션에서 칸을 추가하고 두 계정만 `true`로 켭니다. 트리거와 메인 사이트 `/api/session/create`(`user_sessions` 줄 지우기) 모두 이 계정은 건너뜁니다. 실물 확인(5절)은 이 값을 시험 계정만 잠시 끄고 한 뒤 다시 켭니다.
- 토큰을 새로 고칠 때는 새 줄이 생기지 않으므로, 이 트리거는 **로그인할 때만** 동작합니다.

### 3-2. 서버 로그인 프로그램은 기기 정보를 넘기도록 (결정 1)
서버 액션으로 로그인하는 프로그램은 로그인 때 브라우저의 `user-agent` 머리글을 Supabase에 그대로 넘깁니다. 예: `createServerClient(..., { global: { headers: { "User-Agent": (await headers()).get("user-agent") ?? "" } } })`. 이 처리는 **각 프로그램을 다음에 배포할 때** 함께 넣습니다. 넣기 전까지는 그 프로그램에서 한 로그인이 `other`로 분류되어 제한이 걸리지 않습니다. 끊김이 덜한 쪽으로만 틀리므로 회원 피해는 없습니다.

### 3-3. 메인 사이트 수정 (빌드 1회)
- `app/api/session/create/route.ts`: `force_logout`일 때 **같은 기기 종류의 `user_sessions` 줄만** 지웁니다. 예외 계정이면 지우지 않습니다. 종류는 `device_info`(브라우저 `navigator.userAgent`)로 3-1과 같은 규칙으로 나눕니다. 판정 함수는 `lib/session/deviceKind.ts` 하나로 둡니다.
- `user_sessions`에 `device_kind text` 칸을 추가합니다(마이그레이션). 예전 줄은 `device_info`로 채웁니다.
- 로그인 화면 `LoginForm.tsx`는 `scope: "others"`를 **부르지 않습니다.** 트리거가 대신합니다. 세션 만료(36행)와 409(79행)는 `signOut({ scope: "local" })`로 바꿉니다.
- 로그아웃 8곳은 `scope: "local"`로 바꿉니다(요청서 3절 표). 비밀번호 재설정은 그대로 둡니다.

### 3-4. 하위 프로그램 (따로 배포하지 않음)
다음 배포 때 두 가지를 함께 넣습니다. 첫째, 로그아웃 버튼을 `signOut({ scope: "local" })`로 바꿉니다. 둘째, 서버 로그인이면 3-2를 넣습니다. 각 프로그램 `docs/IMPROVEMENTS.md` 미배포 대기에 한 줄씩 적습니다(담당별 요청). `pending-check.mjs`에 자동 알림을 넣을지는 결정 4입니다.

## 5. 실물 확인 (시험 계정)

1. PC 브라우저 A(ego lite)에서 로그인하고 메인 사이트·무료음악을 엽니다.
2. 휴대폰에서 같은 계정으로 로그인합니다. → **A와 휴대폰 모두 2분 뒤에도 로그인 상태**여야 합니다.
3. PC 브라우저 B(크롬)에서 로그인합니다. → A는 메인 사이트 60초 안, 무료음악은 새로 고칠 때 로그인 화면이 나와야 합니다. **B와 휴대폰은 남아야 합니다.**
4. B에서 로그아웃합니다. → B만 로그아웃되고 휴대폰은 남아야 합니다.
5. 운영 `auth.sessions`에서 그 계정 줄이 PC 0~1개, 모바일 0~1개인지 대조합니다.
