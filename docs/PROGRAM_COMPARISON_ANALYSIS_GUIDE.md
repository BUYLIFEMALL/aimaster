## 2. 1단계 — 자동 수집 (읽기 전용 스크립트)
```bash
node scripts/analyze-category.mjs "<카테고리 slug 또는 이름>"     # 예: "scraping&plan", "유튜브"
node scripts/analyze-category.mjs --slugs a-slug,b-slug          # 카테고리 대신 프로그램을 직접 지정
```
- 운영 DB에서 프로그램 이름·slug·버전·공개 여부·배지·**권한 회원 수**·**사용 기록(`usage_logs`) 수·회원 수(관리자 제외)·최근 사용일**을 읽고,
- 각 폴더 코드에서 **파일·줄 수·API 수·자체 DB 표·브라우저 저장(localStorage·IndexedDB)·본인 키 사용 파일 수·많이 쓰는 AI 모델·주요 라이브러리**를 센다.
- 서비스 키는 루트 `.env.local`에서 읽고 출력하지 않는다. DB에는 GET만 한다.
- 결과 표를 보고서 §1의 바탕으로 쓴다. 폴더가 「(못 찾음)」이면 `programs.slug`와 코드의 `…SLUG` 상수가 다른 것이니 직접 찾아 적는다.

## 3. 2단계 — 코드·화면 확인 체크리스트 (프로그램마다)
자동 수집 숫자만으로 판단하지 않는다. 아래 9가지를 직접 확인해 표 1에 쓴다.

| # | 확인할 것 | 어떻게 | 왜 중요한가 |
|---|---|---|---|
| 1 | 핵심 흐름(입력 → 처리 → 출력) | `AGENTS.md`·`docs/PROGRAM_CAPABILITY_MAP.md` 카드 + 주요 화면·API 코드 | 「같은 일을 하는가」 판단의 기준 |
| 2 | 결과물을 어디에 저장하나 | 자체 DB 표 / 브라우저 저장 / 저장 없음 / 외부(Drive 등) | 브라우저에만 저장하면 기기를 바꾸면 사라짐 → 합칠 때 서버 저장으로 고칠 단점 |
| 3 | 브라우저 저장의 내용 | localStorage가 1 이상이면 그 코드를 열어 **키·결과물·설정**인지 구분 | API 키가 브라우저에 있으면 보안 단점(최상위 규칙 점검) |
| 4 | AI 공급자·모델 | 수집 표의 모델 + 호출 코드 | 한 공급자만 되는지, 구형·종료 모델(예: `gemini-1.5-*`, Imagen 3)이 남았는지 |
| 5 | 키 처리 | 서버가 `user_api_keys`(본인 키)에서 읽는가 | 최상위 규칙(본인 키, 폴백 금지) — 어긋나면 「버릴 단점」 |
| 6 | 회원 데이터 격리 | 다른 회원과 공유하는 캐시·전역 데이터가 있는가 | 최상위 규칙(생성 데이터 회원별·30일) |
| 7 | 30일 자동 삭제 | 정리 작업(`api/cron/cleanup*`)이 있는가 | 없으면 기준 앱 선정 때 감점, 합칠 때 보강 |
| 8 | 완성도·안정성 | 버전, 테스트 유무, 배지(BEST), `IMPROVEMENTS.md`의 미해결 문제 | 기준 앱 선정 |
| 9 | 외부 연동·특수 라이브러리 | OAuth·크롤링(playwright·cheerio)·문서 변환(pptxgenjs·docx 등) | 고유 기능이면 독립 유지 근거 |

- 숫자는 반드시 실제 값(권한 회원 수, 사용 기록 수)을 쓴다. 이메일 등 개인정보는 보고서에 쓰지 않는다(「일반 회원 1명」·「시험 계정」처럼 구분만).
- 사용 기록이 0이면 「회원 사용 추이로 판단 불가 → 기능 겹침·저장/키 안전성 기준」이라고 명시한다.

## 4. 3단계 — 판단 기준
### 4-1. 합칠 조건 (둘 이상 해당하면 합칠 후보)
1. **같은 일**을 한다(입력·출력이 같거나 한쪽이 다른 쪽의 일부).
2. **같은 사용자**가 쓴다(예: 마케터 / 개발자 / 글 쓰는 사람).
3. 합치면 **한 흐름**으로 이어진다(예: 초안 쓰기 → 문체 바꾸기 → 다듬기, 설계 → 저장 → 재사용).

### 4-2. 기준(남길) 앱을 고르는 순서
1. 회원 영향: 권한 회원 수·BEST/FREE 배지·실제 사용 기록이 많은 쪽(회원이 이미 익숙한 주소를 유지).
2. 저장·키 안전성: 서버 저장 + 본인 키 + 30일 삭제를 갖춘 쪽(고칠 일이 적음).
3. 완성도: 기능 폭·버전·테스트·알려진 문제가 적은 쪽.
4. 위 셋이 비슷하면 **옮길 코드가 적은 쪽**(작업량·위험이 작은 방향)을 기준으로 한다. 유튜브 병합 E처럼 실제 코드를 보고 방향을 뒤집는 것도 허용(보고서에 이유 기록).

### 4-3. 장점은 더하고 단점은 뺀다
- 「가져올 장점」은 합쳐지는 쪽에만 있는 기능을 기능 이름으로 구체적으로 쓴다(예: 「화면에서 영역 직접 선택」).
- 「버릴 단점」은 **어떻게 해결하는지까지** 쓴다. 자주 나오는 단점과 해결:

| 단점 | 해결 |
|---|---|
| 결과물·설정을 브라우저에만 저장 | 서버 DB 표(회원별 RLS)로 옮기고, 기존 브라우저 자료는 첫 접속 때 「가져오기」 버튼 |
| AI 공급자 하나·구형 모델 | 기준 앱의 공급자 선택·최신 모델(이미지는 `ai-image-studio` 기준 — `CLAUDE.md` 이미지 규칙) |
| 회원 공용 캐시·운영자 키 | 회원별 저장으로 바꿈(최상위 규칙) |
| 저장 없음(만든 것이 사라짐) | 기준 앱의 프로젝트 저장에 넣음 |
| 30일 삭제 없음 | 기준 앱의 정리 작업에 포함 |

### 4-4. 독립으로 남길 조건 (하나라도 해당하면 남김 — 이유를 표에 씀)
1. **입력·출력이 고유**하다(예: 문서 → PPTX, 이미지 → 스토리보드).
2. **사용자가 다르다**(예: 마케터용 랜딩 기획 vs 개발자용 UI 부품).
3. **저장·동작 방식이 근본적으로 다르다**(예: AI 없이 쓰는 마크다운 + Drive 동기화 vs AI 서버 문서).
4. 합치면 오히려 메뉴가 복잡해지고 얻는 공유 코드가 적다.
5. 카테고리가 맞지 않다 → 남기되 **카테고리 이동을 제안**(DB 값만, 주인님 결정).

### 4-5. 우선순위
1순위: 겹침이 확실하고 단점(보안·데이터 유실) 해소 효과가 큰 묶음 → 마지막: 겹침이 중간이고 작업량이 큰 묶음(보류 가능으로 표시).

## 5. 출력 양식
### 5-1. 보고서 파일
- 위치: `docs/analysis-<카테고리 영문>-consolidation-<YYYYMMDD>/REPORT.md` (병합 실행 때 백업 JSON 등도 같은 폴더).
- 맨 위 인용 블록: 주인님 지시 원문 요약 · 대상(①/② + DB ref) · 「코드·DB 변경 없음 — 분석만」 · 근거 출처.
- 섹션과 표(이 순서·이 열 그대로):

**§1 프로그램별 분석**
| # | 프로그램 (slug · 폴더 · 버전·배지) | 핵심 로직·기능 | 저장 / AI / 키 | 장점 | 단점·한계 | 권한 회원 |
|---|---|---|---|---|---|---|

표 아래에 사용 기록 해석 한 줄, 공통 구조(권한·본인 키) 한 줄.

**§2 병합 결정 (N개 → M개)**
| 묶음 | 합칠 프로그램(→ 기준) | 남는 기준(이유) | 가져올 장점 | 버릴 단점(이렇게 해결) | 우선순위 |
|---|---|---|---|---|---|

**§3 독립으로 남길 프로그램**
| 프로그램 | 남기는 이유 | 겹쳐 보이는 프로그램과 다른 점 | 제안 |
|---|---|---|---|

**§4 병합 진행 방식** — §6 절차 요약 + 배지(FREE) 처리 + 순서 + 비용(새 DB 표 필요 여부 포함).

**§5 확인 필요(주인님 결정)** — 번호 목록. 묶음·순서 동의, 배지, DB 변경, 카테고리 이동 등.

### 5-2. 채팅 보고
- 첫 문장에 결론(「N개를 M개로: ○묶음 합치고 ○개 독립」)과 「분석만, 코드·DB 변경 없음」.
- 판단 근거 한 단락(무엇을 봤는지, 사용 기록이 비었으면 무엇으로 판단했는지).
- 표 3개(§1은 열을 줄여도 됨: 프로그램·핵심 기능·저장/AI·장점·단점·권한 회원) → 「결정해 주실 것」 번호 목록 → 보고서 경로·커밋.
- 한국어 존댓말, 전문 용어만 영어(루트 `CLAUDE.md` 대화 규칙).

### 5-3. 인수인계
- `docs/HANDOFF.md` 맨 위에 한 항목(결론·묶음·보고서 링크·「주인님 결정 대기」).
- 결정 전에는 각 프로그램 `AGENTS.md`를 고치지 않는다(병합을 시작할 때 묶음별로 기록).

## 6. 결정 뒤 병합 실행 절차 (묶음마다 하나씩)
1. 플랜(대상 ①·DB ref·옮길 기능·버릴 단점·DB 변경·버전·검수·비용) → 주인님 확인. `docs/ACTIVE_WORK.md`에 두 폴더 등록.
2. 운영 DB `programs` 두 행 백업 JSON을 보고서 폴더에 저장(`backup-programs-before-merge-<묶음>.json`).
3. 기준 앱에 기능을 옮기고(가져올 장점), 버릴 단점을 해결. 공용 기준 코드가 있으면 사본으로(`docs/SHARED_FEATURE_MAP.md`).
4. 옛 앱은 **주소를 지우지 않고** 기준 앱으로 이동 안내 화면만 남김(회원 북마크·외부 등록 콜백 보호). 옛 앱 API를 외부에서 부르면 410 또는 전달.
5. 권한 합치기: 옛 앱 권한 회원에게 기준 앱 권한을 같은 기간으로 부여(이미 있으면 긴 쪽). FREE·VIP 자동 부여 규칙 확인(`docs/ADMIN_POLICY_GUIDELINES.md`).
6. 카탈로그: 옛 앱 `is_active=false`, 기준 앱 이름·설명·상세 소개 갱신(`docs/PROGRAM_DESCRIPTION_STANDARD.md`).
7. 배포·검수(관리자 + 시험 계정 크롬), 버전 +0.01(코드+DB), 역량 지도 카드에 「병합됨 → 대상 slug(날짜)」.
8. 사용 종료 코드 정리는 **백업 폴더 `D:\Antigravity\AIMaster_backup\retired-programs\` + git 태그 뒤**에만(메모리 규칙).
9. 보고서 §6 「진행 결과」에 묶음별 결과 표 추가, HANDOFF 갱신, ACTIVE_WORK 줄 삭제.

## 7. 자주 하는 실수
- 카드(요약)만 보고 판단 → 저장 위치·키 처리 같은 결정적 차이를 놓침(§3 필수).
- 사용 기록이 0인데 「사용자가 적다」고 단정 → 「기록을 안 남긴다」일 수 있음. 기록이 없으면 그렇다고 쓴다.
- 합칠 방향을 권한 수만으로 정함 → 옮길 코드가 큰 방향이면 위험·작업량이 커짐(§4-2의 4).
- 배지(FREE)·권한 회원 처리 결정을 빠뜨림 → §5 결정 목록에 항상 넣는다.
- 다른 CLI 담당 영역을 결정안에 넣음 → §1-2 확인.
