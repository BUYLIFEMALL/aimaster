## 4. 3단계 — 화면에서 보강·수정 (수정안 방식)

### 4-1. 왜 「바로 커밋」이 아니라 「수정안 → CLI 반영」인가
| 방식 | 장점 | 문제 | 판단 |
|---|---|---|---|
| A. 화면에서 GitHub에 바로 커밋 | 즉시 반영 | ① 쓰기 권한 GitHub 토큰을 운영 서버 비밀값으로 둬야 함 ② 원격이 공용 작업 폴더보다 앞서게 되어 **모든 세션의 다음 푸시가 거절됨**(안전 커밋 도우미는 원격을 받아 오지 않음) — 2026-10-23 인덱스 사고처럼 여러 세션이 엉킬 위험 ③ 여러 세션이 같은 문서를 동시에 고치는 충돌을 화면이 알 수 없음 | 비추천 |
| **B. 수정안을 DB에 저장 → 담당 CLI가 안전 커밋 도우미로 반영** | 토큰 불필요, 기존 커밋 규칙·충돌 검사 그대로, 반영 기록이 남음 | 반영까지 CLI 작업 1번이 필요(보통 다음 작업 시작 때) | **추천** |

### 4-2. 화면 기능
- 문서 읽기 화면의 **「✏️ 수정안 작성」**: 원문을 편집기에 불러와 고치기 → 미리보기 → **바뀐 줄 비교** → 메모와 함께 저장.
- 역할 카드의 **「📝 이 역할에 메모」**: 다음 작업 때 그 세션이 읽을 지시·질문을 남김.
- 「요청함」 목록: 수정안·메모마다 상태(대기 · 반영됨(커밋 번호) · 반려(사유)), 처리한 세션, 처리 시각.

### 4-3. 저장 구조 (운영 DB `esgxyikcnnvmlhygjkth`, 새 표 1개 — DB 변경이라 승인 필요)

### 4-4. CLI 반영 도구 `scripts/dev-requests.mjs`
- `list [--role <역할>]`: 대기 중 요청 보기 → 작업 전 규칙(§2-4)에서 실행한다.
- `apply <id> --as <세션>`:
  1. 현재 문서를 읽는다.
  2. 원문(`base_content`)과 같으면 수정본을 그대로 쓴다. 그사이 바뀌었으면 `git merge-file`로 3-way 병합을 하고, 진짜 충돌이면 멈추고 알린다.
  3. 안전 커밋 도우미로 커밋한다.
  4. 상태를 `applied`로 바꾸고 커밋 번호를 기록한다.
- `reject <id> --reason "…"`: 반려하고 사유를 남긴다.
- `note-done <id>`: 메모를 읽고 처리했음을 남긴다.
- 서버 키는 로컬 `.env.local`에서 읽는다(코드·문서에 넣지 않음).

## 6. 진행 순서
1. **1단계(문서·규칙)**: 역할 파일 9개 초안 → 카테고리 지도 → 개발분석표 칸 추가 → 작업 규칙 한 줄 → 커밋·푸시.
   - 역할 파일 초안은 확인된 사실만 쓴다. 각 역할 세션이 다음 작업 때 고쳐 확정한다.
   - 주인님은 1단계만으로도 GitHub에서 바로 볼 수 있다.
2. **2단계(읽기 화면)** + **3단계(수정안·메모)**: 함께 만들어 **배포 1번**으로 내보낸다.
   1. 읽기 함수 시험(37건 분류·역할 파일 읽기)
   2. `tsc`·`npm run build`(로컬)
   3. DB 표 만들기(승인 뒤)
   4. 푸시(메인 사이트 자동 빌드)
   5. 크롬 실제 창에서 검수
3. 검수: 관리자 계정으로 탭 6개·카드 펼치기·문서 링크 이동·수정안 저장 → `dev-requests.mjs apply`로 실제 반영 1건 → 화면에 「반영됨」 표시 확인. 모바일 폭. 일반 회원 계정(`buylifemall@naver.com`)은 차단 확인.
