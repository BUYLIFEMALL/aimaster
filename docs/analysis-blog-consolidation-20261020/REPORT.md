## 1. 추천 결론

**7개를 전부 하나로 합치기보다, 역할이 다른 4개를 남기고 중복 제작기 3개의 장점을 이관하는 방향을 추천합니다.**

| 남길 역할 | 기준 후보 | 흡수할 기능 | 이관 후 별도 신규 개발 중단 후보 |
|---|---|---|---|
| 네이버 일반 콘텐츠 제작·발행 준비 | 네이버 블로그 에이전트 | BLOG의 자료 수집/서식 편집/이미지 배치, 올인원의 사진 후기/템플릿 | BLOG(원문)생성 자동화, 네이버 블로그 올인원 |
| 키워드·트렌드·경쟁 기회 분석 | AI 블로그 키워드 자동화 | 작업실의 키워드 등급/추이 계산 중 검증된 부분 | 중복 ‘키워드 파인더’ 전체를 별도 제품으로 유지할 필요 없음 |

**이것은 제품 구성 추천입니다. 에이전트/SEO가 모든 면에서 이미 더 안정적이라는 판정은 아닙니다.** 에이전트의 옛 원고 자동 발행 기본값, 올인원의 부분 입력 성공 판정, 공개 이미지 경로와 30일 만료 점검을 먼저 해결/검증해야 기준 프로그램을 확정할 수 있습니다.

‘개발 중단’은 우선 **독립 신규 기능 개발을 멈추는 것**입니다. 기존 회원 접근 차단·사이트 삭제·권한 이전·데이터 이전·확장 폐기·도메인 삭제를 지금 실행한다는 의미가 아닙니다.

## 12. 비용과 의사결정

현재 프로그램별 이용량/요청 토큰/모델별 청구/서버 트래픽/실제 결함률을 조회하지 않았으므로 **월 비용 절감액·품질 향상률·개발일 수를 수치로 보장하지 않습니다.**

운영 개발에서는 작업실의 구간 수만큼 글 호출이 생길 수 있고, 에이전트/올인원은 기획·작성·윤문·검수, SEO는 짧은 본문 보강 최대 2회, 이미지와 검색은 별도 호출입니다. 통합한다고 모든 경로를 연달아 호출하면 비용이 오히려 늘어납니다. 기본 빠른 작성/사진 후기/정밀 집필 모드를 분리하고 예상 호출과 필요한 본인 키를 실행 전에 안내해야 합니다.

추가 개발 제안(미구현): **회원 개인 콘텐츠 작업 묶음**. 선택한 키워드의 근거·주제·자료·검수·원고·사진을 본인 작업 ID로 이어, 다른 화면으로 이동해도 다시 검색/생성하지 않고 필요한 단계만 실행합니다. 같은 회원/같은 권한 범위·원래 30일 만료 유지가 전제입니다. 화면 하나로 모든 기능을 모으는 것보다 반복 입력과 재과금을 줄이는 방향입니다.

승인 시 첫 개발 단위 추천: 다른 CLI의 에이전트 v1.97를 인수·검수한 다음, **에이전트 ‘사진으로 후기 쓰기’ 모드**를 올인원과 기능 대조표를 작성해 작은 범위로 이관합니다. 동시에 나머지 프로그램을 중단하지 않습니다.

## 13. 공식 자료와 해석 한계

- DataLab은 조회 결과의 최대를 100으로 둔 상대 비율입니다. 검색광고 월간 검색수와 단위가 다릅니다. [네이버 통합 검색어 트렌드](https://developers.naver.com/docs/serviceapi/datalab/search/search.md).
- 검색 API의 sim/date·total은 해당 API의 정렬/검색 결과 개수입니다. 이를 프로그램이 측정하지 않은 개인화 노출 순위나 블로그 공식 지수로 제시하지 않습니다. [네이버 블로그 검색 API](https://developers.naver.com/docs/serviceapi/search/blog/blog.md).
- 기존 코드에 C-Rank/D.I.A./홈판 표현이 있어도 알고리즘 내부 가중치·노출 보장·탐지 회피가 검증됐다는 뜻은 아닙니다. 이 문서의 ‘추천’은 소스 구조와 현재 사용자 목적을 비교한 설계 판단입니다.

### 0. 결론과 검토 범위

**공개 블로그 8개는 네 가지 핵심 역할을 중심으로 정리하고, 다른 카테고리는 목적별 결과 전달로 연결하는 안을 권합니다.** 네 역할은 키워드 분석, 간편·반복 제작/발행, 근거 중심 정밀 집필/개선, 티스토리 발행입니다. 서비스 입구를 한곳에서 안내하되 프로그램·권한·데이터를 지금 통째로 합치는 제안은 아닙니다.

콘텐츠 메이커에 세 번째 네이버 최종 발행 엔진을 새로 붙이는 기존 ③-2 플랜은 **재검토 후보**로 둡니다. 텍스트 제작·검수·발행은 SEO와 겹치고, 남은 강점은 제품 사진 합성·영상 첫/끝 장면·이미지 포함 내보내기입니다. 그 강점을 보존해 SEO와 이미지/영상 프로그램에 연결하는 편이 중복 개발을 줄일 가능성이 큽니다. 기능 동등성·원고/이미지 보존·권한 전환을 확인하기 전까지 콘텐츠 메이커를 닫지 않습니다.

| 미디어 경계 | 콘텐츠 메이커의 제품합성/장면 기획 → SEO에서 호출 가능한 작업 흐름 + 이미지/영상 카테고리로 연계 | 전문 이미지/영상 도구의 편집·저장·렌더를 유지 | 제품 원본·ALT·배치·장면쌍·ZIP | 블로그마다 이미지/영상 엔진을 새로 개발하지 않고 같은 회원 자산 ID/선택 파일 전달 | 중간. 동등성 확인 전 콘텐츠 메이커 유지 |

회원 영향: 현재 등록 행 집합 비교에서 BLOG→에이전트 대상 권한 행이 없는 회원은 **78명**, 올인원→에이전트·작업실→SEO·콘텐츠→SEO는 각각0명입니다. 246−196처럼 단순 뺄셈으로 구하지 않았습니다. 이 수치는 등록 행 차이일 뿐 실제 이용 가능 판정은 아니며 FREE/구독/등급/기간을 따로 평가해야 합니다.

에이전트는 BLOG FREE 이용자에게 quick 범위만 주는 코드가 있습니다. 기존 BLOG 원고가 quick 원고로 자동 변환되는 기능은 아니므로, 무료 회원의 과거 원고 접근을 잃게 만드는 전환은 안 됩니다. 배지 이전·권한 부여·자료 이전·원본 비공개/중단은 별도 결정과 검수 뒤 진행합니다.

### 6. 연계 구조 — 현재 가진 것을 재사용할 범위

직접적인 프로그램 간 서버 API 호출을 새로 난립시키지 않습니다. 기존 기준은 소유자가 같은 공용 DB 참조와 `work_inbox`, 파일/허용된 가져오기 경로입니다. 서버→서버 실행 호출과 회원이 선택한 결과 가져오기를 구분합니다.

권장 전달 계약(신규 구현 제안): `sourceSlug`, `sourceId`, `revisionId`, `kind`, `owner`, `createdAt`, `expiresAt`, 출처/검증 상태·선택한 asset ID. 본문 전체·키·토큰·긴 서명URL을 URL 쿼리에 싣지 않습니다. 목적지에서 본인·프로그램 권한·원고 최신성·수명을 다시 검사하고 같은 참조의 중복 전송을 구분합니다.

`work_inbox`는 이미 있지만 블로그에서 보내고 다시 받는 처리까지 있는 것은 아닙니다. 우선 할 일/상태/링크 연결에 쓰는 안을 권합니다. 기존 문서의 ‘가져온 페이지는 남음’을 생성 본문 보관기한 연장으로 자동 적용하면 안 됩니다. 복사/이관이 원본 생성일과 만료를 리셋하지 않게 설계하고, 본문 장기 보관은 사용자 다운로드 또는 별도 정책 결정과 구분합니다.

이미지 전송도 공용 기준 컴포넌트를 재사용하되 단순한 공개 URL만 넘기지 않습니다. 비공개/서명 이미지, AI 생성 표시·원본/수정본, ALT/위치/대표 이미지, 삭제/만료, 대상 프로그램의 용량/형식·비율을 함께 검증해야 왕복 작업이 줄어듭니다. 서버 비용 절감만을 이유로 다른 회원 자산을 공용 캐시로 묶지 않습니다.

글자수·HTML·이미지의 플랫폼별 차이를 감추지 않습니다. 네이버용 문단/인용·카테고리, 티스토리 HTML/TinyMCE, SNS 글/미디어 묶음, 쇼츠 대본·장면은 각각 어댑터로 변환하고 변환 초안을 확인합니다. 한 원고를 모든 채널에 그대로 뿌리는 자동화는 추천하지 않습니다.
