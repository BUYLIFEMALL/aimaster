### 2-2. 데이터 처리 주장과 차이

- 소개 문구: 「어떠한 개인정보도 서버로 전송하지 않으며, 모든 데이터는 이용자의 브라우저 내에서만 처리」.
- 개인정보처리방침(Google Docs, 한·영): 「어떤 형태의 사용자 데이터도 수집하지 않음, 개발사·제3자와 공유 없음」. 웹스토어 공개 선언도 「데이터를 수집·사용하지 않음」.
- **그런데 설정에는 개발자 서버(`*.maker39.workers.dev`) 접근 권한이 있다.** 용도는 확인하지 못했다. 가능성(모두 추정): ⓐ 네이버 검색광고 API 서명·호출을 대신해 주는 중계 서버(이때 검색한 키워드가 개발자 서버를 지난다) ⓑ 공지·최신 버전·허용 목록 확인 ⓒ 사용 통계. 「개인정보」는 아니어도 **검색어가 외부 서버로 갈 수 있다는 점**은 코드로만 확인할 수 있다.
- 네이버 검색광고 API는 원래 회원 본인 API 키(고객 ID·액세스 라이선스·비밀 키)와 서명이 필요하다. 설정 화면에서 회원 키를 받는지, 개발자 공용 키를 중계 서버에 두는지는 **미확인**이다. 후자라면 키 한도·차단 위험이 개발자 한 명에게 몰린다.

## 6. 우리에게 없는 것·가져올 것·하지 않을 것

### 6-1. 우리에게 없는 것

1. **검색 상위 상품의 카테고리 분포·카테고리 ID 추천** — 상품소싱은 회원이 카테고리를 고르고, 상세는 카테고리를 다루지 않는다.
2. **상품명 구성 도우미**(연관어 고르기·길이 확인) — 어디에도 없다.
3. **스마트스토어 태그 추천**(10개 태그 칸용) — 없다.
4. **쇼핑 자동완성어** — `blog-keyword`에 네이버 자동완성 코드(`blog-keyword/src/lib/kw/naver.ts`)는 있으나 블로그용이고 쇼핑 자동완성은 아니다.
5. **이커머스용 크롬 확장 자체**.

### 6-2. 가져올 것(후보 — 구현 전, 주인님 결정 필요)

| 후보 | 넣을 곳 | 방법(우리 방식) | 비용 |
|---|---|---|---|
| A. 「등록 정보 도우미」: 키워드 → 상위 상품 카테고리 분포·추천 카테고리 | 상품소싱(관심 상품 → 등록 준비) | 회원 본인 네이버 키로 **공식 쇼핑 검색 API**(`openapi.naver.com/v1/search/shop`, 상위 100개 `category1~4` 이름 제공)를 서버에서 불러 분포 계산. 카테고리 **ID**는 공식 검색 API에 없어 쇼핑인사이트 카테고리 코드 표와 이름 대조가 필요(확인 필요) | 무료 API(회원 키), AI 0 |
| B. 상품명·태그 초안 | 상세(상품 입력 화면) 또는 소싱 | 검색광고 연관어(이미 `lib/naver/searchAd.ts`)에서 회원이 골라 조합 + **네이버 상품명 가이드 검사**(길이·중복 단어·관련 없는 키워드 경고). 랜덤 조합은 넣지 않는다 | 무료(+선택 시 AI 1회) |
| C. 쇼핑 자동완성어 | 소싱 키워드 등록 화면 | `blog-keyword` 자동완성 코드를 기준으로 쇼핑용 확인 후 재사용 | 무료 |
| D. 결과를 상세로 넘기기 | 소싱 → 상세 | 기존 `lib/shopDetailLink.ts`에 상품명 초안·카테고리 칸만 추가 | 없음 |

### 6-3. 하지 않을 것

- **네이버·쿠팡 페이지 내부 자료 가로채기 확장**(MAIN 실행 공간에 끼어드는 방식) — 약관 회색 지대·잦은 고장·운영 부담. 공식 API로 되는 것은 웹에서 한다.
- **랜덤 키워드 상품명 조합** — 회원 스토어 노출 불이익(어뷰징) 위험.
- **개발자 공용 키·중계 서버로 검색광고 API 부르기** — 최상위 규칙(회원 본인 키)과 충돌.
- 쿠팡 검색 결과 대량 수집 — 쿠팡은 봇 차단이 강하고 공식 API(쿠팡파트너스)는 승인 대기다(`docs/PLATFORM_PATTERNS.md` §20 봇 탐지 원칙).

## 7. 판단 제안

- **판단: 「참고 + 일부 기능 흡수 후보(새 프로그램·확장은 만들지 않음)」.** 이 확장의 가치는 「등록 직전 카테고리·상품명·태그 정하기」라는 우리 이커머스 흐름의 빈칸을 보여 준 것이다. 상품소싱(발굴) → **(빈칸: 등록 정보 정하기)** → 상세(제작) → (대기: 마켓 등록 Phase 16·17) 순서에서 빈칸을 6-2의 A~D로 웹 안에서 채우는 방향이 맞다.
- 우선순위: A(카테고리 분포) + B(가이드 검사가 붙은 상품명 초안)가 핵심, C·D는 함께 하면 작은 일. 넣을 곳은 상품소싱이 자연스럽다(이미 검색광고·네이버 키를 받음). 상세는 받는 쪽으로만.
- 확인 필요(구현 전): 공식 쇼핑 검색 API 결과로 카테고리 ID를 얻을 수 있는지, 네이버 상품명 가이드 최신 기준(2026년) 원문.
- 기록: 이 분석은 `docs/EXTERNAL_PROGRAM_ANALYSIS_REGISTRY.md` 카드 추가 대상이다(이번 작업 범위 밖 — 문서 1개만 작성 지시).

### 「코드(CRX) 정적 분석이 필요한가」 의견

- **지금은 필요성이 낮다.** 기능 흡수 판단에 필요한 정보(대상 사이트·권한·스크립트 구성·화면 위치)는 웹스토어가 공개한 manifest로 이미 확인했고, 우리는 그 구조(페이지 가로채기)를 따라 하지 않을 것이기 때문이다.
- **필요해지는 경우**: ① 회원에게 이 확장을 추천·안내하려 할 때(「서버 전송 없음」 주장과 `maker39.workers.dev` 접근의 실제 용도, 검색어 전송 여부 검증) ② 카테고리 ID를 어디서 얻는지(네이버 내부 자료 필드 이름) 모르면 6-2 A의 방법을 정할 수 없을 때. 이때도 주인님 허락 뒤 **정적 분석만**(실행·설치 없음, 핵심 원칙 21, `docs/REA_REVERSE_ENGINEERING.md`)으로 `background.js`의 외부 호출 주소와 `interceptor.js`가 읽는 자료 이름만 확인하면 된다.
