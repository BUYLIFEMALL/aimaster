# C. 정책 검토 — 메이커 후속(P1 상품별 합성·P2 상품 반환) 저장·회원권한·보관

> **문서·읽기 전용 검토.** 제품 코드·운영 DB 쓰기·배포 없음. 운영 DB(`esgxyikcnnvmlhygjkth`)는 읽기 조회 3번만 했다.
> A(기능) 계약 문서는 아직 없어, [종합 분석 P1/P2](MAKER_UPDATE_REVIEW_20261113.md)의 제안 계약과 **현재 코드**를 기준으로 판정했다. A 계약이 나오면 §3 기준으로 대조한다.

## 0. 결론 요약

1. **P1(로컬 합성·ZIP)은 정책상 막을 것이 없다.** 서버에 아무것도 올리지 않으면 500MB·30일·`retention_exempt`·용량검사·`markPosted` 어느 것도 대상이 아니다. 새 DB도 필요 없다.
2. **P2(원래 상품으로 반환)는 기존 상세페이지 저장 규칙을 그대로 따르면 된다.** 반환 결과는 그 상품 폴더(`<회원>/products/<상품>/…`)에 새 버전으로 쌓이고, 상품과 함께 **상품 생성일 기준 30일**에 지워진다. 1차는 **DB 변경 없이** 가능하다.
3. **반드시 보완할 빈틈 3가지(기존 코드)** — P2 구현 때 같이 고친다.
   - 브라우저가 저장소에 바로 올리는 경로라 **용량 사전검사가 없다**(용량검사 공용 코드는 서버 전용, 상세페이지 사용처 0곳).
   - 섹션 저장 액션 `addCustomSectionImageAction`이 넘겨받은 이미지 주소가 **본인·그 상품 폴더인지 검사하지 않는다**.
   - 반환 메시지에 **상품 ID·수정본(revision)·일회용 작업 번호가 없다** — 지금은 「열려 있는 화면의 상품」이 암묵적으로 대상이다. 대량 반환에서는 부족하다.
4. **11번가 상세사진(`/i/`)은 구독 중에도 영구가 아니다.** 상세페이지 버킷이 아직 「포스팅 표시 버킷」이 아니라서, 구독 회원 파일은 **포스팅 보관 기간(라이트 90일·스탠다드 180일·프로 1년, 파일 생성일 기준)**이 지나면 중앙 정리가 지우고, 그 뒤 11번가 상품의 상세사진이 깨진다. 구독이 끝나면 다음 날 바로 깨진다(주인님 결정 3안 그대로). **지금 깨질 운영 링크는 0건**(링크 15개 모두 관리자·시험 계정).
5. 11월 21일 상세페이지 30일 정리 유예가 끝난다. 그날 일반 회원 상품 3개(10/22 이전 생성)가 정책대로 지워진다 — 정상 동작이며 손대지 않는다.

## 3. 반환(P2) 소유권·거절 기준

A 계약에 아래 값이 들어가야 한다. 비밀키·이메일·전화번호는 넣지 않는다.

| 값 | 누가 만드나 | 검사 |
|---|---|---|
| `jobId` (일회용) | 받는 쪽(상세페이지 창)이 보내기 직전 `crypto.randomUUID()`로 만들어 메모리에 보관 | 돌아온 메시지의 `jobId`가 다르면 무시. 한 번 쓰면 폐기(되풀이 반환 차단) |
| `productId` | 받는 쪽 | **지금 열린 상품과 같아야** 반영. 다르면 「다른 상품의 결과」로 거절 |
| `role` + `slot` | 받는 쪽 | `main`/`sub`/`detail` 중 하나, `detail`은 섹션 키 형식(`^[A-Za-z0-9_-]{1,100}$`) |
| `baseRevision` | 받는 쪽: 보낼 때의 `shop_products.updated_at`(섹션이면 `shop_product_images.updated_at`) | 서버 저장 직전 현재 값과 비교 → 다르면 **덮어쓰지 않고** 「그사이 상품이 바뀌었습니다 — 새 버전으로만 추가할까요?」 |
| `sourceRef` | 보내는 쪽 | 표시용(출처·원본 파일명). 저장 경로로 쓰지 않음 |

**거절 기준(모두 서버에서 다시 확인 — 브라우저 검사만 믿지 않는다)**
1. **다른 origin**: 기존처럼 정확한 주소 일치 + `e.source === 연 창`. 목록 밖 주소는 조용히 무시.
2. **다른 회원**: 서버 액션에서 `requireProgramAccess()` 사용자와 `shop_products.user_id`가 같아야 함(세션 RLS + `.eq("user_id", user.id)` 명시). 저장 경로는 반드시 `<user.id>/products/<productId>/`로 시작 — **`addCustomSectionImageAction`에 경로 검사 추가**(기존 빈틈).
3. **삭제된 상품**: 상품 행이 없으면 저장하지 않고, 방금 올린 파일은 지운다(기존 「DB 저장 실패 시 파일 삭제」와 같은 방식).
4. **묵은 revision**: 위 `baseRevision` 비교. 대표사진은 덮어쓰기 대신 이전 사진을 같은 상품 폴더에 남긴다(아래 §5).
5. **반환이 판매 상태를 바꾸지 않음**: `reviewed_at`·마켓 등록 기록·몰 승인 상태는 반환으로 바뀌지 않는다. 대표사진이 바뀌면 이미 등록된 마켓에는 자동 반영하지 않고 「마켓에는 다시 보내야 반영됩니다」만 안내.
6. **용량 초과**: 업로드 전에 서버 액션 하나(예: `prepareReturnAction(productId, totalBytes, baseRevision)`)가 소유·revision·`checkStorageQuota(admin, user.id, totalBytes)`를 한 번에 판정하고 통과할 때만 브라우저가 올린다. 막히면 「💾 저장공간이 가득 찼습니다」+ 구독 주소(`STORAGE_FULL`).

## 4. 11번가 `/i/` — 게시 후 노출에 주는 영향

| 경우 | 대표·추가 사진(11번가 CDN 복사) | 상세설명 사진(우리 `/i/` 참조) |

| 일반 회원 | 계속 보임 | 보내지 않음(글로 대체, 3안) |

| 구독 중, **포스팅 보관 기간 초과**(라이트 90·스탠다드 180·프로 365일, 파일 생성일 기준) | 계속 보임 | **깨짐** — 중앙 정리가 파일을 지우고 `/i/`가 404. 상품 행은 남아(상세 30일 정리에서 빠짐) 상세페이지 화면도 사진 없는 상품이 됨 |

| 관리자·시험 계정 | 계속 보임 | 계속 보임(무기한) |

- 원인: 상세 버킷이 표시 버킷이 아니라 **모든 파일을 「포스팅됨」으로 본다** — 그래서 지금은 오히려 길게 남는다. 그러나 「포스팅 기간」이 11번가 판매 기간과 무관하게 **파일 생성일**부터 센다.
- 쿠팡 운영도 같은 `/i/` 구조다(링크 22개, 모두 예외 계정). 쿠팡이 상세사진을 복사하는지는 이번에 확인하지 않았다(미확인).
- **권장(결정 필요, 주인님)**: ① 11번가 보내기 직후 상세사진 경로에 `markPosted`를 부른다 — 표시가 있는 파일만 포스팅 기간, 나머지 상세 파일은 생성 기간으로 정리돼 정책과 맞아진다. 단 「버킷이 표시 버킷이 되면 표시 없는 구독 회원 파일이 생성 기간(30/60/180일)으로 줄어드는」 변화가 상세페이지 전체에 생기므로 상세페이지 담당과 같이 배포해야 한다. ② 보내기 화면·저장 구독 해지 화면에 「구독이 끝나거나 보관 기간이 지나면 11번가 상세 사진이 보이지 않습니다. 오래 팔 상품은 11번가에 직접 사진을 올려 두세요」 안내. ③ 장기적으로 11번가 이미지 업로드 API가 있으면 상세사진도 복사(11번가 명세 확인 필요, 미확인).

## 7. 운영자료를 지우지 않는 회귀시험안

원칙: 운영 상품·파일·링크를 지워서 시험하지 않는다. 날짜를 앞당기는 시험도 운영 DB에서 하지 않는다.

| 시험 | 방법 | 기대 |
|---|---|---|
| 다른 origin | 로컬 시험 페이지에서 같은 형식 메시지 전송 | 무시, 저장 0 |
| 다른 회원 | 시험 계정으로 관리자 상품 ID를 넣어 `prepareReturnAction` 호출(단위 시험 또는 시험 계정 실제 호출) | 거절, 저장 0 |
| 남의 경로 주소 | `addCustomSectionImageAction`에 다른 회원 경로 | 거절(새 검사) |
| 삭제 상품 | 시험 계정이 **새로 만든** 시험 상품을 지운 뒤 열린 창에서 반환 | 거절, 올린 파일 정리 |
| 묵은 revision | 두 창에서 같은 상품, 한쪽이 먼저 저장 | 뒤쪽은 덮어쓰기 없이 새 버전 제안 |
| 용량 초과 | 함수 단위 시험(`checkStorageQuota`에 가짜 rpc가 `allowed:false`) | 업로드 전 차단 문구 |
| 30일·포스팅 판정 | 정리 함수의 대상 계산을 **읽기 전용**(목록만, 삭제 호출 없음)으로 돌리거나 Lab DB에 같은 함수를 만들어 날짜 바꿔 시험 | 연장 회원·표시 유무별 대상이 §2·§4와 같음 |
| `/i/` 만료 | Lab 또는 단위 시험(만료 지난 행 + 예외/비예외) | 예외면 200, 아니면 404 |
| 11월 21일 유예 종료 | 11/22 정리 응답의 개수만 확인(`productsDeleted`) — 예외 계정 상품 2개가 남아 있는지 읽기 확인 | 일반 회원 3개만 정리, 예외 2개 유지 |
