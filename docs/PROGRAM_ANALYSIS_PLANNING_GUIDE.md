## 2. ①·② 원본 확인과 정적 분석

### 2-1. 시작 전 확인
1. 원본은 `D:\PDS\Program_dev`에서 찾는다(주인님이 파일 이름만 말해도). 공개 배포처가 있으면 **최신 버전인지**·**해시가 같은지** 확인한다.
2. 소스 공개 여부를 확인한다. 공개 소스가 의존성(라이브러리)뿐인지, 앱 자체 소스인지 구분해 보고서에 적는다(예: `SOURCE_MANIFEST.json`의 `contains_private_application_sources`).
3. 권리: 남의 상용·무료 프로그램은 **기능만 참고**한다. 코드·지시문(프롬프트)·동봉 지식 데이터·문구·이름·아이콘은 옮기지 않는다. 이전에 같은 원본을 참고한 우리 프로그램이 있는지 먼저 찾는다(`grep -i <원본 이름>` — 예: 도톨이 → `blog-workroom`).
4. 출처 모르는 실행 파일은 **실행하지 않는다**. 작업 폴더는 저장소 밖(CLI 임시 폴더 또는 `D:\PDS\Program_dev\<대상>_work\`)의 **새 빈 폴더**로 하고, 내가 쓴 스크립트는 다른 폴더에 둔다.
5. **중복 분석부터 확인한다**: SHA-256을 구한 뒤 앞 8자리로 `grep -rn "<앞 8자리>" docs/ */docs/`를 돌리고, 원본 이름으로도 찾는다. 같은 해시면 다시 풀지 말고 이전 보고서를 기준으로 **현재 우리 프로그램과의 차이만** 다시 본다(2026-10-24 Lyricbi 1.9.0 사례). 이름만 같고 해시가 다르면 이전 보고서와 **바뀐 기능만** 비교한다(REA `compare_application_versions`·`compare_artifacts`).

## 3. ③ 우리 프로그램과 비교

1. [프로그램 비교표](PROGRAM_CAPABILITY_MAP.md)에서 같은 분야 카드를 모두 읽는다. 블로그 분야는 [블로그 기능 비교표](BLOG_FEATURE_MATRIX.md)(블로그 개발 기준 문서, 2026-10-24 블로그 담당)를 함께 본다. 진행 중인 병합·통합 계획(`docs/analysis-*`)과 담당 세션을 확인한다.
2. **겹치는 기능 표**: 원본 기능 × 우리 프로그램(✅ 있음 / △ 일부 / — 없음 / ❌ 필요한데 없음). 비교표 카드만 믿지 말고 의심 가는 칸은 코드로 확인한다.
3. **새 기능 표**: 「우리 프로그램 어디에도 없다」는 주장은 **코드 검색 증거**를 붙인다(대상 폴더 소스에서 키워드 검색 — 빌드 결과물 `.next`·`node_modules`는 빼고 원본 소스로 다시 확인). 열: 기능 · 우리 현황 · 접목 대상 · 웹 구현 방법 · 비용 · 우선(상/중/하).
4. **접목하지 않는 것** 표: 웹에서 불가능한 것(데스크톱·CLI 전용), 권리 없는 데이터, 원본 운영 방식(후원 등).
5. 새 기능과 「이미 있는 기능의 개선」을 섞지 않는다.

## 4. ④ 배치 추천

- 새 기능마다 **넣을 프로그램과 이유**를 표로 낸다. 기준: 그 프로그램의 담당 역할(병합 계획의 기준 앱), 이미 있는 화면·저장 구조를 그대로 확장할 수 있는가, 발행 등 완성 기준을 함께 채울 수 있는가.
- **이관·병합 예정인 프로그램에는 새 기능을 넣지 않는다**(나중에 다시 옮겨야 함) — 예외는 주인님이 정할 때만.
- 추천과 결정은 구분한다. 주인님이 배치를 정하면 보고서·인계에 「배치 승인」이라고 적는다.

| 순서·검수·배포 | 하나씩 구현·커밋 → 묶어서 배포 1회, 버전(`vX.YY`·DB·확장 manifest/ZIP), 크롬 실제 화면 확인 |

| 새 프로그램이면 | 이름 후보 4~5개 표 + 추천 1개 + 한 줄 요약 예시(핵심 원칙 23), 원본 부족한 점 → 보강 표 |

## 6. ⑥ 담당 세션 인계 (분석·플랜 담당 ↔ 구현 담당)

- 분석·플랜 담당은 **플랜까지만** 하고 구현·배포·유료 호출을 하지 않는다. 구현은 그 분야 담당 세션이 맡고 **비용 승인도 구현 담당이 받는다**.
- 인계 문서 `docs/IMPROVEMENT_HANDOFF_YYYYMMDD_<주제>.md` 필수 내용: 넘기는 쪽·**받는 쪽** · 지금까지 한 일(커밋 포함) · **승인 상태를 나눠 적기**(배치 승인 / 플랜·비용 승인 전) · 단계 요약과 바꿀 파일 · 꼭 알아야 할 것(권리·보안·실패 가능성) · **다음 첫 단계**(ACTIVE_WORK 등록 → 플랜 승인 → 첫 단계 구현) · 이후 후보 · 발견 사항 · 비용 리포트.
- 대상 프로그램 `AGENTS.md` 맨 위에 「담당 이어받기 대기」 한 줄과 링크, `docs/IMPROVEMENTS.md` 맨 아래에 제안 기록.
- 받는 쪽이 진행 중인 묶음(예: 병합 B-1~B-8)과 번호·범위가 겹치지 않게 묶음 이름을 정한다(예: D-1~D-4).
