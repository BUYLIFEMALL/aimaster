## 1. 지켜야 할 규칙

**같은 계정은 한 곳에서만 쓸 수 있습니다.** 다른 기기나 브라우저에서 같은 계정으로 새로 로그인하면, 예전 곳은 메인 사이트와 모든 하위 프로그램에서 로그아웃됩니다. **새로 로그인한 곳은 남아야 합니다.** 다른 계정끼리는 서로 영향이 없습니다. 운영 설정은 `site_settings.concurrent_login_policy = force_logout`이며, 이 설정은 바꾸지 않습니다.

## 2. 지금 문제

- Supabase `signOut()`을 범위 없이 부르면 기본값이 `scope: 'global'`입니다(auth-js 2.118). 그래서 **그 계정의 모든 기기·모든 프로그램이 함께 로그아웃됩니다.**
- 첫 번째 문제: 로그아웃 버튼을 한 곳에서만 눌러도 모든 곳이 끊깁니다. 운영 인증 기록에서 로그아웃 4번마다 몇 분 안에 다른 곳에서 `session_not_found`가 났습니다. 15:29에는 실시간으로도 재현했습니다.
- 두 번째 문제: **1인 1접속 규칙이 거꾸로 동작합니다.** 순서는 이렇습니다.
  1. B 기기에서 로그인하면 `/api/session/create`가 A의 `user_sessions` 줄을 지웁니다.
  2. 60초 안에 A의 `SessionProvider` heartbeat가 401을 받고, A는 `/login`으로 이동합니다.
  3. A의 `middleware.ts`(74~84행)가 `?session_expired=true`를 붙여 다시 보냅니다.
  4. A의 `LoginForm.tsx`(34~40행)가 범위 없는 `signOut()`을 부릅니다. 그러면 **방금 로그인한 B까지 끊깁니다.**
- 세 번째 문제: `block_new` 정책일 때 `LoginForm.tsx` 79행도 범위 없는 `signOut()`을 부릅니다. 이러면 **막혀야 할 새 기기가 아니라, 이미 쓰던 기존 기기가 끊깁니다.** 지금 정책에서는 쓰이지 않지만 같이 고칩니다.
- 네 번째 문제: 하위 프로그램은 `user_sessions`를 보지 않습니다. 그래서 지금은 예전 기기의 하위 프로그램이 규칙과 상관없이 남거나 끊깁니다.

## 3. 고칠 것 (메인 사이트, 한 번 배포)

| 파일 | 지금 | 바꿀 것 |
|---|---|---|
| `app/(auth)/login/LoginForm.tsx` `handleLogin` | `/api/session/create` 뒤 다음 화면으로 이동 | 응답이 409가 **아니면** 이동 전에 `await supabase.auth.signOut({ scope: "others" })`를 부릅니다. 이렇게 하면 같은 계정의 예전 기기 로그인이 모든 프로그램에서 무효가 되고, 지금 기기는 남습니다(1인 1접속을 하위 프로그램까지 적용). `create` 요청이 네트워크 오류로 실패해도 부릅니다. |
| 같은 파일 34~40행 (`session_expired`) | `signOut()` | `signOut({ scope: "local" })` (끊긴 기기만 정리) |

| `app/api/session/logout/route.ts` 17행 | `signOut()` | `signOut({ scope: "local" })` |
| `components/layout/Header.tsx` 66행, `Sidebar.tsx` 72행, `AdminSidebar.tsx` 31행, `app/(dashboard)/settings/page.tsx` 117행, `components/dashboard/RelogAdminButton.tsx` 15행 | `signOut()` | `signOut({ scope: "local" })` |

- DB와 환경변수는 바꾸지 않습니다. `user_sessions`, `session_token`, heartbeat 흐름도 그대로 둡니다.
- 같은 브라우저 안의 탭들은 로그인 쿠키(`.buylife.xyz`) 하나를 함께 씁니다. 그래서 `local` 로그아웃을 해도 그 브라우저의 모든 탭은 함께 로그아웃됩니다. 이것은 정상입니다. 범위가 의미 있는 것은 **다른 기기·다른 브라우저 사이**입니다.

## 4. 하위 프로그램 (따로 배포하지 않음)

각 프로그램의 로그아웃 버튼(`signOut()` 약 130곳)은 **그 프로그램을 다음에 배포할 때** `signOut({ scope: "local" })`로 바꿉니다. 각 담당의 미배포 대기에 한 줄씩 넣으면 됩니다. 다 바뀌기 전에는 하위 프로그램의 로그아웃 버튼이 여전히 모든 곳을 끊습니다. 규칙을 어기는 것은 아니고, 더 많이 끊길 뿐입니다.

## 5. 한계 (알고 진행)

`scope: "others"`는 예전 기기의 로그인 갱신 토큰을 바로 무효로 만듭니다. 하지만 이미 발급된 접근 토큰은 만료(기본 1시간)까지 남습니다. 서버에 묻는 `getUser()` 프로그램(무료음악 등)은 바로 끊깁니다. 서명만 확인하는 `getClaims()` 프로그램(쇼츠 등)은 **최대 1시간까지 열려 있을 수 있습니다.** 메인 사이트는 heartbeat로 60초 안에 끊깁니다.

## 6. 확인 방법 (시험 계정, 브라우저 두 개: ego lite와 크롬)

1. A(ego)에서 시험 계정으로 로그인하고 메인 사이트와 무료음악을 엽니다.
2. B(크롬)에서 같은 계정으로 로그인합니다. → A의 메인 사이트는 60초 안에 「세션 만료」, 무료음악은 새로 고치면 로그인 화면이 나와야 합니다.
3. **B가 2분 뒤에도 로그인 상태인지** 확인합니다. 지금 코드는 여기서 실패합니다.
4. B에서 로그아웃합니다. → B만 로그아웃되어야 합니다. A에 다시 로그인한 상태라면 A는 그대로 남아야 합니다.
5. 운영 인증 기록(`auth_logs`)에서 2번 직후 A의 `session_not_found`만 있고 B에는 없는지 대조합니다.
