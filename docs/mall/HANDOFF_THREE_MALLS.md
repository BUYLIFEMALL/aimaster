## 1. 세 몰의 성격

| | ① B2B 입점몰 | ② 분양몰(본사 상품형) | ③ 독립몰 |
|---|---|---|---|
| 한 줄 | 공급사가 모이고 소매상·소비자가 사는 **중심 몰** | 누구나 **자기 이름의 몰**을 분양받아 ① 상품을 판다 | 한 사업자가 **자기 도메인·자기 관리자**로 따로 운영 |
| 운영자 | 본사(바이라이프) | 분양자(개인·사업자) — 본사가 승인 | 그 몰 사업자(바이라이프 자체몰 / 고객) |
| 손님 | 소매상(도매가·외상·견적) + 소비자(소매가) | 분양자의 지인·팔로워·고객(주로 소비자) | 그 사업자의 고객(소매·도매 설정으로) |
| 상품 출처 | 공급사 입점 + 본사 자체 상품 | ① 상품을 골라 받음(재고·가격 연동) | 직접 등록 + 기존 몰 이전(선택: ① 상품 연동) |
| 발송 | 공급사 품목은 공급사, 본사 품목은 본사 | ①(공급사·본사)이 대신 발송 | 그 사업자 |
| 돈의 흐름 | 손님 → 본사 → 공급사(공급가 정산) | 손님 → 본사 → 분양자(마진 정산) + 공급사(공급가) | 손님 → 그 사업자 |
| 구조 | 몰 하나 + 공급사 여럿 | 분양자마다 몰 하나 | 몰 하나만 도는 사이트(단일 몰 모드) |
| 지금 | ✅ 거의 완성(Lab 배포·실제 확인) | ⚪ 새로 개발 | ⚪ 단일 몰 모드부터 |

### T0 운영 이전 — 이어받는 CLI가 할 순서
1. `docs/ACTIVE_WORK.md`·요청함(`node scripts/dev-requests.mjs list --role mall-builder`) 확인.
2. 운영 DB 영향 재확인: 마이그레이션이 공용 부분에서 하는 일은 새 저장소 2개·확장 `http`·새 스키마 `mall_builder_private`뿐(기존 표·auth 표 변경 없음, 2026-11-11 확인). 운영 DB 적용 전 주인님 승인 + 적용 목록 보고.
3. AIMaster 스위치: 운영 모드에서는 `requireProgramAccess()`(slug `mall-builder`)·로그인 공유(`.buylife.xyz` 쿠키)·핸드폰 필수 규칙, 몰 만들기·공급사 초대는 관리자만. 키트 모드(STANDALONE)에서는 끔.

## 5. 작업할 때 꼭 지킬 것(이번에 겪은 교훈 요약 — 상세 [LESSONS_LEARNED.md](LESSONS_LEARNED.md))

- 손님이 읽을 수 있는 표(상품·주문 품목)에 원가·공급가·정산액 칸을 넣지 않는다 → 별도 표.
- 다른 사람 역할(공급사·손님)은 **그 역할만 가진 계정**으로 시험한다(운영자 계정으로 흉내 내면 운영자 규칙으로 통과해 버림 — 실제 확인에서 2건 발견).
- 보안 규칙 하위 조회에서는 바깥 표 칸을 표 이름으로 붙여 쓴다(`objects.name`).
- Supabase MCP 마이그레이션에 `drop`이 있으면 확인 창이 뜬다 → 새 것만 만드는 마이그레이션엔 넣지 않고, 권한(`revoke/grant`)은 따로 적용. 시험 데이터 지우기는 `with d as (delete … returning) select count(*) from d` 한 문장.
- 시험 주문은 문자·메일 알림을 대기열에 넣는다 → 커밋되는 시험이면 바로 지운다.
- 로컬 서버에서 단추가 안 먹으면 `.next/dev` 캐시를 지우고 `node ./node_modules/next/dist/bin/next dev -p 3210`.
- 비용(빌드·운영 DB 적용·새 프로젝트)은 실행 전 주인님 승인, 끝나면 비용 리포트.
