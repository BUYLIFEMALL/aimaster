# 프로그램 상세 설명 작성 표준 (모든 CLI 공통)

> 2026-10-15 주인님 지시: "프로그램 설명글 작성 규칙을 문서화해서, 앞으로 프로그램 등록할 때 이대로 할 수 있도록 해놔."
> **새 프로그램을 등록할 때, 기존 프로그램 설명을 고칠 때 이 문서를 그대로 따른다.** 2026-10-15 80개 전체를 이 표준으로 다시 썼다(작업 기록: [`PROGRAM_DESCRIPTIONS_2026-10-15.md`](PROGRAM_DESCRIPTIONS_2026-10-15.md)).

## 1. 어디에 쓰는가
| 칸 | 위치 | 용도 |
|---|---|---|
| `programs.description` | 관리자 프로그램 편집 화면 `/admin/programs/<id>/edit`의 **"상세 설명"** 에디터 | 공개 상세 페이지 `https://www.buylife.xyz/programs/<slug>`의 "프로그램 상세 소개" |
| `programs.short_desc` | 같은 편집 화면의 한 줄 요약 | 카탈로그 카드·검색 결과 설명. **한 줄, 60자 안팎**, 프로그램이 무엇을 하는지만 |

## 2. 상세 설명 형식
- **분량**: 화면에 보이는 글자 기준 **400~500자 내외**. 기능이 적은 프로그램은 300자대도 괜찮다 — **없는 기능으로 채우지 않는다.**
- **구성(4~6단락)**:
  1. **첫 단락 = 굵은 한 줄 소개**: 이모티콘 + `<strong>`으로 "무엇을 해 주는 프로그램인지" 한 문장.
  2. **기능 단락 2~4개**: 사용 흐름 순서(입력 → 처리 → 결과/저장)로 핵심 기능만. 단락마다 한 가지 주제.
  3. **마지막 단락 = 필요한 것·주의**: 회원 본인 API 키·외부 계정(무엇이 필수/선택인지), 브라우저 안에서만 처리되는지, 서버 저장 여부, 용량·지원 형식 제한, 결과 보증 불가 등.
- **이모티콘**: 단락 맨 앞에 1개씩. 내용을 보여 주는 것으로(🎨 이미지, 📝 글, 🔑 키, 🔒 보안·저장, 💾 저장, ⚠️ 제한 등). 문장 중간에는 쓰지 않는다.
- **문단 사이 간격**: 단락마다 `<p>…</p>`만 쓴다. **빈 줄 단락(`<p><br></p>`)·빈 `<p></p>`를 넣지 않는다.** 간격은 화면 CSS가 준다(관리자 에디터 `.prose-editor p`, 공개 페이지 `[&_p]:my-2`). 빈 줄을 넣으면 에디터에서 간격이 두 배로 벌어진다(2026-10-15 주인님 지적).
- **쓰지 않는 서식**: 제목 태그(`<h2>`·`<h3>`), 목록(`<ul>`/`<ol>`), 표, 마크다운 기호(`##`, `- `), 링크·이미지. 굵게(`<strong>`)는 첫 단락에만.

## 3. 문장 규칙
- 쉬운 한글, 존댓말(-합니다/-해 줍니다). 회원이 읽고 "무엇을 할 수 있는지" 바로 알게 쓴다.
- 기술 용어는 필요한 만큼만(예: PPTX, Gemini API 키, 16:9). 내부 구현명(Supabase, Next.js, RLS, 함수명), 모델 버전 나열, 프로그램 버전 번호는 쓰지 않는다.
- 과장 금지: "100%", "완벽", "God-Tier", "0.1% 상위노출", "압도적" 같은 표현을 쓰지 않는다. 실제 동작을 그대로 쓴다.
- 최상위 규칙 반영: AI·외부 계정이 필요하면 **"회원 본인의 ○○ API 키(계정)를 사용합니다"**를 마지막 단락에 쓴다. 운영자 키를 쓰는 것처럼 보이는 문장 금지. 키가 필요 없으면 "API 키가 필요 없습니다".
- 정책상 주의가 있으면 쓴다: 최종 발행은 회원이 직접, 본인·동의받은 사진만, 실제 발송은 수신 동의 대상에게만, 진단·보증이 아님 등.

## 4. 내용을 정하는 순서(사실 확인)
1. 프로그램 폴더의 `README.md`·`AGENTS.md`·`docs/CLI_HANDOFF.md`·`docs/DEVELOPMENT_PLAN.md`에서 **현재 구현된 기능**을 확인한다(계획만 있고 구현 안 된 Phase는 쓰지 않음). 슬러그와 폴더가 다른 프로그램은 [`PROGRAM_DESCRIPTIONS_2026-10-15.md`](PROGRAM_DESCRIPTIONS_2026-10-15.md)의 대응표 참고.
2. 가능하면 실제 화면(맥미니는 맥미니 크롬, 윈도우는 계정별 브라우저)에서 메뉴·옵션 이름을 대조한다.
3. 필요한 키·계정, 저장 위치(브라우저/서버), 제한 사항을 확인한다.

## 5. 저장 방법
- 관리자 편집 화면의 "상세 설명" 에디터에 직접 쓸 때: 단락마다 엔터로 나누고, 첫 줄만 굵게. 빈 줄을 따로 만들지 않는다.
- SQL로 넣을 때(Supabase MCP `execute_sql`, 프로젝트 `esgxyikcnnvmlhygjkth`): 따옴표 문제를 피하려고 달러 인용을 쓴다.
  ```sql
  update programs set description = $d$<p>📑 <strong>한 줄 소개입니다.</strong></p><p>📂 기능 단락입니다.</p><p>🔑 회원 본인의 Gemini API 키로 동작합니다.</p>$d$ where slug = '<slug>';
  ```
- 여러 개를 고치기 전에는 기존 값을 먼저 파일로 백업한다: `select slug, description from programs where slug in (...)`.
- **편집 화면을 열어 둔 채 DB를 바꿨다면, 그 화면은 새로고침한 뒤에 저장한다**(옛 화면에서 저장하면 옛 내용으로 덮어쓴다).
- DB 값만 바꾼 작업은 프로그램 버전을 올리지 않는다(버전 규칙은 코드·배포를 바꿀 때).

## 6. 등록 후 확인 체크리스트
- [ ] `short_desc` 한 줄(60자 안팎)과 `description`(400~500자, 4~6단락)이 모두 들어갔다.
- [ ] 첫 단락만 굵은 한 줄 소개, 단락마다 이모티콘 1개, 빈 줄 단락 없음: `select count(*) from programs where description like '%<p><br></p>%'` = 0.
- [ ] 마지막 단락에 필요한 키·계정·주의가 있다.
- [ ] 관리자 편집 화면과 `https://www.buylife.xyz/programs/<slug>`에서 단락 간격이 0.5줄 정도로 보인다.
- [ ] 과장 표현·버전 번호·내부 기술명이 없다.

## 7. 예시 (AI 슬라이드 자동화, `ai-slide-builder`)
```html
<p>📑 <strong>회의록·기획서 같은 문서에서 전문 프레젠테이션을 자동으로 구성해 PPTX로 내려받는 슬라이드 도구입니다.</strong></p>
<p>📂 PDF·DOCX·XLSX·TXT 같은 실무 문서를 올리면 내용을 읽어 슬라이드별 핵심 지표와 전략을 자동으로 구성합니다.</p>
<p>🧱 22개 전문 슬라이드 스키마와 3가지 기획 프레임워크(표준·확장판·C-Suite 보고 형식)로 IR 피치덱, 사업계획서, 경영진 보고서를 만들고, 슬라이드를 카드로 하나씩 고칠 수 있습니다.</p>
<p>🖥️ 16:9 슬라이드쇼로 미리 보고, 브라우저에서 바로 16:9 와이드 PPTX 파일로 내려받습니다.</p>
<p>🔑 모든 기능은 회원 본인의 Google Gemini API 키로 동작합니다.</p>
```
(실제 저장은 줄바꿈 없이 이어 붙여도 된다. 위는 보기 쉽게 줄을 나눈 것.)

## 8. 화면 쪽 전제(바꾸지 말 것)
- 공개 상세 페이지 `app/(main)/programs/[slug]/page.tsx`의 설명 영역 `className`에 `[&_p]:my-2`가 있어야 단락 간격이 생긴다(이 저장소에는 Tailwind typography 플러그인이 없어 `prose`가 여백을 주지 않음). 이 클래스를 지우면 단락이 붙어 보인다.
- 관리자 에디터 간격은 `app/globals.css`의 `.prose-editor p { margin: 0.5em 0 }`.
