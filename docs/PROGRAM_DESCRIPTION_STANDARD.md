> 2026-10-15 주인님 지시: "프로그램 설명글 작성 규칙을 문서화해서, 앞으로 프로그램 등록할 때 이대로 할 수 있도록 해놔."
> **핵심 지침: `CLAUDE.md` 핵심 원칙 22 / `AGENTS.md` 핵심 원칙 21 (2026-10-16 주인님 지시 — "이 형식으로 다른 프로그램도 잘 설명할 수 있게 핵심 지침문서로").** 기준 예시는 §7-1 `blog-workroom`.
> **새 프로그램을 등록할 때, 기존 프로그램 설명을 고칠 때 이 문서를 그대로 따른다.** 2026-10-15 80개 전체를 이 표준으로 다시 썼다(작업 기록: [`PROGRAM_DESCRIPTIONS_2026-10-15.md`](PROGRAM_DESCRIPTIONS_2026-10-15.md)).

## 1. 어디에 쓰는가
| 칸 | 위치 | 용도 |
|---|---|---|
| `programs.description` | 관리자 프로그램 편집 화면 `/admin/programs/<id>/edit`의 **"상세 설명"** 에디터 | 공개 상세 페이지 `https://www.buylife.xyz/programs/<slug>`의 "프로그램 상세 소개" |
| `programs.detail_sections` (jsonb, 2026-10-16) | 같은 편집 화면의 **"핵심 특징 · 사용 순서"** 입력칸 | 상세 페이지의 특징 카드 4개와 "실제 사용 순서" 4단계. 값이 없으면 두 묶음을 숨긴다(공통 고정 문구는 2026-10-16 제거) |
| `programs.short_desc` | 같은 편집 화면의 한 줄 요약 | 카탈로그 카드·검색 결과 설명. **한 줄, 60자 안팎**, 프로그램이 무엇을 하는지만 |

## 2. 상세 설명 형식
- **분량**: 화면에 보이는 글자 기준 **400~500자 내외**. 기능이 적은 프로그램은 300자대도 괜찮다 — **없는 기능으로 채우지 않는다.**
- **구성(4~6단락)**:
  1. **첫 단락 = 굵은 한 줄 소개**: 이모티콘 + `<strong>`으로 "무엇을 해 주는 프로그램인지" 한 문장.
  2. **기능 단락 2~4개**: 사용 흐름 순서(입력 → 처리 → 결과/저장)로 핵심 기능만. 단락마다 한 가지 주제.
  3. **마지막 단락 = 필요한 것·주의**: 회원 본인 API 키·외부 계정(무엇이 필수/선택인지), 브라우저 안에서만 처리되는지, 서버 저장 여부, 용량·지원 형식 제한, 결과 보증 불가 등.
- **이모티콘**: 단락 맨 앞에 1개씩. 내용을 보여 주는 것으로(🎨 이미지, 📝 글, 🔑 키, 🔒 보안·저장, 💾 저장, ⚠️ 제한 등). 문장 중간에는 쓰지 않는다.
- **문단 사이 간격**: 단락마다 `<p>…</p>`만 쓴다. **빈 줄 단락(`<p><br></p>`)·빈 `<p></p>`를 넣지 않는다.** 간격은 화면 CSS가 준다(관리자 에디터 `.prose-editor p`, 공개 페이지 `[&_p]:my-2`). 빈 줄을 넣으면 에디터에서 간격이 두 배로 벌어진다(2026-10-15 주인님 지적).
- **쓰지 않는 서식**: 제목 태그(`<h2>`·`<h3>`), 목록(`<ul>`/`<ol>`), 표, 마크다운 기호(`##`, `- `), 링크·이미지. 굵게(`<strong>`)는 첫 단락에만.

## 2-1. 비슷한 프로그램은 차별점을 앞세운다 (2026-10-16 주인님 지시)
- 같은 분야 프로그램이 여럿이면(블로그 글쓰기·쓰레드·이미지·유튜브·음악·상세페이지·성격 검사·프롬프트 등), **첫 단락의 굵은 한 줄 소개에 "이 프로그램만 하는 일"**을 넣는다. 다른 프로그램 이름을 직접 비교하지 않고, 이 프로그램의 고유한 입력·방식·결과로 구분되게 쓴다.
- 쓰기 전에 같은 카테고리의 다른 프로그램 설명을 먼저 읽고 겹치는 표현을 피한다. 예(2026-10-16 전체 재작성 기준):
  - 블로그: `blog-workroom` 내 문체 분석→근거 승인→검수 / `naver-blog-agent` 5단계 에이전트+최종원고 확인 / `naver-blog-seo-studio` 검색 전략·페르소나+기존 글 SEO 재작성 / `naver-blog-allinone` 사진을 AI가 보고 쓰는 맛집·여행 글 / `ai-auto-blog` 실시간 이슈 원문 / `blog-content-maker` 기존 원고 다듬기·발행 전 점검 / `tistory-auto-blog` 티스토리 서식 입력.
  - 쓰레드: `auto-threads-posting` 기본형 수집·초안·예약 / `threads-content-ops` 여러 계정 운영 / `threads-affiliate-poster` 쇼핑 제휴 링크 / `threads-easy-planner` 초보자용 기획 / `threads-comment-reply` 댓글 답글.
  - 상세페이지: `detail-page-12p` 상품명만으로 12단·9단 통이미지 / `shop-detail-page` 상품 사진 분석 15섹션 / `auto-detail-page` HTML 상세페이지.
  - 썸네일·유튜브: `thumbnail-master` 타겟별 A/B 썸네일 2종 / `seo-thumbnail-pro` 제목·설명·태그·고정 댓글 전략+썸네일 / `youtube-viral-studio` 떡상 영상 발굴 / `youtube-channel-consultant` 채널 진단 / `shorts-viral-studio` 떡상 공식 분석→대본.

## 2-2. 핵심 특징 4개 + 사용 순서 4단계 (`detail_sections`, 2026-10-16 주인님 확정)
- **상세 페이지는 3단 구성이다**: ① 상세 설명(`description`) → ② 핵심 특징 카드 4개 → ③ 실제 사용 순서 4단계. ②③은 `programs.detail_sections`에 프로그램별로 저장한다. 형식: `{"features":[{"icon":"🔗","title":"…","desc":"…"}×4],"steps":[{"title":"…","desc":"…"}×4]}`.
- **특징 4개**: 이모지 1개 + 제목(14자 안팎) + 설명(60자 안팎). 이 프로그램만의 실제 기능·강점으로 쓴다(상세 설명 기능 단락과 같은 내용을 짧게 다시 말하지 말고, 카드 하나에 한 가지). 쓰지 않는 기능(AI 없는 프로그램의 "AI 엔진", 자동 발행이 없는 프로그램의 "자동 발행")은 절대 넣지 않는다. 키가 필요 없거나 브라우저에서만 처리하는 것은 장점이므로 카드로 써도 된다.
- **사용 순서 4단계**: 단계 제목(12자 안팎) + 설명(45자 안팎). **프로그램 화면의 실제 메뉴·작업 흐름 순서**를 따른다(첫 단계는 보통 키·계정 연결 또는 입력, 마지막은 저장·발행·내보내기). 발행을 회원이 직접 하는 프로그램은 「직접 발행」으로 쓴다.
- 과장 수치(「90% 절감」 등)·다른 분야 용어(유튜브가 아닌데 「VPH」 등) 금지. 값이 아직 없으면 비워 둔다(화면에서 숨겨짐) — 공통 문구로 채우지 않는다.
- 기준 예시(`blog-workroom`):
  - 특징: 🧬 내 문체 분석 — 최근 글 5~30개로 어조·문장·구성·독자를 분석해 승인한 스타일로 씁니다. / 🔑 골드키워드 검증 — AI 후보를 월간 검색량·블로그 문서수로 검증해 등급을 매깁니다. / 📚 근거 확인된 자료만 — 상위 글 5개에서 근거 구절이 확인된 정보만 남기고 직접 승인합니다. / ✅ 6영역 최종 검수 — 문체·사실·경험·유사·과장 표현을 점검하고 필수 수정이 남으면 저장을 막습니다.
  - 순서: 01 내 블로그 스타일 → 02 키워드·트렌드 찾기 → 03 자료 승인·초안 → 04 검수·이미지.
- 2026-10-16 82개 전체 입력 완료(데이터 원본은 DB, 작업 기록 [`HANDOFF_PROGRAM_DETAIL_PAGE_2026-10-16.md`](HANDOFF_PROGRAM_DETAIL_PAGE_2026-10-16.md)).
- **④ 추천 활용 대상 3개 (`detail_sections.audiences`, 2026-10-16 주인님 지시 "프로그램마다 다른 기능과 차별점을 강조한 형태로")**: 상세 페이지 사용 순서 아래 「추천 활용 대상」 카드 3개도 프로그램별 값이다(예전 공통 문구 「1인 창업가·이커머스 셀러·마케팅 대행사」 제거, 값이 없으면 섹션 숨김). 형식: `"audiences":[{"icon":"💬","title":"댓글이 많은 인스타 운영자","desc":"…","points":["…","…"]}×3]`.
  - **대상(18자 안팎)**: 이 프로그램을 실제로 쓸 사람을 구체적으로(「마케터」처럼 넓게 쓰지 않고 「댓글로 상품 링크를 주는 셀러」처럼 상황까지).
  - **설명(70자 안팎)**: 그 사람에게 **왜 이 프로그램이 맞는지를 이 프로그램의 실제 기능·차별점으로** 쓴다(특징 카드 기능 이름을 문장 속에 넣는다). 비슷한 프로그램끼리(인스타/쓰레드/유튜브 댓글, 블로그 원문 생성 여러 개 등) 같은 문장을 쓰지 않는다.
  - **효과 2줄(14자 안팎)**: 그 대상이 얻는 구체적 결과. 과장 수치 금지.
  - 기준 예시(`blog-workroom`): ✍️ 내 문체를 지키고 싶은 블로거 — 내 블로그 글을 분석해 문체를 익히고 그 말투로 초안을 씁니다. (AI 티 덜 나는 글 · 블로그 정체성 유지) / 🔑 키워드를 근거로 고르는 분 / 🧐 정확한 정보가 중요한 분.
  - 2026-10-16 82개 전체 입력(원본 사본 [`program-descriptions/audiences-2026-10-16.json`](program-descriptions/audiences-2026-10-16.json), 입력 전 백업 `program-descriptions/backup-detail-sections-before-audiences-2026-10-16.json`). 관리자 편집 화면 「핵심 특징 · 사용 순서」 입력칸 아래에 「추천 활용 대상 3개」 입력칸이 있다.

## 3. 문장 규칙
- 쉬운 한글, 존댓말(-합니다/-해 줍니다). 회원이 읽고 "무엇을 할 수 있는지" 바로 알게 쓴다.
- 기술 용어는 필요한 만큼만(예: PPTX, Gemini API 키, 16:9). 내부 구현명(Supabase, Next.js, RLS, 함수명), 모델 버전 나열, 프로그램 버전 번호는 쓰지 않는다.
- 과장 금지: "100%", "완벽", "God-Tier", "0.1% 상위노출", "압도적" 같은 표현을 쓰지 않는다. 실제 동작을 그대로 쓴다.
- 최상위 규칙 반영: AI·외부 계정이 필요하면 **"회원 본인의 ○○ API 키(계정)를 사용합니다"**를 마지막 단락에 쓴다. 운영자 키를 쓰는 것처럼 보이는 문장 금지. 키가 필요 없으면 "API 키가 필요 없습니다".
- 정책상 주의가 있으면 쓴다: 최종 발행은 회원이 직접, 본인·동의받은 사진만, 실제 발송은 수신 동의 대상에게만, 진단·보증이 아님 등.

## 4. 내용을 정하는 순서(사실 확인)
1. 프로그램 폴더의 `README.md`·`AGENTS.md`·`docs/CLI_HANDOFF.md`·`docs/DEVELOPMENT_PLAN.md`에서 **현재 구현된 기능**을 확인한다(계획만 있고 구현 안 된 Phase는 쓰지 않음). 슬러그와 폴더가 다른 프로그램은 [`PROGRAM_DESCRIPTIONS_2026-10-15.md`](PROGRAM_DESCRIPTIONS_2026-10-15.md)의 대응표 참고.
2. 가능하면 실제 화면(맥미니는 맥미니 크롬, 윈도우는 계정별 브라우저)에서 메뉴·옵션 이름을 대조한다.
3. 필요한 키·계정, 저장 위치(브라우저/서버), 제한 사항을 확인한다.

## 5. 저장 방법
- 관리자 편집 화면의 "상세 설명" 에디터에 직접 쓸 때: 단락마다 엔터로 나누고, 첫 줄만 굵게. 빈 줄을 따로 만들지 않는다.
- SQL로 넣을 때(Supabase MCP `execute_sql`, 프로젝트 `esgxyikcnnvmlhygjkth`): 따옴표 문제를 피하려고 달러 인용을 쓴다.
  ```sql
  update programs set description = $d$<p>📑 <strong>한 줄 소개입니다.</strong></p><p>📂 기능 단락입니다.</p><p>🔑 회원 본인의 Gemini API 키로 동작합니다.</p>$d$ where slug = '<slug>';
  ```
- 여러 개를 고치기 전에는 기존 값을 먼저 파일로 백업한다: `select slug, description from programs where slug in (...)`.
- **편집 화면을 열어 둔 채 DB를 바꿨다면, 그 화면은 새로고침한 뒤에 저장한다**(옛 화면에서 저장하면 옛 내용으로 덮어쓴다).
- `detail_sections`는 관리자 편집 화면의 **"핵심 특징 · 사용 순서"** 입력칸(특징 4줄·단계 4줄, 빈 줄은 저장 안 함)에서 넣거나, SQL로 `update programs set detail_sections = '{"features":[...],"steps":[...]}'::jsonb where slug='<slug>';`.
- DB 값만 바꾼 작업은 프로그램 버전을 올리지 않는다(버전 규칙은 코드·배포를 바꿀 때).

## 6. 등록 후 확인 체크리스트
- [ ] `short_desc` 한 줄(60자 안팎)과 `description`(400~500자, 4~6단락)이 모두 들어갔다.
- [ ] 첫 단락만 굵은 한 줄 소개, 단락마다 이모티콘 1개, 빈 줄 단락 없음: `select count(*) from programs where description like '%<p><br></p>%'` = 0.
- [ ] 마지막 단락에 필요한 키·계정·주의가 있다.
- [ ] 관리자 편집 화면과 `https://www.buylife.xyz/programs/<slug>`에서 단락 간격이 0.5줄 정도로 보인다.
- [ ] 과장 표현·버전 번호·내부 기술명이 없다.
- [ ] `detail_sections`에 특징 4개·사용 순서 4단계가 있고, 그 프로그램에 없는 기능(AI·자동 발행 등)이 들어가지 않았다: `select slug from programs where detail_sections is null` = 0건.

## 7-0. 바로 쓰는 작성 틀
빈칸만 채우면 표준 형식이 된다. 단락 수는 기능 수에 맞춰 3~4개로 조절하고, 없는 기능으로 채우지 않는다.
```html
<p>{이모티콘} <strong>{누구의 무엇을} {어떤 흐름/방식으로} {무엇을 해 주는} {프로그램 성격}입니다.</strong></p>
<p>{이모티콘} {1단계: 무엇을 넣으면} {무엇을 분석·처리해} {무엇을 보여 주거나 저장}합니다.</p>
<p>{이모티콘} {2단계 기능 — 한 단락에 한 주제}.</p>
<p>{이모티콘} {3단계 기능 — 결과를 어떻게 확인·수정·내보내는지}.</p>
```
