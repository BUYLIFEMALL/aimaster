## 2. 지금 구조에서 P1이 닿는 곳

읽기만 한 현재 코드(엔진 0.8.5) 기준이다. **역할(2026-11-19 주인님 지시로 변경, Master 확정 msg_5f1eca22975d)**: 엔진 그림 구현과 새 웹은 이 세션(ECOM), 음악 담당은 음악 기능 회귀 확인, 일반 검수는 MacMini. 음악 담당의 진행분은 인계받아 이어 간다. 음악 담당 읽기 검토(msg_0962d9630d0e)를 반영했다.

### 2-1. 지금 엔진의 권한 구조 (확인한 사실)

- **토큰**: 6자리 코드로 짝지으면 토큰 1개를 발급해 `paired.json`의 목록 하나에 넣는다. 토큰에 발급 출처·소유 범위 기록이 없다. 허용된 어느 출처에서든 유효한 토큰이면 통과한다.
- **작업**: 대기열 작업에 접수 출처·소유 기록이 없다. `GET /queue`는 그림 전용 출처에도 **모든 작업 목록**(음악 작업의 제목·상태 포함, 요청 원문은 제외)을 준다.
- **결과·취소·지우기**: `GET /image-art/<작업 번호>`, `POST /queue/<번호>/cancel`, `DELETE /queue/<번호>`는 작업 번호만 알면 어느 토큰으로든 된다. 그림 전용 출처도 주소 형식만 맞으면 음악 작업을 취소할 수 있다.
- **접수**: 그림 전용 출처는 `kind: "art"`만 넣을 수 있다(이 제한은 이미 있다). 같은 요청을 두 번 보내면 작업이 두 개 생긴다(중복 방지 없음).

따라서 **새 출처를 허용 목록에 넣는 것만 먼저 하면** 새 사이트가 음악·이미지 스튜디오 작업을 보고 취소할 수 있게 된다. 출처 등록은 아래 권한·호환 조건과 **같은 변경으로** 묶고, 단독으로 먼저 하지 않는다.

### 2-2. 권한·소유 범위 설계안

| 항목 | 설계 |
|---|---|
| 토큰의 출처 묶음 | 새로 발급하는 토큰에 발급 출처와 범위 번호(무작위)를 기록한다. 토큰은 발급 출처에서만 유효하다 |
| 작업 소유 기록 | 접수 때 작업에 `site`(출처)와 `scope`(토큰의 범위 번호)를 적는다 |
| 새 그림 사이트의 조회 | `GET /queue`는 `site`·`scope`가 자기 것과 같은 작업만 준다 |
| 새 그림 사이트의 결과·취소·지우기 | 대상 작업의 `site`·`scope`가 자기 것일 때만. 아니면 「없는 작업」(404)으로 답해 존재 여부도 알리지 않는다 |
| 기존 두 출처(무료음악·이미지 스튜디오) | **지금 동작 그대로**. 옛 토큰(기록 없는 토큰)은 기존 두 출처에서만 유효한 「기존 범위」로 읽고, 기존 범위는 지금처럼 `site` 기록이 없는 작업 전체와 자기 작업을 본다. 새 사이트의 작업은 기존 범위 목록에 넣지 않는다(음악 화면에 낯선 작업이 섞이지 않게) |
| 엔진 창(내 PC 화면) | 모든 작업을 보고 취소할 수 있다(PC 주인의 최종 통제) |

회원 구분: 엔진은 회원 PC에서 돌고 AIMaster 회원 정보를 확인할 수 없다. 새 웹이 토큰을 **로그인 회원 번호별로** 브라우저에 보관하고, 회원이 바뀌면 그 회원의 토큰이 없으므로 다시 짝짓게 한다. 범위가 달라 앞 회원의 작업·결과는 보이지 않는다.

### 2-3. 이전 작업과 재연결 정책

| 상황 | 처리 |
|---|---|
| 브라우저 새로고침·탭 닫았다 열기 | 같은 토큰 → 같은 범위. 목록·결과가 이어진다 |
| 토큰 교체(다시 짝짓기)인데 옛 토큰이 아직 유효 | 짝짓기 요청에 옛 토큰을 함께 보내면 **같은 범위 번호를 이어받는다**. 옛 토큰은 그때 폐기 |
| 옛 토큰 없이 새로 짝짓기(브라우저 자료 삭제·다른 브라우저·다른 회원) | 새 범위. 앞 범위의 작업은 웹에서 보이지 않고, 진행 중이면 계속 돌며 엔진 창에서만 보고 취소한다. 기록은 기존 보관 기간(작업 기록 30일, 그림 파일은 지금 기준 하루) 뒤 정리 |
| 엔진을 새 버전으로 올린 직후 | 옛 토큰·`site` 없는 옛 작업은 「기존 범위」로 읽어 기존 두 사이트에서 지금처럼 보인다. 자료 형식 변환 없음 |
| 새 버전에서 옛 버전으로 되돌림 | 옛 엔진은 모르는 항목(`site`·`scope`·토큰 기록)을 읽지 않고 무시한다. 토큰 파일은 옛 형식(문자열 목록)을 유지하고 새 기록은 **옆 파일**에 둬서 옛 엔진이 그대로 읽게 한다 |

### 2-4. 접수 ID(중복 방지)

- 새 웹이 항목마다 접수 ID(무작위 UUID)를 만들어 `clientRequestId`로 보낸다. 묶음 24장은 접수 ID 24개와 묶음 표시용 `batchId` 1개.
- 엔진은 **같은 `site`·`scope` 안에서** 같은 접수 ID의 작업이 기록에 남아 있으면 새로 넣지 않고 그 작업을 그대로 돌려준다. 범위가 다르면 같은 ID라도 서로 다른 작업이다.
- 유효 기간은 작업 기록 보관 기간과 같다(기록이 정리되면 같은 ID를 다시 받아도 새 작업).
- 접수 ID가 없는 요청(기존 두 사이트)은 지금과 같이 매번 새 작업이다.
- 결과가 불확실할 때(응답을 못 받음) 웹은 같은 접수 ID로 다시 물어 상태를 확인하고, 새 ID로 다시 그리지 않는다.

### 2-6. 호환 경계 — 음악 담당 검토용 의사결정과 검증 조건

2-2~2-4의 경계를 좁힌 것이다. 아래와 2-2~2-4가 다르면 **이 절이 우선**한다. 구현 방법은 음악 담당이 정하고, 여기에는 지켜야 할 결과만 적는다.

**결정 1 — 새 범위의 자료는 기존 공유 목록과 저장을 나눈다 (주인님 확정 2026-11-19: 「그렇게 해」)**

| 자료 | 기존(무료음악·이미지 스튜디오) | 새 범위(새 그림 사이트) |
|---|---|---|
| 토큰 | `paired.json` — 형식·내용 그대로 | 별도 파일에만 둔다. `paired.json`에는 넣지 않는다 |
| 대기열 작업 | 기존 대기열 파일 — 형식 그대로, 새 항목을 넣지 않는다 | 별도 대기열 파일에만 둔다 |
| 그린 그림 | 기존 위치 | 별도 폴더 |
| 실행 | 그래픽카드는 하나이므로 두 대기열을 합쳐 **한 번에 한 작업**만 돌린다. 순서는 접수 시각 순 | 왼쪽과 같음 |

이렇게 하면 이전 엔진(0.8.5)으로 내려도 새 범위의 토큰·작업이 이전 엔진의 공유 목록에 **섞일 길이 없다**(이전 엔진은 별도 파일을 읽지 않는다). 2-3·3절의 「작업에 항목 추가만」「옆 파일」 설명은 이 표로 대체한다 — 기존 대기열 파일에는 `site`·`scope` 항목도 넣지 않는다.

대안(채택하지 않음 — 저장을 나누지 않을 때만): 안전한 내리기 절차를 엔진에 넣는다 — 「이전 버전으로 내리기 준비」를 실행하면 새 범위의 대기·진행 작업을 끝내거나 취소하고, 새 범위 작업·토큰을 공유 파일에서 빼 격리 파일로 옮긴 뒤에만 내리기를 안내한다. 이 절차 없이 내려 깔면 섞이므로, 대안을 고르면 절차 없는 내리기를 설치판이 막아야 한다. 구현·검증 부담이 커서 추천하지 않는다.

**결정 2 — 새 범위 기록이 없거나 깨졌으면 닫는다 (주인님 확정 2026-11-19: 「진행해」)**

- 새 범위 토큰 파일이 없거나 읽지 못하면 새 범위 토큰은 **하나도 유효하지 않다**. 새 사이트 요청은 「연결 필요」로 답하고, 기존 범위로 읽어 주지 않는다.
- 새 범위 대기열 파일을 읽지 못하면 그 파일을 덮어쓰지 않고 따로 보존한 뒤 새 범위 작업을 실행·조회하지 않는다. 엔진 창에 사유를 보여 준다.
- 두 경우 모두 기존 범위(무료음악·이미지 스튜디오)의 연결·대기열·실행은 영향이 없다.

**결정 3 — 재연결 승계는 세 조건이 모두 맞을 때만 (주인님 확정 2026-11-19: 「진행해」)**

1. 요청 출처가 이전 토큰의 발급 출처와 같다.
2. 이전 토큰이 유효하다(새 범위 토큰 파일에 있고 폐기되지 않음).
3. 엔진 창의 6자리 코드를 이번 요청에 넣었다(PC 주인의 명시적 연결 승인).

- 이전 토큰만으로는 새 토큰을 받을 수 없다. 코드만 있고 이전 토큰이 없거나 조건 1·2가 틀리면 승계 없이 **새 범위**로 연결한다(앞 범위는 보이지 않음).
- 승계가 되면 새 토큰 기록과 이전 토큰 폐기를 한 번의 저장으로 끝낸다(둘 다 유효하거나 둘 다 없는 순간이 없게).
- 기존 범위 토큰(`paired.json`)은 승계 대상이 아니다. 기존 두 사이트의 짝짓기는 지금 동작 그대로다.

**결정 4 — 접수 ID는 한 번만 저장하고, 내용이 다르면 충돌 (주인님 확정 2026-11-19: 「진행해」)**

- 같은 범위·같은 접수 ID가 **동시에** 여러 번 와도 작업은 하나만 저장되고, 모든 응답이 같은 작업 번호를 돌려준다(확인과 저장 사이에 다른 접수가 끼어들지 못하게).
- 접수할 때 요청 내용(모델 판·프롬프트·크기·시드)의 요약값을 작업에 함께 적는다. 같은 범위·같은 접수 ID인데 요약값이 다르면 **충돌 응답(409)**을 주고 새 작업을 만들지 않으며 기존 작업도 바꾸지 않는다.
- 접수 ID 형식(길이·문자)이 맞지 않으면 접수를 거절한다.

## 3. 호환과 되돌리기

- **옛 엔진 + 새 웹**: 옛 엔진은 허용 목록에 없는 출처의 요청을 버전 조회까지 모두 403으로 거절한다(`gateway.mjs`의 출처 검사가 모든 주소 앞에 있다). 브라우저에서는 이 응답이 「엔진이 꺼져 있음」과 구별되지 않으므로, 새 웹은 연결 실패 때 「엔진을 켜 주세요. 켜져 있다면 새 버전으로 올려 주세요」와 내려받기 안내를 함께 보여 준다. 크기 값을 보내도 옛 엔진이 조용히 1024로 그리는 일은 연결 자체가 안 되므로 생기지 않는다. 연결된 뒤에는 응답의 엔진 버전으로 최소 버전을 다시 확인한다.
- **새 엔진 + 기존 웹 2곳**: 요청 형식이 같아 지금과 같은 결과다. 크기 기본값·출처 분기가 그대로인지를 완료 조건에 넣는다.
- **되돌리기**: 엔진은 이전 설치판(0.8.5)으로 다시 설치하면 된다. 모델 폴더는 그대로이고, 새 범위의 토큰·작업·그림은 기존 파일과 나눠 저장해(2-6 결정 1) 이전 엔진의 공유 목록에 섞이지 않는다. 내린 뒤 새 범위 자료는 디스크에 남아 있다가 다시 새 버전을 깔면 이어서 쓴다. 웹은 새 프로그램 하나라 배포 중단·이전 배포로 되돌리기로 끝난다. DB 변경이 없어 되돌릴 자료가 없다.
- **모델 파일**: 기존 `ImageModels` 구조와 고정 해시를 그대로 쓴다. 이미 받은 회원은 다시 받지 않는다.

## 4. 최소 첫 단계 (P1-1)

가장 작은 범위로 「용도를 고르고 여러 장을 맡기면 내 PC가 그려서 폴더에 모아 준다」까지만 만든다.

1. **엔진(ECOM)**: 2-2~2-4의 권한·범위·접수 ID와 허용 크기 받기(1024×1024 · 1280×720 · 720×1280 세 가지만, 기본 1024×1024)를 **한 변경으로** 넣고, 그 변경 안에서 새 출처를 등록한다. 출처 등록만 먼저 내보내지 않는다.
2. **웹(새 프로그램, ECOM)**: 시작하기(엔진 연결·모델 준비 확인) → 만들기(용도 프리셋 4개, 비율 3개, 설명 여러 줄, 장수) → 일괄 시작 → 작업 기록(진행·실패 원인·결과 받기).
3. 프리셋이 모델을 고른다(1-2의 후보). 사용자가 바꿀 수 있다. 프롬프트는 영문 프리셋 틀 + 사용자가 고칠 수 있는 칸(한글 자유 입력의 자동 번역은 이 단계에 넣지 않는다 — 엔진이 ASCII만 읽는다).
4. 저장: 엔진이 그린 PNG를 웹이 받아 사용자가 고른 폴더에 저장(브라우저 폴더 접근 허용 1회) 또는 내려받기. 서버 업로드 0.

P1-1에 넣지 않는 것: 예약 실행, 폴더 감시, 참조 편집, 한글 문구 합성, ZIP·형식 변환, 메인 사이트 등록·요금, 로컬 번역 모델.

자동화 조건(목표): 처음 설정 3단계 · 매 작업 시작 1회 · 실행 중 조작 0회 · 연결 승인 1회 · 유료 호출 동의 0회.
