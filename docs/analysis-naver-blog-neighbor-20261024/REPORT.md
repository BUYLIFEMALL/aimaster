## 4. 우리 플랫폼 기준 판단

### 4-1. 기술적으로 가능한가 — **가능**
- 우리에게 이미 네이버 블로그 크롬 확장 기반이 있다(`naver-blog-agent`·`naver-blog-seo-studio` 확장: 웹 연결 토큰, `chrome.alarms`, 디버거 사람처럼 입력 — 인수인계 `docs/analysis-naver-realty-collector-20261024/HANDOFF_20261024_REALTY_LISTING_ALERT.md` §5-1에 위치 정리).
- AI 댓글 초안은 우리 표준대로 서버에서 회원 본인 키(`user_api_keys`, `resolveApiKey`)로 만들 수 있다.
- 댓글 답글 「초안 → 검토 → 게시」는 이미 3개 프로그램(`instagram-comment-reply`·`threads-comment-reply`·`youtube-auto-reply`)의 검증된 패턴이다.

### 4-2. 정책·위험 관점 — 원본 그대로는 **위험이 매우 큼**
| 위험 | 설명 |
|---|---|
| 네이버 운영정책 | 기계적·반복적 공감·댓글·서로이웃 신청은 스팸·어뷰징으로 보고 **신청 제한·댓글 제한·블로그 이용 제한·검색 노출 제외(저품질)**가 걸릴 수 있다. 회원 블로그에 직접 피해(상품 판매·체험단 블로그엔 치명적) |
| 제3자 피해 | 키워드로 찾은 **모르는 사람 블로그에 AI 댓글·이웃 신청을 대량으로** 보내는 것은 받는 사람 입장에서 스팸 |
| 비밀번호 | 우리 규칙상 프로그램이 회원 비밀번호를 받거나 입력하지 않는다(회원이 직접 로그인한 브라우저를 그대로 씀) |
| 봇 탐지 | 원본은 `insertText` 한 번 붙여넣기 — `docs/PLATFORM_PATTERNS.md` §20(사람처럼 한 글자씩·쉼) 기준 미달 |
| 숨은 동작 | H1(회원 계정으로 제작자 글 홍보)·H2(IP·패스워드 전송)는 우리가 절대 하지 않는 방식 |
| 키 돌려쓰기 | 한도를 피하려 여러 키를 돌리는 것은 무료 한도 우회 — 회원 키 1개 원칙 |

### 4-3. 결론
- **원본과 같은 「완전 무인 대량 서이추·스댓공」은 만들지 않는 것을 추천.** 기술은 되지만 회원 블로그가 제한될 위험과 제3자 스팸 문제가 크다.
- **대신 「내 블로그 소통 관리」 중심으로 재설계하면 구현 가치가 크다** — 우리 플랫폼에 네이버 블로그 소통 도구가 아직 없고(프로그램 비교표 확인), 댓글 프로그램 3개의 검증된 「AI 초안 → 회원 확인 → 게시」 패턴을 그대로 쓸 수 있다. 상세: [개발 플랜](PLAN_20261024_BLOG_NEIGHBOR_CARE.md).
