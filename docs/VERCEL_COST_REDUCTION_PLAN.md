## 1. 현황 (2026-10-18, 결제 주기 23일 남음)

- 포함 크레딧 $20 소진, 추가 요금 **$20.87**. 가장 큰 항목은 **Build CPU Minutes $31.92**(빌드할 때 쓰는 CPU 시간)이고, 나머지는 모두 $4 미만이다.
- **원인 1 — 빌드 머신이 가장 비싼 Elastic(4~30 vCPU 자동 확장)이었다.** 빌드 CPU 비용은 "빌드 시간 × CPU 개수"라 같은 빌드도 몇 배로 청구됐다.
- **원인 2 — 메인 사이트(`aimaster`)가 GitHub 푸시마다 자동 빌드된다.** 2026-10-17 오후 약 9시간 반 동안 최근 배포 100건 중 **87건이 메인 사이트 운영 빌드**(모두 `master` 푸시 자동 시작)였다. 이 저장소에는 모든 CLI가 하루 수십 번 푸시하는데, 바뀐 것이 서브프로그램뿐이어도 메인 사이트 전체가 다시 빌드된다(메인 사이트는 루트 `app`·`components`·`lib`·`types`만 사용 — 2026-10-18 확인).
- **원인 3 — 공용 기준 코드를 고칠 때마다 사본 30곳을 즉시 재배포했다.** 2026-10-17~18 이미지 공용 모듈 작업에서 30곳 × 4차례 + 9곳 등 130회 이상 빌드(Claude Code 윈도우). 문구·내부 개선처럼 급하지 않은 변경도 매번 전체 재배포했다.

## 2. 개선안

### A. 빌드 단가 낮추기
| # | 내용 | 상태 |
|---|---|---|
| A1 | 팀 기본 빌드 머신과 전체 프로젝트를 **Basic(2 vCPU)**으로 변경 | ✅ 2026-10-18 주인님 적용 |
| A2 | 동시 빌드 추가 구매(On-Demand Concurrent Builds) 끄기 — 여러 빌드가 겹치면 줄을 서서 순서대로(느려지지만 추가 요금 없음) | 🟡 주인님이 Vercel 설정에서 확인 |
| A3 | **Basic에서 빌드가 `JavaScript heap out of memory`(메모리 부족)로 실패하면** — Basic·Standard는 메모리가 둘 다 8GB라 Standard로 올려도 대개 해결되지 않는다. ① 먼저 그 프로그램만 빌드 명령의 Node 메모리 한도를 올린다: `package.json`의 `"build": "next build"` → `"build": "node --max-old-space-size=6144 ./node_modules/next/dist/bin/next build"`(윈도우 로컬에서도 동작, 추가 비용 없음) ② 그래도 실패하면 **그 프로젝트만** Enhanced(16GB)로 올리고 이 표·그 프로그램 `AGENTS.md`에 기록한다(팀 기본값은 Basic 유지). CPU가 모자라 빌드가 너무 느린 경우만 Standard를 검토한다 | ✅ 2026-10-18 규칙 확정(주인님 제안 반영) |

### B. 메인 사이트 불필요한 자동 빌드 막기 (가장 효과 큼)
| # | 내용 | 상태 |
|---|---|---|
| B1 | 루트 `vercel.json`에 `ignoreCommand`를 넣어, **직전 배포 이후 메인 사이트 파일(`app`·`components`·`lib`·`types`·`public`·`middleware.ts`·설정 파일)이 안 바뀌었으면 빌드를 건너뛴다.** 서브프로그램만 바뀐 푸시는 빌드하지 않는다. 비교 기준은 Vercel이 넣어 주는 `VERCEL_GIT_PREVIOUS_SHA`(직전 성공 배포), 값이 없으면 안전하게 빌드한다 | ✅ 2026-10-18 적용(주인님 승인) |
| B2 | `master`가 아닌 브랜치(`cloud-work` 등) 푸시의 미리보기 빌드 건너뛰기 — 클라우드 세션은 배포하지 않는 규칙이라 미리보기가 필요 없다 | ✅ 2026-10-18 적용(주인님 승인) |

### C. 작업 방식 (모든 CLI 규칙)
| # | 규칙 | 상태 |
|---|---|---|
| C1 | **공용 기준 코드 변경의 재배포 등급을 나눈다.** ① 회원에게 바로 영향이 있는 버그·이중 과금·보안 수정 → 사본 전체 즉시 재배포(지금처럼) ② 안내 문구·주석·내부 정리처럼 급하지 않은 변경 → 사본은 저장소에 `--sync`로 반영만 하고, **그 프로그램을 다음에 고쳐 배포할 때 함께 나간다**(그때 버전 +0.01). 미배포 사본 목록은 `docs/SHARED_MODULES.md`에 적어 둔다 | ✅ 2026-10-18 적용(주인님 승인) |
| C2 | **같은 날 같은 프로그램은 한 번만 배포**한다. 연달아 나오는 개선은 모아서 한 번에 배포한다(오늘처럼 같은 30곳을 4번 배포하지 않는다) | ✅ 2026-10-18 적용(주인님 승인) |
| C3 | **배포 전에 로컬에서 먼저 확인**한다(`npx tsc --noEmit`, 테스트, 필요하면 `npm run build` — 로컬은 무료). Vercel 빌드 실패로 다시 배포하는 일을 줄인다 | ✅ 2026-10-18 규칙화 |
| C4 | 루트(`.`) 배포는 메인 사이트 코드나 루트 `public/downloads` 파일(예: poster-web 확장 ZIP)이 실제로 바뀐 때만 한다 | ✅ 2026-10-18 규칙화 |
| C5 | 여러 폴더 연속 배포는 `git diff`로 **직전 배포 이후 실제로 바뀐 폴더만** 대상으로 하고, 폴더마다 작업 중 표를 다시 확인한다(2026-10-18 ERROR_LESSONS) | ✅ 2026-10-18 규칙화 |
| C6 | 커밋·푸시는 작업 단위로 모아서 한다(잦은 작은 푸시 자제). B1이 적용되면 메인 사이트 비용 영향은 거의 없어지지만 기록 정리에도 좋다 | ✅ 2026-10-18 규칙화 |
