# Vercel 비용 절감 작업 방식 개선안 (VERCEL_COST_REDUCTION_PLAN.md)

> **★★★ 최상단 고정 — 개발·배포 지침: 작은 소스 수정은 모았다가 배포한다 (2026-10-22 주인님 지시: 「배포비용 절감을 위해 다음 작업을 위해 배포완료가 되어야 하는 경우를 제외하고 작은 소스수정 작업은 매 작업시마다 배포하지 말고 모았다가 배포한다」, 모든 CLI·모든 장비 공통)**
> **작은 소스 수정(문구·화면 조정·작은 버그·내부 정리·후보 처리 등)은 작업마다 Vercel 배포하지 않는다.** 로컬 검사(시험·`tsc`·필요하면 `npm run build`, 무료)까지 마치고 커밋·푸시한 뒤 「미배포 대기」로 모아 두었다가, 같은 프로그램의 다음 배포 때 함께 내보낸다.
> **예외 — 바로 배포한다:** ① **대량 소스 수정**이 발생한 경우 ② **다음 작업을 위해 배포 완료가 필수**인 경우(예: 다른 프로그램이 새 API를 불러야 함, 실제 화면·외부 연동 검수가 다음 단계의 전제). 회원에게 바로 피해가 가는 버그·보안·이중 과금 수정도 기존 규칙대로 즉시 배포한다.
> **모아 둘 때 지킬 것:** ⓐ 버전(`vX.YY`)은 실제로 배포할 때 한 번만 올린다(미배포 커밋은 버전을 올리지 않음) ⓑ 미배포 변경은 그 프로그램 `docs/IMPROVEMENTS.md`(또는 AGENTS.md 맨 위)에 「미배포 대기: 무엇·커밋」으로 적고, 루트 `docs/HANDOFF.md` 항목에도 「미배포」라고 밝힌다 ⓒ 다음에 그 프로그램을 배포하는 CLI는 대기 목록을 확인해 함께 내보내고 대기 표시를 지운다 ⓓ 확장이 있는 프로그램은 배포 때 manifest·ZIP·DB 버전을 함께 맞춘다(핵심 원칙 10) ⓔ 완료 보고에는 「배포: 미배포 대기(사유)」 또는 「배포: 예외 ①/② 적용」을 적는다. 비용 사전 보고·종료 비용 리포트 규칙은 그대로다. 상세: [`docs/VERCEL_COST_REDUCTION_PLAN.md`](VERCEL_COST_REDUCTION_PLAN.md) 맨 위(이 문서).
> **미배포 대기 한곳 목록(2026-10-22 추가):** 프로그램별 「미배포 대기」를 모아 보는 색인은 [`docs/PENDING_DEPLOYS.md`](PENDING_DEPLOYS.md) — 미배포로 커밋할 때 한 줄 추가, 그 프로그램을 배포할 때 확인·삭제. 공용 사본 미배포는 `docs/SHARED_MODULES.md` 「미배포 사본」 표. 배포 전 확인: `node scripts/pending-check.mjs <폴더>`. 배포 도우미: `node scripts/deploy.mjs <폴더> [--go]`(확인 후 배포).

## 2. 개선안

### A. 빌드 단가 낮추기
| # | 내용 | 상태 |
|---|---|---|
| A1 | 팀 기본 빌드 머신과 전체 프로젝트를 **Basic(2 vCPU)**으로 변경 | ✅ 2026-10-17 주인님 적용 |
| A2 | 동시 빌드 추가 구매(On-Demand Concurrent Builds) 끄기 — 여러 빌드가 겹치면 줄을 서서 순서대로(느려지지만 추가 요금 없음) | 🟡 주인님이 Vercel 설정에서 확인 |
| A3 | **Basic에서 빌드가 `JavaScript heap out of memory`(메모리 부족)로 실패하면** — Basic·Standard는 메모리가 둘 다 8GB라 Standard로 올려도 대개 해결되지 않는다. ① 먼저 그 프로그램만 빌드 명령의 Node 메모리 한도를 올린다: `package.json`의 `"build": "next build"` → `"build": "node --max-old-space-size=6144 ./node_modules/next/dist/bin/next build"`(윈도우 로컬에서도 동작, 추가 비용 없음) ② 그래도 실패하면 **그 프로젝트만** Enhanced(16GB)로 올리고 이 표·그 프로그램 `AGENTS.md`에 기록한다(팀 기본값은 Basic 유지). CPU가 모자라 빌드가 너무 느린 경우만 Standard를 검토한다 | ✅ 2026-10-17 규칙 확정(주인님 제안 반영) |

### B. 메인 사이트 불필요한 자동 빌드 막기 (가장 효과 큼)
| # | 내용 | 상태 |
|---|---|---|
| B1 | 루트 `vercel.json`에 `ignoreCommand`를 넣어, **직전 배포 이후 메인 사이트 파일(`app`·`components`·`lib`·`types`·`public`·`middleware.ts`·설정 파일)이 안 바뀌었으면 빌드를 건너뛴다.** 서브프로그램만 바뀐 푸시는 빌드하지 않는다. 비교 기준은 Vercel이 넣어 주는 `VERCEL_GIT_PREVIOUS_SHA`(직전 성공 배포), 값이 없으면 안전하게 빌드한다 | ✅ 2026-10-17 적용(주인님 승인) |
| B2 | `master`가 아닌 브랜치(`cloud-work` 등) 푸시의 미리보기 빌드 건너뛰기 — 클라우드 세션은 배포하지 않는 규칙이라 미리보기가 필요 없다 | ✅ 2026-10-17 적용(주인님 승인) |

### C. 작업 방식 (모든 CLI 규칙)
| # | 규칙 | 상태 |
|---|---|---|
| C1 | **공용 기준 코드 변경의 재배포 등급을 나눈다.** ① 회원에게 바로 영향이 있는 버그·이중 과금·보안 수정 → 사본 전체 즉시 재배포(지금처럼) ② 안내 문구·주석·내부 정리처럼 급하지 않은 변경 → 사본은 저장소에 `--sync`로 반영만 하고, **그 프로그램을 다음에 고쳐 배포할 때 함께 나간다**(그때 버전 +0.01). 미배포 사본 목록은 `docs/SHARED_MODULES.md`에 적어 둔다 | ✅ 2026-10-17 적용(주인님 승인) |
| C2 | **같은 날 같은 프로그램은 한 번만 배포**한다. 연달아 나오는 개선은 모아서 한 번에 배포한다(오늘처럼 같은 30곳을 4번 배포하지 않는다) | ✅ 2026-10-17 적용(주인님 승인) |
| C2 정정 | **(2026-10-18 주인님 정정) C2는 하루 횟수 제한이 아니다.** 필요하면 같은 날에도 배포한다. 비용이 커지는 원인은 여러 프로그램을 한꺼번에 동시에 빌드하는 것(동시 빌드 추가 사용·서버 부하)이므로 ① 여러 프로그램은 한 번에 하나씩 순차 배포(앞 배포 `vercel inspect` Ready 확인 후 다음) ② 같은 프로그램에 짧은 간격으로 나오는 작은 수정은 작업 단위로 모아 배포 ③ 회원에게 영향이 있는 수정(버그·프롬프트 오류·보안)은 기다리지 않고 배포 | ✅ 2026-10-18 적용(주인님 지시) |
| C3 | **배포 전에 로컬에서 먼저 확인**한다(`npx tsc --noEmit`, 테스트, 필요하면 `npm run build` — 로컬은 무료). Vercel 빌드 실패로 다시 배포하는 일을 줄인다 | ✅ 2026-10-17 규칙화 |
| C4 | 루트(`.`) 배포는 메인 사이트 코드나 루트 `public/downloads` 파일(예: poster-web 확장 ZIP)이 실제로 바뀐 때만 한다 | ✅ 2026-10-17 규칙화 |
| C5 | 여러 폴더 연속 배포는 `git diff`로 **직전 배포 이후 실제로 바뀐 폴더만** 대상으로 하고, 폴더마다 작업 중 표를 다시 확인한다(2026-10-17 ERROR_LESSONS) | ✅ 2026-10-17 규칙화 |
| C6 | 커밋·푸시는 작업 단위로 모아서 한다(잦은 작은 푸시 자제). B1이 적용되면 메인 사이트 비용 영향은 거의 없어지지만 기록 정리에도 좋다 | ✅ 2026-10-17 규칙화 |
