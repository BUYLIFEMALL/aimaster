**주인님 확정 방향(2026-10-19): 당분간 기존 프로그램 기능 개선·버그 수정·안정화에 집중합니다. 그 과정에서 잘 만들어지고 검증된 기능을 레퍼런스 모듈로 정리하고, 신규 프로그램·기존 프로그램 리뉴얼 때 필요한 모듈을 하나씩 적용합니다. 전체 프로그램 일괄 전환·지금 당장 모든 후보 추출은 하지 않습니다.**

## 끼웠다 뺐다 하는 범위

유튜브 조회, 쇼핑 검색, 글쓰기, 콘텐츠 수집, 네이버/티스토리 확장 입력을 **입력·출력 규격이 정해진 독립 기능**으로 다룹니다. 프로그램이 필요한 모듈을 선택하고 연결 코드를 바꿔 교체할 수 있게 합니다. 처음부터 복잡한 실행 중 플러그인 로더·공용 서버·통합 재작성은 만들지 않습니다. DB가 필요한 모듈은 연결을 제거해도 저장 데이터가 자동 삭제되지 않으며 별도 마이그레이션·롤백이 필요합니다.

현재 공식 기준은 [SHARED_MODULES](../SHARED_MODULES.md)와 [SHARED_FEATURE_MAP](../SHARED_FEATURE_MAP.md)입니다. 등록된 기준 기능은 4개입니다. 아래의 나머지 항목은 비교 후보이며 검증된 신규 공용 모듈로 등록됐다는 의미가 아닙니다. 이 표를 두 번째 공식 등록부로 운영하지 않습니다.

## 콘텐츠 수집은 방식별로 선택

| 방식 | 참고·연결 범위 | 공통 결과에 기록할 것 |
|---|---|---|
| 공개 웹 URL | 안전한 URL 수집 + 본문 추출 | 최종 URL·제목·본문·출처·조회 시각·공개/유료 여부 |
| RSS/Atom | 피드 항목 해석 + 원문 연결 | 게시/수정 시각·원문 URL·중복 식별값 |
| 검색/웹 리서치 API | Perplexity·네이버·검색 제공사별 어댑터 | 회원 제공사·조회 조건·근거 링크·실제 호출/사용량 |
| 유튜브 | 공식 데이터 조회·허용된 자막/회원 제공 대본을 별도 구분 | 영상/채널 ID·지표 기준 시각·본문 획득 방식 |
| 로그인된 웹의 확장 수집 | 회원이 로그인한 페이지·허용된 대상만 | 회원·사이트·수집 범위·중단 상태. 로그인 우회 금지 |
| 파일/수동 입력 | PDF/DOCX/TXT·붙여넣기·회원 음성/대본 | 원본 파일 표시·페이지/구간·파싱 오류·회원 권리 확인 |

수집 표준 `SourceDocument` 후보: `schemaVersion/id/sourceUrl/title/text/author/publishedAt/fetchedAt/method/contentHash/originalCreatedAt/expiresAt/rights`입니다. 소유자는 클라이언트가 보내는 문자열로 신뢰하지 않고 인증된 회원 문맥에서 결정합니다. 출처 원문은 신뢰하지 않는 자료로 취급하고, 원문 속 지시를 도구 실행 명령으로 사용하지 않습니다. 수집 실패를 추측한 본문으로 채우지 않습니다.

쇼핑 `ProductCandidate` 후보는 제공사·상품 ID·가격/통화·가격 기준 시각·재고 확인 여부·이미지·제휴 상태를 구분합니다. 유튜브 쇼츠 조회와 상품 검색 API는 별개 모듈이며, 보편적인 하나의 '쇼핑쇼츠 API'가 존재한다고 가정하지 않습니다. 필요한 작업에서 상품 선정 → 쇼츠 기획/대본 순으로 조합합니다.

## 네이버·티스토리 확장 포스팅

공통 처리: 웹에서 작업 전달 → 본인 계정 확인 → 실행 선점/번호 → 편집기 열기 → 블록 입력 → heartbeat → 결과 보고. 플랫폼별 DOM·선택자·이미지 삽입 방식은 별도 어댑터에 둡니다. 문서 블록 규격이 같아도 네이버 선택자를 티스토리에 그대로 복사하지 않습니다.

현재 티스토리 확장 `manifest.json`은 **최종 저장·발행을 자동으로 하지 않는 입력기**입니다. '자동 포스팅'이라는 표현만으로 이 경계를 자동 발행으로 바꾸지 않습니다. 각 프로그램의 승인된 최종 발행 경계를 보존합니다. 작업 중단·오래된 결과 보고·여러 탭의 중복 실행을 합성 편집기로 검증한 뒤 실제 회원 화면 입력을 검수합니다. 이 분석에서는 실제 입력/게시를 하지 않았습니다.

확장 모듈을 채택해 제품을 변경할 때는 해당 앱 `<프로그램>/extension/`, manifest 버전, 기존 주소의 ZIP, DB 확장/앱 버전, 라이브 ZIP 검증을 같은 출시 작업에서 처리합니다([확장 출시 규칙](../EXTENSION_RELEASE_RULES.md)). 옛 확장과 서버의 요청 규격 호환도 확인합니다.

## 좋은 기능을 기준으로 승격하는 조건

**주인님 확정 검토 기준은 ① 자동화 기능이 안정적으로 구현되는가 ② 현재 개발된 프로그램에 적용 가능한가 ③ 사용자에게 편리한 자동화 기능인가, 세 가지입니다.** 세 항목을 각각 근거와 함께 기록합니다. 오류/중단/중복 실행, 기존 프로그램 구조·개인 계정/API·데이터 정책 호환, 단계·반복 입력 감소와 복구 안내를 확인합니다. 확인하지 않은 것은 '검증 필요'이며 후보 등록만으로 통과시키지 않습니다. 유지보수성은 이 기준을 지속해서 지키기 위한 구현 조건입니다.

| 항목 | 남길 내용 |
|---|---|
| 출처 | 후보 비교·선정 이유·기준 파일·참고 커밋·기능 담당 프로그램 |
| 규격 | 입력/출력 예시·버전·지원/미지원 기능·오류·시간/크기 상한 |
| 검증 | 합성 응답/순수 단위 검사·제공사 계약·UI/확장 회귀·소비 앱 빌드 |
| 개인 자료 | 인증된 회원·본인 키·소유자 조건/RLS·원생성일 30일·정리 관측 |
| 운영 | 취소·재시도·멱등성·비용/중복 과금·비밀 가리기·실패 안내 |
| 유지보수 | 사용 예제·사용 앱 목록·사본 검사·변경 이력·이전/롤백 안내 |

여러 기능을 한 번에 합치기보다 **작은 독립 기능 하나**부터 승격합니다. 안정성 → 유지보수 → 결과 품질 순으로 고르고, 테스트가 없다면 먼저 기존 동작을 확인합니다. 문제가 발견된 전역 캐시·중복 발송 패턴을 그대로 레퍼런스로 복사하지 않습니다. 코드가 짧거나 최신이라는 이유만으로 기준을 바꾸지 않습니다.

## 실제 적용 순서 — 대규모 전환 일정 아님

1. 지금은 각 프로그램의 기능 개선·버그 수정·안정화 작업을 진행합니다. 새 모듈 추출만을 위한 일괄 작업은 시작하지 않습니다.
2. 그 작업에서 재사용 가치가 높은 기능이 발견되면 프로그램별 인수인계에 '레퍼런스 후보'와 근거·남은 검증을 기록합니다.
3. 코드·오류 처리·회원 흐름이 안정되면 해당 기능 하나를 분리합니다. 추출 비용이 재사용 이득보다 크면 사례 문서로만 남겨도 됩니다.
4. 검증 후 공식 SHARED_MODULES/SHARED_FEATURE_MAP와 기존 사본 검사기에 등록합니다. 이미 있는 기준을 중복 등록하지 않습니다.
5. 신규 프로그램 또는 기존 프로그램 리뉴얼 시 적합한 모듈을 한 개씩 선택해 적용하고, 자체 연결 코드·화면·비용·회원 격리를 검수합니다.
6. 적용 전/후 기능·오류·빌드·배포 증거와 개선점·미작업을 프로그램별로 남깁니다. 회원 생성 자료를 함께 배포하거나 공용화하지 않습니다.

모듈을 뺄 때도 기존 자료의 접근·30일 정리·이력 정합성을 보존합니다. 연결 규격이 깨지면 소비 앱별 수정과 회귀 검증이 필요하므로 '아무 검사 없이 자유롭게 끼우기'로 해석하지 않습니다.
