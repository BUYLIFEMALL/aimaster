## 1. 지금 구조
- 운영자 표 `mall_builder_store_staff`(몰·사용자·역할). 역할 칸은 이미 `owner / manager / staff` 세 값을 받지만, 지금은 몰을 만든 대표(owner)만 들어가고 직원을 넣는 길이 없음.
- 「운영자인가」 판단 `mall_builder_is_store_staff()`가 **보안 규칙 63개·DB 함수 50개**에 쓰임 → 모두 권한별로 바꾸면 매우 큰 작업. 그래서 막는 범위를 결정 항목으로 둠.

## 2. 기능(제안)
| 기능 | 내용 |
|---|---|
| 직원 초대 | 대표가 이메일·권한을 정해 초대 링크 생성(7일·1회용) → 받은 사람이 같은 이메일로 로그인해 수락 |
| 권한 | 메뉴 묶음별 켬/끔 — 주문·견적 / 상품·재고·공동구매 / 손님·쿠폰·포인트 / 게시판(후기·문의·FAQ·공지) / 첫 화면·사진 / 통계. 설정·직원 관리는 대표만 |
| 관리 화면 | 권한 없는 메뉴는 숨기고 그 화면을 열면 「권한이 없습니다」 |
| 직원 목록 | 대표가 권한 바꾸기·내보내기 |
| 접속 기록 | 개인정보 화면(손님 상세·주문 상세)을 연 기록, 직원 초대·권한 변경·내보내기 기록 — 대표만 열람 |

## 3. 결정 항목 (주인님께 여쭐 것)
1. **권한 단위**: (추천) 위 메뉴 묶음 6개 + 설정·직원 관리는 대표만 / 메뉴 하나하나 따로
2. **막는 곳**: (추천) 화면은 메뉴 묶음별로 막고, DB에서는 돈·비밀값·사람이 걸린 것만 권한 검사 추가 — 결제·세금계산서·알림 키와 폐쇄몰 저장, 환불·주문 취소, 포인트 지급·차감, 직원 관리 / 보안 규칙 63개·함수 50개 전부를 권한별로(큰 작업, 빌드·시험 많이 늘어남)
3. **초대 방식**: (추천) 초대 링크 + 이메일 일치(초대한 이메일로 로그인해야 수락) / 이메일 상관없이 링크만 있으면 수락
4. **접속 기록 보관**: (추천) 1년(개인정보의 안전성 확보조치 기준 최소 기간), 대표만 열람 / 30일(플랫폼 생성 데이터 기본 보관 기간) — 접속 기록은 법정 보관 기록이라 30일 자동 삭제 대상이 아니라고 보는 것이 추천 이유
