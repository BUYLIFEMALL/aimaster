# 카드 결제(토스페이먼츠) — 개발 플랜 (2026-11-05)

- 대상: Lab `labs/mall-builder` (DB `rjjtjakljjxsgjelqgek`). 운영 DB·운영 사이트·메인 사이트 결제(페이앱)는 건드리지 않음
- 상태: 플랜 — 주인님 승인 대기
- 원칙: **몰 운영자 본인 토스페이먼츠 계정·본인 키**(최상위 규칙). 플랫폼(주인님) 키로 다른 몰 결제를 대신 받지 않는다

## 1. 문제
지금 결제는 무통장(입금 확인 수작업)·외상(사업자만)뿐이라, 일반 손님이 그 자리에서 결제를 끝낼 수 없다.

## 2. 왜 토스페이먼츠인가
| 항목 | 내용 |
|---|---|
| 개발·시험 | 전자결제 계약 전에도 테스트 키로 결제창·승인·취소까지 시험 가능(공식 문서 2026-11-05 확인), 실제 돈이 나가지 않음 |
| 연동 | 결제위젯 v2 — 클라이언트 키로 결제창, 서버가 시크릿 키로 「결제 승인」(요청 후 10분 안) |
| 취소 | `POST /v1/payments/{paymentKey}/cancel` — `cancelAmount`로 **부분 취소** 가능 → 기존 부분 취소(D5)와 맞물림 |
| 실제 운영 | 운영자가 토스페이먼츠와 전자결제 계약·심사 뒤 라이브 키로 바꾸면 됨(수수료는 운영자 부담, 계약 때 요금 확인) |

메인 사이트의 페이앱은 주인님 구독 결제용이라 그대로 두고, 몰 결제와 섞지 않는다.

## 3. 설계 — 시크릿 키는 DB 밖으로 나가지 않는다
D8·D9에서 정한 원칙(손님 요청에서 운영자 키를 꺼내는 길을 만들지 않는다)을 지키면서, 결제 승인은 손님이 결제창에서 돌아온 그 순간에 해야 한다. 그래서 **DB 함수가 토스 API를 직접 부른다**(Supabase `http` 확장, 응답을 바로 받는 방식).

```
손님 주문서 「카드 결제」 → 주문(입금 대기·카드) 생성·재고 확보
 → 토스 결제창(운영자 클라이언트 키) → 성공 주소로 paymentKey·orderId·amount
 → 서버 동작이 DB 함수 mall_builder_card_confirm(주문, paymentKey, amount) 호출
     DB 함수: 그 주문의 손님인지·카드 주문인지·입금 대기인지·금액이 주문 금액과 같은지 확인
            → 비밀 표의 시크릿 키로 토스 승인 API 호출(DB 안에서) → 성공이면 결제 완료·결제 기록
 → 손님 화면에는 결과만(키·토스 응답 원문은 돌려주지 않음)
```

| 항목 | 내용 |
|---|---|
| 키 보관 | 클라이언트 키 = 몰 설정(공개돼도 되는 값), 시크릿 키 = D8 비밀 표에 칸 추가(규칙 0개) |
| 결제 기록 | 새 표 `mall_builder_card_payments`(주문·paymentKey·금액·상태·승인/취소 시각·토스 거래 번호, 운영자·그 주문 손님만 읽기) |
| 금액 위조 막기 | 금액은 DB의 주문 금액만 믿는다. 돌아온 amount가 다르면 승인하지 않고 주문을 그대로 둠 |
| 중복 승인 막기 | 같은 주문은 한 번만(고유 제약 + 주문 행 잠금), 이미 결제 완료면 다시 부르지 않음 |
| 실패·포기 | 실패 주소 → 주문 화면에 사유와 「다시 결제」·「주문 취소」. 카드 주문은 **30분 결제 기한**을 붙여, D8 자동 취소가 켜져 있으면 결제하지 않은 주문의 재고를 되돌림 |
| 취소·환불 | 운영자가 카드 주문을 취소·부분 취소하면 DB 함수가 토스 취소 API를 부름(멱등키 = 취소 기록 번호). 성공해야 재고·금액을 바꿈 |
| 결과 불확실 | 토스 응답이 끊기면 「확인 필요」로 남기고, 운영자 화면 「결제 다시 확인」(조회 API)로 맞춘다 — 자동으로 다시 승인하지 않음 |
| 알림 | 결제 완료 → 기존 「입금 확인 → 손님」 알림 문구를 「결제 완료」로(D9 트리거에 카드 조건 추가), 운영자 「새 주문」은 그대로 |

검토했지만 쓰지 않는 방법: Lab 앱에 Supabase 서비스 키를 넣어 서버가 키를 읽게 하기 — 앱 전체가 모든 몰의 비밀을 읽을 수 있게 되어 위험이 큼. 토스 웹훅만으로 처리 — 승인은 어차피 서버가 불러야 해서 1차에는 넣지 않음(나중에 가상계좌를 붙일 때 추가).

## 4. DB 변경 (추가만 원칙의 예외 1건)
| 변경 | 내용 |
|---|---|
| 확장 | `http` 확장 켜기(Lab DB 전체에 적용되는 추가 — 다른 Lab 프로그램에는 영향 없음) |
| **예외** | 주문 표 `pay_method` 제약이 지금 `'bank'`만 허용 → `'card'`를 넣으려면 **이 제약 하나를 지우고 다시 만들어야 함**(지우기 = Supabase 확인 창). 주인님 승인 뒤 확인 창을 눌러 주시거나 SQL 편집기에서 한 줄 실행 |
| 표·칸 | 비밀 표 `toss_secret_key`, 몰 설정 `toss_client_key`, 결제 기록 표 |
| 함수 | 카드 주문 만들기(기존 주문 함수에 결제 방법 추가), `mall_builder_card_confirm`, `mall_builder_card_cancel`, `mall_builder_card_recheck`, 키 저장(운영자만) |

## 5. 화면
- 운영자 설정 「카드 결제(토스페이먼츠)」: 클라이언트 키·시크릿 키(「등록됨」만 표시), 테스트/라이브 표시(키 앞부분 `test_`/`live_`로 판별), 「켜기」
- 손님 주문서: 결제 방법에 「카드 결제」(키가 있을 때만), 주문하기 → 토스 결제창
- 결제 성공·실패 화면, 주문 상세에 결제 정보(카드사·승인 시각, 카드 번호는 저장·표시 안 함)
- 운영자 주문 상세: 결제 정보, 취소·부분 취소 때 「카드 환불」이 함께 됨, 「결제 다시 확인」

## 6. 구현 순서와 확인
| 순서 | 할 일 | 확인 |
|---|---|---|
| 1 | DB(확장·제약 예외·표·함수) | DB 시험(되돌림, 지우기 문장 없이): 남의 주문·금액 다름·이미 결제됨 거절, 키 없음 거절. 토스 호출은 문서용 테스트 키로 실제 시험 승인·취소 |
| 2 | 결제창·성공/실패 화면 | 자동 시험(금액 검사·키 종류 판별), 내 PC 빌드 |
| 3 | 취소·부분 취소 연결 | DB 시험: 부분 취소 금액·재고·결제 기록이 함께 맞는지 |
| 4 | Lab 배포(빌드 1회, 직전 재확인) | 실행 주소·화면 |
| 5 | 실제 시험(테스트 모드) | 손님(ego)이 카드 결제 → 결제 완료·알림 → 운영자 부분 취소 → 토스 테스트 내역과 금액 대조 |

## 7. 주인님 준비
1. 토스페이먼츠 개발자센터 가입(무료) → 테스트 키(클라이언트 키·시크릿 키) 확인. 가입 전에는 공식 문서용 공개 테스트 키로 1~3단계를 진행
2. 배포 뒤 몰 설정 화면에 테스트 키 직접 입력
3. DB 제약 1건 교체 승인(확인 창 또는 SQL 한 줄)
4. 실제 판매 전 토스페이먼츠 전자결제 계약·심사(라이브 키) — 이번 범위 밖
