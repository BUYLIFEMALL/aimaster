# 원고 저장 충돌·응답 유실 보완 — v1.71 (2026-10-11)

## 작업 범위와 현재 상태

남은 작업 2번입니다. 에이전트의 웹 원고 저장을 보완했습니다. BLOG는 클로드 담당이며 수정하지 않습니다. 기존 회원 계정·API 키·DB 스키마·환경변수를 바꾸지 않습니다. SQL은 프로그램/확장/다운로드 버전 메타데이터 갱신만 포함합니다. 운영 배포 및 실제 회원 화면 검수 결과는 아래 운영 기록에 이어 적습니다.

## 문제 → 수정

- 두 탭이 같은 원고를 읽은 뒤 차례로 저장하면, 서버 조회 시점의 updated_at만 비교하던 방식은 두 번째 탭의 오래된 내용을 허용했습니다. 목록/발행 설정 GET과 생성 응답에 save_revision을 반환하고, POST/PUT/발행 설정 저장은 해당 값을 확인합니다. DB 반영은 여전히 회원+ID+상태+updated_at 조건으로 확인합니다. 오래된 요청은409이며 화면 편집본을 남깁니다. 자동으로 최신 버전을 빌려 강제 덮어쓰지 않습니다.
- 신규 POST가 저장됐지만 응답이 유실되면 재전송으로 새 행이 생길 수 있었습니다. 브라우저가 저장 전에 원고 UUID와 요청 UUID를 정하고 유지합니다. 기존 UUID 기본 키와 research_summary.draft_save 마지막 영수증을 같은 insert/update에 저장합니다. 같은 요청/내용은 기존 저장을200으로 확인하고 원고 updated_at을 다시 쓰지 않습니다. 같은 요청 번호로 다른 내용을 보내거나 더 최신 저장 이후 옛 요청을 보내면409입니다. 타인 UUID는 새 사본으로 우회하지 않습니다.
- 저장 확인이 안 된 요청은 PostSaveClient.pending에 그대로 보관합니다. 본문·이미지 배열도 복사해서 요청 내용이 뒤늦게 바뀌지 않습니다. 같은 화면에서 재시도할 때 미확인 저장부터 확인하고, 변경된 편집본이 있으면 그다음 요청으로 저장합니다. HTTP200만으로 성공 처리하지 않고 success·원고ID·save_revision이 맞아야 합니다. 동시 생성/동시 동일 수정은 PK 또는 CAS 경쟁 뒤 영수증을 다시 확인합니다.
- 큐/생성 화면의 캐시는 서버가 확인한 해당 행만 합칩니다. 오래된 응답은 더 최근 updated_at의 행을 덮지 않으며 다른 행도 보존합니다. 원고 전환 뒤 늦게 온 이미지/편집 응답은 현재 화면과 캐시를 건드리지 않습니다. 실패한 임시보관은 nba_unsaved_post_<UUID>에 별도로 보관하고 서버 저장 성공·대기 등록으로 표시하지 않습니다.
- 편집창을 열 때의 버전을 별도로 유지합니다. 다른 저장 작업의 최신 버전을 오래된 편집창에 빌려주지 않습니다. 부모 목록/이미지가 갱신돼도 열린 편집창 내용을 초기화하지 않고, 닫았다 다시 열 때만 초기화합니다.409/통신 실패 시 창이 닫히지 않습니다.
- 발행 설정도 같은 저장 계약을 사용합니다. 같은 화면에서 본문/이미지를 저장했고 설정에 미저장 변경이 없다면 최신 설정을 불러옵니다. 변경 중인 설정은 그대로 두고 안내합니다. '설정 다시 불러오기'는 변경 내용을 먼저 보관하도록 안내한 후 명시적으로 불러옵니다. 검수 확인만 바뀌고 원고/설정이 동일하면 save_revision을 바꾸지 않습니다.
- 생성 원고의 저장을 확인하지 못했다면 후속 유료 이미지 자동 생성은 시작하지 않습니다.

## 주요 위치와 계약

- src/lib/postSaveProtocol.ts: 편집/상태/설정 지문, 마지막 저장 영수증. 검수/진행 메타데이터만의 변경은 편집 지문에서 제외하되 DB CAS는 유지합니다. 매 저장 요청 번호가 지문에 포함돼 A→B→A 변경도 구분합니다.
- src/lib/postSaveHandler.ts: 본인 원고 조회·버전 확인·검수/진행 보호·atomic UUID insert/CAS update·실제 저장 확인.
- src/lib/postSaveClient.ts: 정확한 미확인 요청 재시도·응답 검사·동시 저장 차단·행 단위 캐시 병합.
- /api/posts POST/PUT: id + save_request_id(UUID), 신규는 create:true, 기존은 expected_revision. 서버가 반환한 post.save_revision을 다음 저장의 기준으로 사용합니다. PUT 없는/타인 원고404, UUID 충돌/옛 버전409, 미검수 대기 전송422, 저장소/결과 확인 실패503. research_summary/검수 기록은 클라이언트 입력으로 덮지 않습니다.
- /api/posts/[id]/publishing PUT: 동일 expected_revision/save_request_id, 기존 category/tags/setDefault/executionMode. post 저장 후 블로그 기본값 반영 실패는500으로 남기고 같은 요청으로 재시도할 수 있습니다. 계정 기본값과 원고 저장은 하나의 DB 트랜잭션이 아닙니다.
- generate 응답: 기존 saved/postId와 함께 save_revision이 있는 post를 반환합니다. /api/extension/* 계약은 유지하므로 이전 확장도 서버와 연결됩니다.

## 검사와 한계

- 실제 TypeScript API/클라이언트/페이지 콜백을 실행하는 자동 검사105개 통과: 저장18개, 기존 검수/실행28개, 화면/캐시/이미지20개, 큐 필터3개, 확장 결과16개, 편집 안전6개, 공통 입력14개.
- 기존 posts API(f015614b)에 새 저장 검사 초기15개 적용:10개 실패. 서버 API 이전본만 대조했으므로 발행 설정/클라이언트의 일부 검사는 최신본입니다. 충돌/응답 유실 사례를 실제로 잡는 검사임을 확인합니다.
- 기존 확장 수명/재시작/결과 재보고32개 시나리오도 통과(총137개+발행 설정·상태·편집 저장·회원 데이터4개 검사 스크립트). 변경 TS/TSX lint 오류0, 경고69(기존 패턴 포함). npm run build 통과.
- 이 검사는 메모리 DB/전송 장애 모의 검사입니다. 실제 다중 Chrome 탭 및 실제 운영 DB 저장 검수와 구분합니다.
- 마지막 영수증1개만 유지하며 전체 요청 이력을 보관하지 않습니다. 이후 다른 저장이 있으면 이전 미확인 요청은409로 멈추고 최신 원고 비교가 필요합니다.
- 미확인 요청은 열린 화면 메모리에 보관합니다. 새로고침 후 요청 큐/실패 편집본 자동 복구 기능은 구현하지 않았습니다. 미저장/충돌 안내 때 내용을 복사해 보관하고 최신 원고를 다시 여는 절차가 필요합니다. 별도 로컬 백업 키는 자동 로드하지 않습니다.
- 배포 전에 열린 구 웹 화면 또는 버전 정보가 없는 구 캐시의 저장은409로 차단합니다. 내용을 먼저 보관한 뒤 웹 화면을 새로고침하고 최신 원고를 다시 열어야 합니다. 다른 프로젝트 SEO 저장소로의 쓰기 우회는503으로 차단하고 기존 목록 읽기 호환은 유지합니다.
