## 판단과 적용 범위

클로드의 `docs/SHARED_NAVER_ENGINE_PROPOSAL_2026-10-10.md`에서 제안한 실행 번호, 임대(lease), 오래된 결과 차단, 명시적 복구를 채택했습니다. v1.65의 공통화 A(각자 엔진+공통 검증 규칙)는 유지합니다. 네이버 입력 엔진을 BLOG의 CDP 엔진으로 교체하지 않았으며 BLOG/티스토리 코드는 수정하지 않았습니다.

제안서의 새 DB 열은 이번 구현에 필수가 아닙니다. 운영 `nba_posts.research_summary`가 jsonb임을 정보 스키마로 확인했고 `naver_execution`에 실행 정보를 보관합니다. 기존 검수·출처·발행 설정을 병합 보존합니다. 새로운 열·테이블·정책·환경변수·키를 만들거나 바꾸지 않습니다. SQL 파일은 프로그램 릴리스 메타데이터만 갱신합니다. 구조 변경이 필요해지는 후속 작업은 별도 승인 대상입니다.

공식 근거: [Supabase JSON 자료](https://supabase.com/docs/guides/database/json), [필터 사용](https://supabase.com/docs/reference/javascript/using-filters). JSON 경로와 `updated_at`을 함께 비교해 새 실행·동시 변경을 차단합니다.

## 서버 동작

- 새 확장 `supportsRuns:true`가 검수된 queued 원고를 선점하면 UUID 실행 번호와 연결 소유자(토큰 SHA-256), 단계·안내·done/total·시각·3분 임대를 저장합니다. 사용자·블로그·queued 상태·원고 시각을 모두 비교합니다. 토큰 원문은 실행 기록에 저장하지 않으며 연결 소유자 해시는 웹/확장 응답에서 제외합니다.
- 같은 연결의 publishing 원고가 이미 있으면 본문을 다시 보내지 않고 recovery 안내만 반환합니다. 선점 응답 유실로 두 번째 원고를 자동 입력하지 않습니다. 목록 조회 오류는 빈 대기로 오인하지 않고 503으로 알립니다.
- `/api/extension/status`가 heartbeat/stage/progress/waiting을 저장합니다. 현재 실행 번호·연결·회원·publishing·임대가 맞는 경우에만 갱신합니다. 최종 발행 단계에서 작성 단계로 돌아갈 수 없고 진행 수치/총수/안내 길이를 검사합니다. 같은 밀리초에서도 변경 시각을 증가시켜 비교 갱신이 유효하도록 합니다.
- `/finish`도 실행 번호·연결·회원·상태·변경 시각을 비교합니다. 만료 후라도 같은 실행의 실제 발행 결과는 보고할 수 있습니다. 이미 저장된 동일 결과의 응답 유실 재시도는 최초 시각을 보존합니다. 새 실행으로 바뀌거나 회원이 복구해 폐기한 실행의 늦은 보고는 RUN_SUPERSEDED로 거절합니다. 진행 보고와의 경쟁은 503 재시도로 처리합니다.
- `/api/posts/[id]/recovery`는 본인 원고, 현재 번호, publishing, 연결 만료, `confirmed:true`, 변경 시각이 모두 맞아야 draft로 복구합니다. 회원이 열린 글·게시글·예약 목록을 확인하는 체크가 필요합니다. 원문·이미지·검수 기록을 보존하고 자동 대기 등록/재입력/발행은 하지 않습니다.
- 일반 PUT의 실행 중 상태/결과/공개 범위 변경과 실행 중 삭제를 막습니다. 삭제 경쟁에서 0행은 성공으로 알리지 않습니다. 화면의 단일·일괄 삭제도 ACK 뒤에만 반영합니다.

## 확장과 보관함

- 새 작업의 단계·진행·결과에 선점 때 받은 runId를 그대로 전달합니다. 진행 쓰기는 순차 실행하며 실행 중 45초마다 생존을 확인합니다. 로그인 대기 중에는 주기 펌프에서도 연결을 확인합니다. pendingResult 보고가 생존 확인보다 먼저입니다.
- 새 편집기를 열기 전, 블록 입력 전, 이미지 다운로드 후, 실제 변형 명령 전, 최종 발행 직전에 서버 실행 권한을 확인합니다. 확인 실패 시 원고/이미지/입력 기록을 보존하고 안전하게 중지합니다.
- 주입된 편집기 명령에도 실행 번호·유효 시간을 전달합니다. DOM 대기 전후에 만료 또는 같은 프레임의 새 실행을 검사합니다. 유효 시간은 서버가 반환한 남은 시간에서 15초를 빼므로 PC 시계 차이에 의존하지 않습니다. 워커가 종료된 뒤 늦은 입력이 계속되는 것을 제한합니다.
- 이전/종료 실행의 결과와 checkpoint는 로컬 resultConflicts에 보존하고 activeTask와 분리합니다. 데이터 저장 성공 뒤에만 분리하며 서버의 새 실행을 덮어쓰지 않습니다. 이 기록은 자동 삭제하지 않습니다. 단순 DB/네트워크 오류·형식이 잘못된 ACK는 pendingResult를 유지합니다.
- 보관함은 queued/publishing 원고가 있을 때 10초마다 서버를 다시 조회합니다. 단계·횟수·마지막 확인 시각·실행 번호·연결 종료 후 복구를 표시합니다. 늦은 목록 응답은 새 저장 ACK 뒤의 화면을 덮어쓰지 않습니다. 서버가 빈 목록을 확인하면 과거 로컬 대기를 되살리지 않습니다. 흰색 화면·기존 배치를 유지합니다.
- 준비 전용 실행은 최종 버튼/예약 등록을 누르지 않습니다. 자동 발행 모드는 기존 계약을 유지합니다. 실제 회원 최종 발행은 이번 검수 범위에 포함하지 않습니다.

## 호환성과 한계

기존 runId 없는 로컬 작업/옛 확장의 기존 신규 원고 계약은 유지합니다. 이미 새 실행 기록이 있는 원고는 옛 확장이 선점할 수 없습니다. 옛 확장이 새 기능을 쓰는 것으로 표시하지 않습니다. 실행 번호 없는 기존 publishing 원고에는 만료 복구 버튼이 생기지 않습니다. 최신 ZIP 적용 이후 새 실행부터 전체 보호가 적용됩니다.

JSON 저장은 당장 필요한 상태/임대를 기존 데이터 구조에서 처리하는 선택입니다. 장기 실행 이력 전체 검색, 연결별 동시 선점의 DB 트랜잭션 보장, 대규모 진행 쿼리 인덱스는 별도 설계/스키마 승인 후속입니다. 이번 버전은 기존 한 원고의 queued 선점 경쟁을 막으며, 의도적으로 서로 다른 PC에서 서로 다른 원고를 처리하는 것까지 금지하지 않습니다.

네이버 실제 UI의 변경, 로그인 만료, 다운로드 실패를 모두 없앴다고 주장하지 않습니다. 오류가 생겨도 잘못된 새 입력·중복 발행·새 실행 결과 덮어쓰기를 막고 확인 가능한 기록을 남기는 데 초점을 두었습니다.

### 마지막 재개 시도와 다음 작업

추가로 별도 원고에서 ‘입력 중 탭 닫힘 + 서버 저장 후 결과 응답 1회 유실’을 검사하려 했습니다. 그러나 GUI 도구가 DevTools 콘솔 입력에 `window_not_focused`를 반환했고, `--restore-window`도 포커스를 얻지 못했습니다. 접근성 조회는 가능했지만 화면 캡처는 `screenshot_failed`였습니다. 추가 시험 명령의 실행을 확인할 수 없어 장애를 발생시키지 않았습니다. 회원 원고를 변경하거나 제품 오류로 판정하지 않습니다.

최종 읽기 전용 DB 확인에서 위 prepared 원고는 18/18·오류 없음·발행 URL/시각 없음으로 유지됐습니다. 기존 두 원고의 상태·본문/이미지 지문도 같습니다. 제목 `[검수용 v1.69] 입력 중 탭 닫힘·결과 응답 유실 확인`인 추가 원고는 생성되지 않았습니다. 릴리스 검사는 다시 실행해 실패0·경고0을 확인했습니다. 검수용 DevTools를 닫은 뒤 창 목록에서 검수 Chrome 창으로 돌아온 것을 확인했습니다.

다음 CLI는 준비된 원고9509d689…와 그 네이버 탭을 보존하고 다음 순서로 재개합니다.

1. 현재 Chrome 창·주소·에이전트 확장 ID·설치 v1.69·회원/블로그·activeTask/pendingResult 없음·서버 대기 없음과 GUI 입력 전달을 확인합니다. 도구가 포커스를 얻지 못하면 같은 키 입력을 반복하지 않습니다.
2. 본인 회원 API로 별도 검수 원고와 빈 네이버 탭을 만들고 prepare 설정 재조회·직접 검수 지문·전송 ACK를 확인합니다. 기존 준비 탭은 입력 대상으로 지정하지 않습니다.
3. 입력 기록의 `authoringCheckpoint.cursor`가 3 이상인 시점에 새 검수 탭만 닫습니다. `done/total`은 서버 진행 필드이며 로컬 checkpoint 필드와 혼동하지 않습니다. 종료 사유, 원고/이미지 보존, 닫힌 탭 참조 정리, 자동 재입력 없음까지 확인합니다.
4. 같은 검수 실행의 finish 응답만 서버 저장 성공 뒤 1회 유실시켜 pendingResult 보관→동일 runId 결과 재보고→서버 멱등 ACK→보관 결과 정리를 확인합니다. 입력 함수 호출은1회, 결과 보고는2회여야 하며 테스트 개입은 반드시 해제합니다. 운영 통신 전체를 끊지 않습니다.
5. 작업기 재시작/임대 만료 후 회원 확인 복구는 별도 시험으로 구분합니다. 새 유료 이미지 생성과 공개/예약 최종 발행은 해당 실행 범위의 승인을 확인한 후 진행합니다.
