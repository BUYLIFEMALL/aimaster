# 네이버 블로그 에이전트 개선 순서와 인수인계

작성일: 2026-10-10. 주인님 요청에 따라 기능 단위로 하나씩 검수·배포 후 진행합니다. **에이전트는 Codex 담당, BLOG는 클로드 담당**입니다. BLOG 코드·프로젝트 문서는 Codex 작업 범위에서 제외합니다. [클로드용 공용 인수인계](../../docs/BLOG_AUTOMATION_HANDOFF_2026-10-10.md), [상세 비교 근거](AUTOMATION_COMPARISON_2026-10-10.md).

## 1. 구현 순서

**최신 작업:** v1.68은4단계 이미지 장수/본문 자리·새 서버 원고 ID·개별 생성/교체/삭제 저장·실패 버퍼 보존을 보완했습니다. [검수·운영·남은 일](IMAGE_SAVE_2026-10-10.md). 신규9+기존75=84 및 관련 검사/빌드 통과, 운영 READY·DB/ZIP 검증 완료. v1.67 검수 지문 기준은 유지합니다. 다음 기능 단위는5단계 진행/실행 복구이며 실제 새 네이버 E2E는 별도입니다.

| 단계 | 목표·완료 기준 | 상태 |
|---|---|---|
| 1 | 결과 저장 확인: DB 오류/0행에 성공 응답 금지, 소유자·진행 상태 확인, 같은 결과 재보고 시 시각 보존, 확장은 올바른 저장 응답에만 pendingResult 정리 | v1.64 운영 배포·릴리스 검증 완료 |
| 2 | 발행 전 준비 흐름: 최종 검수한 원고의 고정본 전달 → 입력·이미지·설정 검증 → 준비 완료를 독립 상태로 표시. 자동 최종 발행 경로와 준비만 하는 경로를 명확히 구분 | v1.66 모드/상태 분리 운영 배포·ZIP/DB 검증 완료, 실제 E2E와 고정본 보장 후속 |
| 3 | 검수 기준 연결: FAIL/UNKNOWN 원고 전송 차단 또는 명시적인 재검수, 검수 후 수정 시 무효화; 최근 본인 제목을 실제 전달, 윤문 URL·수치 보존, 모델별 지원 파라미터 확인 | v1.67 구현·검사 통과, 운영 READY·DB/ZIP 검증 완료 |
| 4 | 이미지·저장 일관성: 선택 장수대로 다른 장면 계획·생성·배치, 개별 추가/삭제 자동 저장, 저장 배지 실제 응답 연결, 임시 ID→서버 ID 중복 저장 방지 | v1.68 구현·검사/빌드 통과, 운영 READY·DB/ZIP 검증 완료; 다중 탭/응답 유실 멱등 후속 |
| 5 | 진행·복구 관측: 현재 빈 응답인 progress/stage/waiting 경로 보완, 원고/실행/PC 상태 구분, 선점 응답 유실·장시간 단절 복구, 필요한 실제 경계 검사 | 미착수 |

각 단계는 독립 릴리스합니다. v1.66부터 준비 완료(prepared)와 실제 발행 완료(published)를 구분합니다. 기존 자동 발행은 유지하며 원고별로 준비만 하는 방식을 명시적으로 고릅니다. 주인님의 BLOG 목표도 준비까지 자동 진행하고 최종 발행은 회원이 하는 흐름이며 클로드가 별도로 구현합니다. 검수한 고정본·실행 번호/임대·실제 E2E는 모드 구현만으로 해결됐다고 보고하지 않습니다.

## 2. 1단계 v1.64 구현

- `src/app/api/extension/finish/route.ts`: 토큰·현재 권한 확인 후 `id + user_id + status=publishing` 조건으로 결과 갱신, `.select(...).maybeSingle()`로 실제 반영 확인. Supabase가 error를 반환하거나 예외가 나면 503, 원고 없음/타인 원고는 404, 취소/대기/상이한 완료 결과는 409. 응답은 모두 no-store이며 내부 DB 오류 내용을 노출하지 않습니다.
- 이미 저장된 동일 결과는 성공으로 확인하되 최초 `published_at/updated_at`을 바꾸지 않습니다. 뒤늦은 실패가 성공을 덮어쓰지 않습니다. 예약 목록 등록 확인의 URL 없음도 기존 계약대로 허용하며 미래 실제 게시와 구분합니다.
- `extension/background.js /result`: `success=true`, `persisted=true`, 같은 taskId, 같은 published/failed 상태를 모두 확인한 뒤 로컬 결과를 정리합니다. HTTP200이라도 응답이 다르면 pendingResult/activeTask를 보존하고 서버 보고만 재시도합니다. 확인된 성공을 입력 실패로 바꾸거나 자동 재발행하지 않습니다.
- 서버는 옛 확장용 success/message 필드를 유지합니다. 새 확장은 새 저장 확인 필드가 필요하므로 서버 배포 후 최신 ZIP을 적용합니다.
- 스키마·환경변수·API 키·회원 원고 내용은 바꾸지 않습니다. SQL은 프로그램 릴리스 메타데이터만 변경합니다.

## 3. 검사와 운영 결과

- 실제 TypeScript route를 변환해 실행하는 `test:extension-results` 14개: DB 반환 오류/예외/0행, 토큰 오류, 소유권/권한, 취소 경쟁, 잘못된 요청, 동일 결과 재보고·시각 보존, 예약 URL 없음, 서로 다른 결과 충돌.
- 실제 background worker의 `test:extension-tabs` 21개: 기존 탭/재시작 16개 + 잘못된 HTTP200 저장 확인4개 + DB503 결과 보존1개. 보고 재시도 때 화면 입력/탭 생성/최종 클릭 없음 확인.
- 기존 `test:extension`, `test:publishing`, `test:edit-save` 통과. 이전 route에 새 검사를 실행하면 실패하므로 구현 복제만 확인하는 검사가 아닙니다.
- 운영 배포·라이브 ZIP/DB 검증·원고 지문 보존 결과는 아래 항목에 기록했습니다. 실제 회원 발행으로 DB 장애를 유발하는 시험은 하지 않았습니다.

## 4. 다음 작업자가 알아둘 제한

- 현재 taskId는 원고 ID입니다. 취소 후 같은 원고를 다시 publishing으로 만든 경우 아주 늦은 옛 실행의 결과까지 구별하는 실행 ID는 아직 없습니다. 새 실행 ID/원고 버전 고정·선점 임대는 2·5단계 설계 항목이며 스키마 변경 필요 시 사전 승인 대상입니다.
- 404/409는 pendingResult 보존과 오류 안내로 안전 중지합니다. 자동으로 원고 상태를 덮어쓰거나 보관 결과를 삭제하지 않습니다. 전용 충돌 해결 UI와 재시도 지연 정책은 후속입니다.
- 기존 v1.63의 실제 입력 중 탭 닫힘 검사, 생성 검수 연결·이미지 장수·자동 저장 문제는 이 릴리스에서 해결하지 않았습니다.
- 본인 API/계정만 사용. 실제 입력 검사는 본인 계정의 별도 빈 편집기에서 하며 최종 발행은 별도 승인 범위를 따릅니다.

공식 절차: [AI 에이전트 기반 자율 개발·검수·배포](../../docs/AI_AGENT_AUTONOMOUS_DEV_WORKFLOW.md). 배포 후 다른 PC는 ZIP 재다운로드 → 기존 폴더 덮어쓰기 → `chrome://extensions` 새로고침이 필요합니다.
