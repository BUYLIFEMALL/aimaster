## 문제와 범위

기존 `/api/upload-image`는 공용 공개 버킷 URL을 반환한다. 개인 사진 후기에는 그대로 재사용하지 않는다. 새 `nba-private-photos` 비공개 저장소에 `회원 UUID/파일 UUID.확장자`로 저장하고 서버에서 회원/이용 권한과 원래 업로드 시각을 확인한다. 저장소 생성·권한 정책은 별도 제안서를 준비하고 **적용 승인을 받은 뒤에만 실행**한다. 기존 공개 버킷·기존 업로드·회원 키/환경변수는 변경하지 않는다.

| 순서 | 구현 | 검수 기준 |
|---|---|---|
| 1 | POST `/api/photos` 업로드, POST `/api/photos/resolve` 조회 | 로그인·이용 권한, 본인 경로, JPEG/PNG/WebP 서명과 MIME·4MB 제한, 저장소 비공개 확인, 서버 오류 노출 방지 |
| 2 | 저장 ID와 임시 미리보기 주소 분리 | DB에는 `storagePath`를 식별자로 사용. 임시 URL은 저장/검수 지문에 섞지 않음. 사진 원래 생성일 +30일, 임시 주소는 최대 5분이며 남은 보관 시간보다 짧게 |
| 3 | 확장 작업 전달 직전 사진 주소 발급, 다운로드 직전 재발급 | 원고 검수 후, 작업 선점 전에 회원 경로·원본 만료 확인. 실패하면 queued 유지. 긴 원고 입력 중에는 회원·실행·연결 사진을 확인해 갱신. DB 원고·검수 지문은 변경하지 않음. 기존 URL 방식은 호환 |
| 4 | 기존 일일 정리 경로에 새 버킷 정리 연결 | 미연결 업로드도 30일 만료. 페이지를 끝까지 읽고 삭제는 수집 후 실행해 건너뛰기 방지. dry=1은 삭제 0. 새 사진은 업로드 원시각 기준 |
| 5 | 무료 모의 회귀·타입 검사·로컬 빌드·인수인계 | 타 회원·경로 위조·만료·서명 실패·공개 버킷 거부·다중 페이지·확장 선점 전 실패/성공 검증. 운영 검수와 구분 |

## 경계와 다음 단계

- BLC-02에서 사진 최대 6장 입력/대표/순서/캡션 UI를 연결한다. 이번에는 저장 기반과 확장 전달 경로만 준비한다.
- BLC-03의 사진 AI 분석·후기 생성, BLC-04의 실제 편집기/저장 연결은 아직 구현하지 않는다.
- 새 버킷은 직접 브라우저 Storage 접근을 차단하고 인증된 앱 서버를 통해 접근한다. 기존 전역 허용 Storage 정책에 섞이지 않도록 새 버킷 전용 제한 정책을 제안한다.
- 원본을 덮어쓰거나 서버에서 복사해 수명을 연장하는 API를 만들지 않는다. 기존 콘텐츠 이관이 필요하면 최초 생성일을 보존하는 별도 설계가 필요하다.
- 임시 주소는 가진 사람이 만료 전까지 접근할 수 있는 권한이다. 서버 응답 no-store, 짧은 수명, 공유 금지. 직접 접근은 주소 만료/원본 삭제로 차단된다.
