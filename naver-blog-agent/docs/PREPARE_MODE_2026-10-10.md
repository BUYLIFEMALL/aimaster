# v1.66 — 발행 전 준비와 최종 발행 구분

주인님 지시에 따라 개선 2단계의 진행 방식·결과 상태 분리를 구현합니다. 에이전트는 Codex, BLOG는 클로드 담당입니다. BLOG 폴더는 수정하지 않습니다. 클로드의 공통화 제안 A(각자 입력기 유지·같은 규칙 검사)를 유지하며 에이전트의 문서 전체·이미지 이름·인용구·링크 카드 출처 검증을 그대로 사용합니다.

## 회원 사용 흐름

1. 서버에 저장된 원고의 **네이버 발행 설정 → 확장 진행 방식**에서 `발행 전 준비까지만` 또는 `최종 발행까지 자동 진행`을 고르고 설정을 저장합니다. 저장 전 전송은 차단됩니다. 예전 원고는 기존 자동 발행을 유지하므로 준비 방식을 원하는 원고는 직접 선택·저장합니다.
2. 원고를 작업 대기에 보내면 최신 확장이 본인 블로그·빈 편집기를 확인하고 제목·본문·이미지를 입력·검증한 뒤 카테고리·태그·공개 범위·예약 설정을 적용합니다.
3. 준비 방식은 설정 적용과 로그인 확인 후 멈춥니다. 최종 발행 버튼 및 예약 등록을 실행하지 않습니다. 보관함에 **발행 전 준비 완료**가 표시되고 확장 연결 화면의 **준비된 원고 열기**로 마지막 준비 탭을 열 수 있습니다. 회원이 실제 화면을 검토하고 최종 버튼을 직접 누릅니다.
4. 자동 발행 방식은 기존 최종 클릭·결과 확인 흐름을 유지합니다. 준비 완료 탭은 다음 작업에서 재사용·초기화하지 않고 새 탭을 사용합니다. 탭을 닫으면 보호 목록에서 제외합니다.

준비 완료는 네이버 게시 성공·예약 등록·DB에 네이버 임시글 저장 완료를 의미하지 않습니다. 실제 원고는 열린 회원 Chrome 탭에 있습니다. 탭을 닫거나 페이지를 이동하면 원고를 잃을 수 있으므로 최종 검토 전 열린 탭을 유지합니다. 회원이 수동 최종 발행한 결과는 이번에 자동 수집하지 않으므로 웹 상태는 준비 완료로 남을 수 있습니다.

## 구현·호환성

- `research_summary.naver_publishing.execution_mode`에 기존 블로그 ID와 함께 prepare/publish를 보관합니다. 별도 DB 칸·상태 제약 추가 없음. 잘못된 명시값·다른 블로그에 저장된 진행 방식은 자동 발행으로 폴백하지 않습니다.
- `/api/extension/task`는 새 확장의 `supportsPrepare:true`를 확인합니다. 옛 확장의 준비 원고 수신은 409로 차단하고 queued 상태를 유지합니다. 자동 발행 원고는 옛 계약을 유지합니다. task.type=prepare/publish, payload.executionMode를 전달합니다.
- worker는 기존 입력기 검증과 설정 적용 후 stage=prepared를 선보관하고 `{prepared:true,published:false}`를 보고합니다. `/finish`는 회원·권한·소유권·저장한 진행 방식·진행 상태를 확인하여 status=prepared, post_url/published_at=null로 기록합니다. prepared와 success/error/postUrl 동시 보고, 준비 원고의 발행 성공 주장은 거절합니다.
- 기존 DB ACK 확인과 같은 결과 재보고 시각 보존을 준비 결과에도 적용합니다. HTTP503·잘못된 ACK·통신 실패는 결과를 보존하고 보고만 재시도합니다. prepared 체크포인트에서 재시작해도 입력·최종 클릭·예약 확인은 실행하지 않습니다.
- `preparedEditorTabs`와 `lastPrepared`를 확장 로컬 저장소에 보관하고 다음 작업이 해당 탭을 덮어쓰지 않도록 제외합니다. pendingResult 복구 시 서버 ACK 이전에 탭 보호도 다시 저장합니다. `openPrepared`는 같은 연결 블로그·기존 유효 편집기를 확인하고 활성화만 합니다.
- 웹 POST/PUT 요청으로 prepared 상태를 직접 만들 수 없습니다. 준비 뒤 제목·본문·태그·이미지·공개 범위를 수정하거나 발행 설정을 다시 저장하면 draft로 되돌려 기존 준비 표시를 무효화합니다. 이미 열린 네이버 탭을 자동으로 수정하지 않으며 재전송하여 새로 준비합니다.
- UI는 기존 흰색 설정 카드·명시적 label·저장 중 비활성화·원고 변경 시 폼 재생성·비동기 취소 처리를 유지합니다. 새 전역 상태나 라이브러리를 추가하지 않았습니다.

## 자동 검수

- 실제 TypeScript finish route 모의 DB 검사 16개: 준비 결과 저장·중복 ACK·모드 불일치·모순된 발행 주장과 기존 오류/소유권/경쟁 처리.
- 실제 background worker 모의 Chrome 검사 25개: 준비에서 설정 패널을 여는 클릭 1회만 실행, 최종 클릭·예약 등록 없음; 다음 작업의 준비 탭 보존; 설정 실패 시 준비 성공 금지; 재시작·DB503·보호 기록 복구에서 보고만 재시도. 기존 탭 닫힘·발행 결과 보존도 통과.
- editor 판정 4개·양쪽 실제 입력 core 공통 규칙 14개 통과. 위 번호형 검사 합계 59개이며 연결·발행 설정·저장 상태·편집 저장 검사는 별도 통과했습니다.
- task route 실제 실행으로 옛 확장 차단과 queued 유지, 새 확장의 prepare 수신/선점 확인. 설정 API 저장·재조회, 원본 연구자료 보존·잘못된 값 거절·prepared 설정 수정 무효화 확인. POST/PUT 허위 준비 상태 거절·준비 후 편집 무효화 확인.
- JS 문법·로컬 프로덕션 빌드·타입 검사 통과. 운영 배포 증거는 완료 후 아래에 기록합니다.

## 검수 한계와 후속 순서

이번 검사는 모의 Chrome/DB 및 실제 route/core 실행입니다. **새 준비 흐름의 실제 로그인 웹→확장→네이버 전체 E2E는 미실행**입니다. 최종 발행·회원 원고 변경·유료 API 호출·키/환경변수/스키마 변경도 실행하지 않습니다. 최신 ZIP을 PC에 적용한 후 본인 계정의 별도 빈 글에서 prepare(now/reserve) 입력·설정·준비 표시·탭 열기·다음 글 탭 보호를 확인해야 합니다. 최종 버튼은 직접 실행 승인 범위를 따릅니다.

다음 기능 단위는 3단계 생성 검수 기준·최근 본인 제목·윤문 URL/수치·모델 파라미터 연결입니다. 준비 모드 자체의 구현과 **검수한 원고 고정본 보장**은 구분합니다. taskId가 원고 ID이므로 새 실행/버전 번호가 없으며, 웹의 기존 POST/PUT는 대기·입력 중 내용 수정을 완전히 차단하지 않습니다. 실행 고정본·선점 임대는 별도 설계이며 DB 칸 추가는 사전 승인 대상입니다.

4단계에서는 기존 원고 저장·전송 화면의 서버 응답 확인을 함께 처리합니다. 현재 생성 화면의 전송/임시보관 및 보관함 단일·일괄 전송은 응답 확인 전에 로컬 상태/성공 안내를 갱신하는 기존 문제가 있습니다. 이번에 고쳤다고 보고하지 않습니다. 개별 이미지 자동 저장·임시 ID 중복 저장도 같은 후속 범위입니다.

배포 후 설치된 확장은 **최신 ZIP 재다운로드 → 기존 폴더 덮어쓰기 → chrome://extensions 새로고침**, 웹 페이지 새로고침이 필요합니다.
