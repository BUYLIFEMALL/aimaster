# v1.67 검수한 원고와 확장 전송 연결

작성: 2026-10-10. 담당 Codex. BLOG는 클로드 담당이며 BLOG 코드/문서를 수정하지 않습니다. 공통화 A(각자 입력 엔진 유지+같은 규칙 검사)를 유지합니다.

## 사용 흐름

1. 본인 API 키와 본인 블로그를 등록하고 원고를 생성합니다. 서버가 AI 검수 판정과 원고를 함께 저장하고 실제 서버 ID를 돌려줍니다.
2. 제목·본문·태그·블로그·이미지 전체를 최종 저장합니다. 생성 화면/보관함 발행 설정의 「최종 원고 검수」는 화면 원고와 서버 저장본을 비교합니다. 저장본이 다르면 전송할 수 없습니다.
3. 현재 저장본에 대한 AI PASS는 전송을 허용합니다. WARN/FAIL/UNKNOWN/미검수/수정 후 검수 무효는 회원이 사실·수치·출처·이미지·표현을 확인하고 필요 시 수정·저장한 뒤 체크하여 「직접 검수 완료 기록」을 누릅니다. 직접 검수는 CONFIRMED이며 AI PASS로 바꾸지 않습니다. 이전 AI 경고/실패 판정도 보존·표시합니다.
4. 발행 설정을 저장하고 「네이버 확장 작업 대기에 전송」합니다. v1.66의 prepare는 최종 클릭 없이 준비까지, publish는 기존 자동 발행 경로입니다. 최종 발행 권한·동작은 이 검수 기능에서 추가하지 않습니다.
5. 제목·본문·태그·블로그·이미지가 바뀌면 기존 검수 지문과 달라져 다시 검수해야 합니다. queued/publishing 중 일반 저장 API의 내용 변경은 차단합니다. 대기 취소 후 수정합니다. 이미 처리 중인 입력을 즉시 취소/회수하는 기능이나 실행 ID 보장은 이번 범위가 아닙니다.

## 구현과 판단

- `postReviewSnapshot.ts`: 브라우저/서버가 동일한 정렬 JSON을 사용합니다. 제목·본문·태그·블로그·이미지 객체 전체를 비교합니다. 배열 순서/내용 차이는 반영하고 객체 키 순서만 같게 정리합니다.
- `postReview.ts`: SHA256 지문·검수 상태 계산, 기존 JSON 보존, 직접 검수 시 원래 AI 판정 보존. 클라이언트가 보낸 reviewStatus/research_summary를 통과 기록으로 신뢰하지 않습니다.
- `POST /api/generate`: 회원 소유 블로그/최근 제목 10개 실제 조회 후 파이프라인에 전달, AI 판정과 최종 원고를 기존 `research_summary`에 함께 저장합니다. 저장 실패에도 생성 결과를 돌려주되 saved=false/saveError를 표시하고 직접 검수가 필요합니다. 기존 JSON 칸 활용이며 스키마 변경 없음.
- `GET/POST /api/posts/[id]/review`: 회원·사용 권한·원고 소유자 확인. 명시적 confirmed와 현재 지문, 상태 및 updated_at 조건으로 승인합니다. 동시 편집/대기 전환 409, DB 실패 503, 모든 응답 no-store.
- posts POST/PUT와 extension task 모두 유효한 현재 검수를 검사합니다. task 선점과 저장은 소유자/상태/updated_at 조건을 사용합니다. 검수된 원고를 정상 API로 대기·입력 중 덮어쓰지 못하게 합니다. 원고 전체를 별도 불변 저장소에 복제한 구조는 아닙니다.
- 생성 화면과 보관함은 서버가 실제 저장/대기 등록을 확인한 뒤 성공을 표시합니다. 일괄 전송은 성공/실패 개수를 각각 표시하고 성공한 행만 로컬 상태를 갱신합니다. 생성 서버 ID 재사용으로 2차 중복 생성 저장을 줄입니다. 오프라인 임시 보관은 로컬 백업임을 구분합니다.
- 최근 제목은 본인/해당 블로그 DB 값만 사용합니다. 과거에 작성한 제목은 사실대로 전달하고 생성의 현재 연도 지시는 유지합니다. reviewer에 최종 제목도 전달합니다. 윤문은 URL 또는 수치가 달라지는 편집을 거절합니다.
- 선택한 공급사에 본인 키가 없으면 등록 안내만 합니다. 다른 공급사/모델이나 운영자 키로 치환하지 않습니다. OpenAI는 기존 gpt-4 계열에만 temperature를 보내고 나머지는 생략합니다. 17개 선택 모델의 ID/요청 전달 검사는 모의 검사이며 실제 공급사별 호출 성공을 보장하지 않습니다.

공식 참고: [Supabase update](https://supabase.com/docs/reference/javascript/update), [OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning). 매 요청의 지원 파라미터는 실제 사용 모델 공식 문서와 대조합니다. 새 유료 호출/키 등록 시험은 이번에 하지 않았습니다.

## 검수 증거와 한계

- 신규 route/키/윤문 등 12개 + 실제 화면 처리 함수 실행 4개 = 신규16개 통과. 클라이언트가 올바른 지문까지 붙인 위조 PASS도 저장 승인되지 않습니다. 직접 검수는 AI FAIL을 보존합니다. 수정/소유자/권한/DB 실패/동시 편집과 task 선점 경계를 검사합니다.
- 기존 결과 route16, worker25, editor4, 양쪽 core14 포함 총75개 시나리오 통과. Node는 worker 파일을 1개 테스트로 집계하므로 출력51개는 내부 worker25개를 포함한 것입니다.
- 연결·저장 상태·말투/문체32조합·선택 모델17개·발행 설정/소유권·편집 저장·키 선택 검사 통과. `npm run build` 타입/컴파일 통과. TSX 수정은 기존 흰색 화면, 취소/전환 시 응답 무효화, 저장본 불일치 시 차단을 확인했습니다.
- 실제 네이버 새 prepare/검수 화면 E2E는 미실행입니다. 현재 공유 Chrome에서 다른 CLI/사용자 티스토리 작업이 진행되고 있어 화면을 계속 전환하지 않았습니다. 키 입력의 실제 대상/효과도 입증되지 않았으므로 실제 사용자 검수 완료를 주장하지 않습니다. 공개/예약 발행·유료 AI 호출·회원 원고 수정 없음.
- 설치 PC의 v1.67 ZIP 적용은 별도입니다. ZIP 재다운로드→기존 폴더 덮어쓰기→chrome://extensions 새로고침. 옛 원고에 검수가 없으면 묵시적 PASS 없이 직접 검수해야 합니다. 과거에 대기 등록한 미검수 원고도 작업 수신을 거절하며 대기 취소/직접 검수 후 다시 전송합니다.

## 남은 일과 다음 순서

1. 4단계 이미지·저장: 이미지 선택 장수와 현재 2개 프롬프트 제한 일치, 개별 생성/추가/삭제 자동 저장, 이미지 0개 삭제 후 계획 이미지 복귀 문제, 편집 저장 배지/서버 ID의 모든 경로 일관성.
2. 5단계 진행·복구: progress/stage/waiting 실제 저장·표시, 실행 번호·임대·선점 응답 유실. 현재 taskId는 원고 ID이므로 취소→빠른 재전송 시 아주 늦은 옛 실행 결과까지 구분하지 못합니다. 필요 시 DB 스키마 변경은 사전 승인 대상이며 BLOG의 승인으로 대체하지 않습니다.
3. 본인 계정의 별도 빈 네이버 편집기에서 수정 후 재검수→prepare→설정/이미지/본문 확인→준비 탭 보존, 입력 중 탭 닫힘을 실제 검수합니다. 회원 대신 최종 발행하지 않습니다.
