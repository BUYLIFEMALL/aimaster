# v1.75 Chrome 복원 탭 보호와 실제 이미지 검수

2026-10-11, Codex. 에이전트만 수정하며 BLOG는 클로드 담당입니다.

## 재현·수정

- 증상: Chrome 재시작 후 기존 준비 편집기의 탭 ID가 바뀌면 preparedEditorTabs의 옛 ID로 보호하지 못하고, freshEditor 작업이 복원된 탭을 글쓰기 URL로 다시 이동시킬 수 있었습니다. 실제 보호 원고를 훼손하는 시험은 실행하지 않았습니다.
- 원인: 새 작업도 전체 탭에서 기존 편집기를 찾고 freshEditor일 때 URL을 갱신했습니다. 수동 작성 중인 미등록 편집기도 같은 위험이 있었습니다.
- 해결: extension/background.js의 editorTab에서 freshEditor 작업은 기존 탭 조회·선택·이동 없이 새 탭을 생성합니다. 회원의 명시적 세션 재연결은 기존 편집기 재사용 동작을 유지합니다. 기존 탭/입력 기록을 삭제하지 않습니다.
- 검사: 실제 worker를 VM 브라우저로 실행하는 회귀2개 추가. 수정 전 복원된 탭2가 선택돼 실패했고, 수정 후 탭 ID 변경/미등록 편집기/읽기 화면 보호와 새 탭 생성 통과. 확장 수명 검사34개 전체 통과. 실제 Chrome 재시작 후 새 prepare 확인은 후속이며 자동 검사와 구분합니다.
- 대시보드 다운로드 버전의 고정 v1.8.0을 APP_VERSION으로 연결했습니다. v1.75 웹/확장/다운로드/DB 릴리스 정보가 같은 값을 사용합니다. 서버 API·스키마·환경변수·키 변경 없음.

## 현재 화면 제어 제한과 재개

- 실제 Chrome은 Orca computer의 접근성 트리→최신 요소 번호→click/set-value/Select→재관찰로 검사합니다. 회원 화면과 Supabase 소유 원고 상태를 대조하며 입력 호출 성공만으로 결과 성공을 판단하지 않습니다. Node 회귀·빌드/타입과 실제 화면 검수, Vercel 배포/ZIP·로그 검수를 구분합니다.
- Windows capabilities는windows.focus=false, surfaces.menus/dialogs=false입니다. 준비 모드 select와 북마크 메뉴 click은actionUnsupported→synthetic/unverified이고 값 변경이 확인되지 않았습니다. 현재 새5장 원고의 진행 방식은publish 그대로이고 전송/최종 발행은 실행하지 않았습니다. 값이prepare로 실제 저장됐는지 확인하기 전에는 전송하지 않습니다.
- 주인님께 검수용Chrome 창을 앞으로 가져와 잠시 그대로 두는 동작만 요청했습니다. 비밀번호/API 키/토큰 요구 없음. 임시 장수 북마크[검수용 v1.74] 이미지 장수 제어 - 삭제 예정은 아직1개 남아 있고, 메뉴가 동작하면 종료 전 삭제/검색0개를 확인합니다. 북마크는count select의change 이벤트만 보내며 서버 호출·계정/키 변경이 없습니다.
