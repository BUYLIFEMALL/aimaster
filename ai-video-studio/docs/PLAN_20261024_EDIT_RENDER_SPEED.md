## 4. 개선 플랜 (단계별, 승인 필요)
**1단계 — 진단·안내 (v1.21에 묶음, 빌드 추가 0회)**
- ① 진행 막대에 **남은 예상 시간** 표시(라이브러리 `renderEstimatedTime` 사용). 20초 뒤 예상이 3분을 넘으면 「이 PC에서는 약 N분 걸립니다」 안내.
- ② **진단 기록**: 렌더 끝(또는 멈춤)에 `renderedFrames`·`encodedFrames`·걸린 시간·하드웨어 설정을 콘솔에 한 줄로 남김 → 장면 그리기와 인코딩 중 어디서 막히는지 구분.
- ③ **하드웨어 가속 바꿔 보기**: 주소 끝 `?render=software`면 `hardwareAcceleration: "prefer-software"`로 렌더(회원 화면은 그대로, 시험용).
- 맥미니 요청 절차: 같은 영상으로 기본값·`?render=software` 두 번 재기 → 결과 기록.
**2단계 — 원인 확정 뒤 (별도 승인)**
- 인코딩이 원인이면: 맥에서 자동으로 소프트웨어 인코딩, 또는 「⚡ 내 PC 렌더러로 만들기」 권장 버튼(이미 있는 `compress`로는 자막·음악 합성이 안 되어 새 명령 필요 — 큰 작업).
- 글꼴: 자막 글자만 받기(첫 화면 121건 → 몇 건)는 첫 화면 속도 개선으로 따로 다룸(작은 작업).

## 8. 2단계 플랜 (2026-10-25, [역할: video] Claude Code(윈도우) `claude-win-video`) — 주인님 승인 대기
- **§7로 좁혀진 원인**: 렌더 때 `@remotion/media` `<Video>`는 장면마다 원본 영상을 인터넷 주소에서 구간 요청(`mediabunny` `UrlSource`)으로 받아, 키프레임부터 다시 풀어(`VideoSampleSink`, 브라우저 디코더) 그린다. 맥은 CPU를 거의 안 쓰고 장면마다 약 20초 기다림 → 후보는 ⓐ 원본 구간 받기 대기(서명 주소 구간 요청이 맥 크롬에서 느림) ⓑ 맥(인텔) 크롬 영상 디코더가 장면을 늦게 내놓음, 둘뿐이다. 윈도우는 같은 영상 5.3초라 코드 자체 문제는 아니다.
- **v1.22 내용(빌드 1회)**
  1. **원본 미리 받기(기본값으로)**: 「영상 만들기」를 누르면 클립 원본을 먼저 통째로 받아(5초 클립 1~3MB) 내 PC 메모리 주소(`blob:`)로 바꿔 렌더한다 → ⓐ를 없앤다. 받는 동안 「영상 받는 중 N/M」 표시. 예전 방식은 `?render=remote`로 비교용으로 남긴다. 윈도우에서 먼저 `blob:` 주소가 구간 요청까지 되는지 로컬 시험(무료)으로 확인하고, 안 되면 이 항목은 빼고 2만 낸다.
  2. **자세한 진단(`?render=verbose`)**: Remotion `logLevel: "verbose"`로 장면 추출·키프레임 묶음 로그를 남기고, 진단 줄에 「미리 받기 걸린 시간」「장면 1장 평균 시간」을 더한다(`software`와 함께 쓸 수 있게 `?render=software,verbose`).
  3. **「멈추는 중…」 바로 표시**: 멈추기를 누르면 즉시 버튼을 「멈추는 중…」으로 바꾸고 다시 누르지 못하게 한다(실제 중단은 장면 하나가 끝날 때 — 라이브러리 방식).
  4. **남은 시간 계산 수정 `d8c0aed57`**(미배포 대기, 주인님 결정대로 함께).
- **맥미니 측정(무료)**: 기본(미리 받기) 1회 + `?render=remote,verbose` 1회. 미리 받기로 빨라지면 ⓐ 확정·끝. 그대로면 ⓑ → 3단계 후보: 맥은 「⚡ 내 PC 렌더러」로 안내하거나 원본을 내 PC 렌더러로 「형식 맞추기」(`normalize`, 1.30에 있음) 뒤 렌더.
