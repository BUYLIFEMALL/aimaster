# 개발 플랜 — WebCodecs 하드웨어 가속 (2026-10-23, Claude Code 맥미니 · 주인님 승인 「진행해」, v1.20 예정)

## 문제
엔진(ffmpeg.wasm 단일 스레드)이 원본(휴대폰 1080p·4K)을 소프트웨어로 해석·축소하는 일을 사다리 시도마다 반복한다(잔점 4초 영상 4번 시도 92초, v1.19 실검수).

## 방법
- 영상 풀기·해석: `mediabunny` 1.61.3(MPL-2.0, MP4·MOV·WebM, WebCodecs 사용)로 **처음 한 번만**, 구간·fps에 맞춰 프레임을 뽑고 브라우저가 목표 가로폭으로 줄임.
- 엔진에는 줄인 프레임(압축 없음)만 넘겨 색상표·GIF(필터 그대로). 사다리 다음 단계는 그 프레임에서 조금 더 줄이거나 fps만 낮춤.
- 예상 메모리 한도(약 256MB) 초과·WebCodecs 없음(사파리 일부·파이어폭스)·지원 안 되는 코덱·실패 → 지금 방식 자동 전환. 멀티스레드 엔진은 쓰지 않음(「상세페이지로」 창 연결 유지).

## 순서
1. **측정(무료, 맥미니 크롬)**: 같은 내용을 1080p·560px MP4로 만들어 A(지금 방식, 1080p) · B(하드웨어 해석으로 560px·40fps 프레임 뽑기) · C(지금 방식, 560px 원본 = 작은 프레임에서 엔진 비용 근사)를 잰다. **B + C ≤ A의 절반이 아니면 중단**하고 결과만 기록.
2. 윈도우에 `npm install mediabunny@1.61.3` 요청.
3. 구현: `lib/fastFrames.ts`, `components/ConverterWorkspace.tsx`, 설정 패널 「⚡ 하드웨어 가속」 표시.
4. 검수: 순수 함수 시험·tsc·eslint, 배포 뒤 맥미니 크롬 시간 비교·결과 크기·프레임 수·화질 나란히 비교·세로 영상 회전·구간·fps 단계·ZIP·상세페이지로 회귀.
5. 배포: 큰 소스 변경(예외 ①) v1.20, 빌드 1회(수정 시 1회 더) — 그때 사전 승인.

## 비용
측정·구현 없음. 배포 Vercel 빌드 1~2회. 회원 비용 없음(브라우저 안 변환).

## ① 측정 결과 (2026-10-23 19~20시, 맥미니 크롬·운영 v1.19·시험 계정) — **기준 미달, 구현 중단**
- 시험 영상: `mediabunny` `Output`+`CanvasSource`로 장면을 하나씩 그려 만든 MP4 — 1080p(14.9MB)·560×316(3.2MB), 둘 다 정확히 10초·300장, 같은 내용(그라데이션·도형 12개·글자·잔점 400개). 실시간 녹화(`MediaRecorder`)는 창이 가려지면 그리기가 밀려 길이가 줄어 버림(4.88초) — 측정용 영상은 이 방식으로 만들 것.
- 결과(설정 560px·40fps):
  - A 지금 방식 1080p: 157초(시도 1 = 102초, 시도 2 = 54초), 5.31MB
  - B 하드웨어 해석 프레임 뽑기 1080p → 560×315·400장: 작업 화면 8.5·9.5초, 가벼운 화면 5.4·5.5초. 압축 없는 RGBA 268MB(구현했다면 3바이트 이하로 줄여야 함)
  - C 지금 방식 560px 원본: 103초(시도 1 = 70초, 시도 2 = 33초), 5.38MB
- 판정: 새 방식 예상 B + C ≈ 112초 = A의 71% → 기준(≤ 50%) 미달. 1080p 해석 비용은 시도당 약 20~30초뿐이고, 나머지 대부분은 엔진의 색상표 만들기·디더링(단일 스레드).
- 다음 후보(미검토): 멀티스레드 엔진(COOP → 「상세페이지로」 연결 방식 변경 필요), 디더링 가볍게, JS GIF 인코더. 4K 원본은 해석 비중이 커서 이득이 더 클 수 있음.
