# BLC-09 구간별 저장·이어쓰기 개발 플랜 (2026-10-22, Claude Code 윈도우 — 승인 대기)

> 기준: `docs/BLOG_CONSOLIDATION_TASKS.md` BLC-09 「작업실 → SEO: 구간별 저장·이어쓰기·최종본 검수 지문 — 긴 글 생성 중 실패해도 처음부터 재생성/재과금하지 않게 함. 확인: 구간 중지/이어쓰기, 동시 수정 충돌, 본문 변경 후 검수 무효화, 실패 구간만 재실행」.
> 원본: `blog-workroom/src/lib/actions/write.ts`(outline → section 순차 호출·구간마다 즉시 저장·저장 직전 최신 상태 재조회) + `prompts.ts`(`outlinePrompt`·`sectionPrompt`). 코드 복사가 아니라 SEO 구조에 맞춰 다시 구현.

## 1. 지금 SEO 스튜디오의 문제 (코드 확인)

| 항목 | 현재 | 문제 |
|---|---|---|
| 원고 생성 | `/api/drafts/generate` 한 요청 안에서 생성 1 + 보강 최대 2 + 끝맺음 수정 1 | 도중 실패(분량 부족·시간 초과)면 이미 쓴 호출 비용이 버려지고 처음부터 다시 (2026-10-22 v1.88~v1.90 실패 사례) |
| 동시 수정 | 서버가 저장 직전 DB의 `saveRevision`과 비교 | 화면이 불러온 시점의 번호를 보내지 않아, 탭 두 개에서 고치면 나중 저장이 먼저 저장을 조용히 덮어씀 |
| 본문 변경 후 무효화 | 자동 발행은 `publicationFingerprint`로 준비 뒤 변경 시 멈춤. 「발행 전 점검」은 AI 없이 실시간 재계산 | 점검은 항상 현재 본문 기준이라 별도 무효화 불필요 → 이번 범위는 「구간 원고를 합친 뒤 구간을 고치면 합친 원고와 달라짐」 표시 |

## 2. 범위 (「자료부터 집필」 경로에만 추가 — 기존 「새 글 만들기」·「기존 글 최적화」는 그대로)

1. **목차 만들기(AI 1회)**: 승인된 근거로 제목 후보 3개 + 소제목 4~6개(각 구간 목표 한 줄). 새 표에 저장.
2. **구간 쓰기(구간마다 AI 1회)**: 화면이 순서대로 1구간씩 호출, 구간마다 바로 저장. 「중지」하면 쓴 구간은 남고, 다시 열면 「이어쓰기」. 실패한 구간은 그 구간만 「다시 쓰기」.
   - 승인 근거만 사실로 사용(BLC-08a 규칙 그대로), 승인 문체는 말투·구성만(끝맺음 필수 규칙은 넣지 않음 — v1.91 교훈).
   - 서버는 저장 직전 최신 행을 다시 읽어 다른 구간 결과를 덮어쓰지 않음(작업실 방식).
3. **원고로 합치기(AI 0~1회)**: 모든 구간이 끝나면 하나의 원고로 합쳐 기존 원고 표(`naver_blog_seo_drafts`)에 저장 → 기존 원고 화면·발행 전 점검·확장 전달·자동 발행을 그대로 사용. 문체가 해요체/합니다체로 판별되면 v1.92의 끝맺음 안전 수정 1회(1,500자·95%·비율 개선 시만 채택).
4. **동시 수정 충돌**: 원고 수정 API(`PATCH /api/drafts/[draftId]`)가 화면이 불러온 `saveRevision`을 받아, 다르면 409 「다른 창에서 먼저 저장했습니다. 새로고침 후 다시 저장해 주세요」. 번호를 보내지 않는 옛 화면·확장은 지금처럼 동작(하위 호환).
5. **합친 뒤 변경 표시**: 구간 화면에서 이미 합친 원고가 있으면 「합친 원고 열기」, 합친 뒤 구간을 다시 쓰면 「구간이 바뀌었습니다 — 다시 합치기」 안내(기존 원고는 덮어쓰지 않고 새 원고로 합침).

## 3. 저장 구조 (운영 DB `esgxyikcnnvmlhygjkth` — 스키마 변경, 승인 필요)

새 표 `naver_blog_seo_outlines`: `id`, `user_id`(RLS 본인 4개), `research_id`, `style_id`(null 가능), `title`, `titles jsonb`, `sections jsonb`(`[{heading, goal, body, status: empty|done|failed, error, updatedAt}]`), `status`(outline|writing|written|joined), `draft_id`(합친 원고), `joined_hash`(합칠 때 구간 본문 지문), `created_at`, `updated_at`. 30일 자동 정리(`draftRetention`에 추가). 다른 회원 데이터와 섞이지 않게 모든 조회·쓰기에 `user_id` 조건.

## 4. 구현 순서와 검수

1. 순수 함수(`lib/sections.ts`: 목차 정리·구간 병합·합치기·지문) + 단위 시험 → `npx tsc --noEmit`·전체 시험
2. API 4개: `POST /api/outlines`(목차), `POST /api/outlines/[id]/section`(구간 1개), `POST /api/outlines/[id]/join`(합치기), `GET /api/outlines`(최근 목록) — 모두 `checkProgramAccessApi` + `force-dynamic`·`force-no-store`
3. `PATCH /api/drafts/[draftId]`에 선택적 `saveRevision` 비교 + 화면에서 보내기
4. 화면: `ResearchView` 승인 뒤 「구간별로 쓰기(실패해도 쓴 구간은 보존)」 버튼과 구간 목록(상태·중지·이어쓰기·다시 쓰기·합치기)
5. 마이그레이션 SQL 파일 → 운영 SQL 편집기 적용(공개 키 쓰기 거절 확인) → 로컬 빌드 → 배포 → DB·확장 v1.93 검증
6. 웨일(주인님 지정) 시험 계정 실검수: 목차 → 2구간 쓰고 중지 → 새로고침 후 이어쓰기 → 1구간 다시 쓰기 → 합치기 → 원고 화면·발행 전 점검 표시 / 탭 두 개 동시 저장 → 409 확인

## 5. 비용

| 구분 | 항목 | 예상 |
|---|---|---|

## 7. 하지 않는 것

- 기존 「새 글 만들기」·「이 근거로 글 만들기」 한 번에 생성 경로는 바꾸지 않음.
- AI 검수(작업실 `review`)는 이번 범위가 아님 — SEO는 AI 없는 「발행 전 점검」을 유지.
- 자동 발행·확장 코드는 바꾸지 않음(합친 원고는 기존 원고와 같은 형식).
