## 3. 만들 것

### 3-1. 표식(DB, 운영 공용 DB — 승인 필요)

- 새 표 `member_site_scheduler_allow`(가칭): `user_id uuid primary key references auth.users`, `granted_by uuid`, `granted_at timestamptz`, `note text`.
- RLS 켬. 회원 쓰기 정책 없음(서비스 역할만 씀). 회원 본인 행 읽기만 허용(화면에 「허용됨」을 보여 줄 때).
- `profiles`에 칸을 더하지 않는 이유: 회원이 자기 `profiles` 행을 고칠 수 있는 경로가 있으면 보호 트리거가 따로 필요하다. 별도 표는 그 위험이 없다.
- 관리자(`profiles.is_admin`)는 표와 상관없이 항상 허용.
- 뜻: 「이 회원의 예약을 사이트(Vercel) 예약으로 돌려도 된다」. 예약 기능이 있는 다른 프로그램도 나중에 같은 표를 읽을 수 있다(이번에는 이 프로그램만 읽는다).
- 마이그레이션 SQL 파일은 루트 `supabase/migrations/`에 남긴다(메인 사이트 공용 표). 번호·적용은 Master 순번.

### 3-3. 이 프로그램의 판정과 차단

판정 함수 하나(프로그램 고유 `schedulerConfig.ts`): `canUsePlatformScheduler(service, userId)` = 관리자이거나 허용 표에 행이 있음.

| 자리 | 바꿀 동작 |
|---|---|
| 기본 방식 | 허용 계정이 아니면 기본 = `cronjob`. 허용 계정은 지금처럼 고른 값(행이 없으면 `vercel`) |

| 예약 저장 | 허용 계정이 아닌데 방식이 `vercel`이면 거절하지 않고 **cron-job.org 기준으로 확인**(키 없으면 등록 안내, 있으면 그 키로 예약) |

| 예약 누르는 자리 | 키가 없으면 그 자리에서 「cron-job.org 무료 가입 → 키 한 줄」 안내와 설정 열기 |

| 안 | 내용 | 영향 | 내 의견 |

## 9. A안 설계 — 공용 기준의 「선택 연결점」 (2026-11-19, Master `msg_81623dd95517`)

- 상태: **설계 표만**. 기준·사본 편집 0, `--sync` 0, DB·제품 편집 0, 실제 게시·배포·유료 호출 0.

- §3-3 정정: 「허용 계정은 행이 없으면 `vercel`」이라고 적었던 것은 Master 조건에 따라 **행이 없으면 누구나 `cronjob`**으로 바꾼다.

### 9-1. 연결점(프로그램 고유 `schedulerConfig.ts`가 **내보낼 때만** 켜진다)

| 선택 내보내기 | 뜻 | 없을 때(다른 프로그램 전부) |
|---|---|---|
| `SCHEDULER_DEFAULT_MODE` | 행이 없는 회원의 기본 방식 | 지금 식 그대로(`SCHEDULER_IS_STANDALONE ? "cronjob" : "vercel"`) |
| `platformSchedulerAllowed(service, userId)` | 이 회원이 사이트(Vercel) 예약을 써도 되는가 | 전원 허용(지금과 같음) |
| `listPlatformAllowedUserIds(service)` | 사이트 예약 실행이 처리해도 되는 회원 목록 | 「제외 목록」 방식 그대로 |

- 읽는 방법: 기준이 `import * as cfg from "./schedulerConfig"`로 읽고 있으면 쓰고 없으면 건너뛴다 → **다른 프로그램의 `schedulerConfig.ts`는 한 줄도 바뀌지 않는다.**

- 운영 DB 변경은 **설계만**: 이 앱의 실행 방식 표 `aif_member_scheduler`에 `platform_chosen_at timestamptz null`(가칭) 한 칸. 기존 행은 전부 null → 옛 `vercel` 행은 저절로 「다시 고르기 필요」가 된다(일괄 수정 없음). 칸 이름·마이그레이션은 Master 조정.
- 관리자 허용(권한 표)과 회원의 선택(실행 방식 행)은 저장 위치도 다르다 — 관리자가 허용만 해서는 Vercel이 켜지지 않고, 회원이 고르기만 해서도 켜지지 않는다.

### 11-2. 경합 시험이 찾은 것

1. **(고침)** 회원이 Vercel을 고르는 요청과 예약 시작이 겹치면: 예약 시작이 행을 cronjob으로 올림 → Vercel 선택이 행을 vercel로 저장하고 작업을 끔(아직 작업이 없어 헛돎) → 예약 시작이 새 작업을 만들고 켜짐으로 기록 → **Vercel 행에 회원 cron 작업이 켜진 채 남음.** 순서 섞기 300회 중에 잡혔다. 고침: 새 작업을 만든 뒤 「행이 아직 cronjob일 때만」 켜짐으로 적고 아니면 그 작업을 끈다.
2. **(남김, 알림)** 같은 회원의 두 요청이 겹치고 cron 켜기까지 실패하는 경우: cronjob 선택이 옛 행을 읽음 → Vercel 선택이 저장되고 성공 응답 → cronjob 선택이 행을 cronjob으로 덮음 → 켜기 실패 → 읽어 둔 옛 행(cronjob)으로 되돌림. 끝 상태는 cronjob(안전한 쪽)이지만 **Vercel 선택은 성공 응답을 받았는데 반영되지 않았다.** 허위 선택은 아니고 「나중 요청이 이긴」 결과다. 완전히 막으려면 행에 판 번호를 두고 조건부 갱신을 해야 한다(DB 변경) — 판정 필요.
3. **(남김, 알림)** Vercel 선택과 예약 시작이 겹쳐 「행은 cronjob·켜짐으로 적혔는데 실제 작업은 꺼짐」으로 끝나는 순서가 있다. 공용 원본에도 있는 종류이고, 다음 예약 때 실제 상태를 다시 확인해 켠다(기존 동작). 그때까지 그 회원의 대기 글은 늦어질 수 있다.

### 13-3. 판 번호의 적용·철회와 기존 앱 호환

- **적용 순서**: 이 SQL을 먼저 적용해도 지금 운영 코드(v1.27과 같은 공용 코드)는 그대로 돈다 — 그 코드는 칸 이름을 적어 읽고(`user_id, mode, active, paused`) 새 칸 없이 넣고 고친다. 새 칸은 비어도 되거나 기본값이 있다. 시험에서 그 모양의 조회·넣기·고치기·충돌 시 고치기(upsert)·제외 목록 조회를 적용 뒤 DB에 돌려 확인했다. 그 코드가 쓴 행은 선택 없음·판 번호 0으로 남는다.
- **판 번호가 뜻을 갖는 시점**: 연결점을 켠 코드가 배포된 뒤부터. 그 전에 옛 코드가 조건 없이 쓴 갱신은 번호를 올리지 않지만, 그때는 번호를 보는 코드도 없다. **옛 코드와 새 코드가 같은 행을 동시에 쓰는 구간**(배포 전환 순간)에는 옛 코드의 쓰기가 번호를 올리지 않아 새 코드가 그 쓰기를 알아채지 못할 수 있다 — 전환은 한 번의 배포로 끝나고 이 앱의 실행 방식 행은 운영에 1건(2026-11-19 읽기)이라 영향은 작지만, D13 확인과 함께 「전환 순간에 대기 예약 0건」을 본다.
- **철회(원복) 순서**: ㉠ 코드를 「연결점 없음」 판으로 되돌려 배포 → ㉡ 자료를 버릴지 판단(선택 시각·지정/철회 기록) → ㉢ 버리기로 했으면 비우고 원복 SQL 실행. 코드가 남은 채 칸·표를 지우면 그 코드의 행 조회와 허용 조회가 실패한다(코드는 실패를 Vercel 차단으로 처리하지만 예약 방식 화면도 실패한다). 판 번호 칸만 지우고 싶으면 코드의 연결점 설정에서 `revisionColumn`을 먼저 빼야 한다(그러면 값 비교로 돌아가고 §12-1의 약점이 다시 생긴다).
- 원복은 **자료가 남아 있으면 멈춘다**(선택 시각이 있는 행 수·허용 표 행 수를 오류에 적는다). 판 번호 값은 자료로 치지 않는다.

### 13-6. 한계와 판정 요청

- 격리 DB(postgres 17, 소유자 `postgres`)의 결과다. 운영 표의 실제 소유자·기본 권한·다른 정책·트리거, PostgREST 경유 동작은 보지 않았다.

- 메인 사이트 관리자 화면의 저장 계약(내 제안): 지정 = `insert … on conflict (user_id) do update set granted_by, granted_at = now(), note, revoked_at = null, revoked_by = null` / 철회 = `update … set revoked_at = now(), revoked_by` / 목록 = 전체 조회. 관리자 확인은 화면 서버가 먼저 하고, 표가 한 번 더 한다.
- 판정 요청: 표·칸 이름 최종 확정, 관리자 삭제 제한(`restrict`) 유지 여부, 마이그레이션 번호와 파일 위치(이 앱 폴더 `supabase/migrations/`가 맞는지), 관리자 화면 담당.

### 14-2. 함수 계약

| 함수 | 실행할 수 있는 역할 | 돌려주는 것 | 비고 |
|---|---|---|---|

### 14-3. 지정한 관리자 계정이 지워질 때 — 대안 대조(정책 확정은 별도)

| 안 | 관리자 계정 삭제 | 누가 했는지의 보존 | 판단 |
|---|---|---|---|
| ㉠ 참조 + `restrict`(1판) | **막힌다** — 기록이 있는 동안 운영 계정을 지울 수 없다 | 번호가 살아 있는 계정을 가리킨다 | 운영 계정 관리와 부딪힌다 |
| ㉡ 참조 + `set null` | 된다 | 번호가 비워져 **누가 했는지 사라진다** | 감사 목적에 맞지 않는다 |
| ㉢ 참조 + `cascade` | 된다 | 지정 행·이력까지 지워진다(회원의 허용이 조용히 사라진다) | 쓰지 않는다 |
| ㉣ **참조 없이 번호 + 그때의 이메일을 이력에 적어 둠(2판 후보)** | **된다** | 번호와 그 시점의 이메일이 남는다(계정이 없어져도 읽힌다) | 후보로 채택. 이력에 이메일(관리자의 것)이 남는다는 점은 보관 기간과 함께 정책 확정 필요 |

- 대상 **회원** 쪽: 허용 행은 회원이 지워지면 함께 지워진다(`cascade` — 지워진 회원의 허용을 남길 이유가 없다). 이력에는 회원 **번호만** 남는다(이메일은 적지 않는다).
- 시험: 지정한 임시 관리자를 지워도 막히지 않고, 그 지정은 유효하며, 이력에 번호와 이메일이 남는 것을 확인했다.

### 14-5. 한계

- 「로그인한 관리자」는 격리 DB에서 역할 바꾸기 + 요청 회원 번호 설정으로 옮긴 것이다. 실제 로그인 토큰 검증과 PostgREST 경유는 보지 않았다.
- 함수는 소유자 권한으로 돈다. 운영 소유자가 두 표·`profiles`·`auth.users`를 읽을 수 있는지, 행 단위 보안의 영향은 배포 전 점검 항목이다(격리 DB의 소유자는 상위 권한이라 차이가 드러나지 않는다).
- 관리자용 함수를 로그인한 회원 역할에 연 것은 「누구나 부를 수는 있지만 관리자가 아니면 거절」이라는 뜻이다. 부르는 횟수 제한은 없다.
- 이력 표는 계속 쌓인다(보관 기간 미정 — 관리자 이메일이 들어 있다).
- 동시성 시험은 시간차로 겹친다. 순서는 결과로 확인했다(잠금이 없으면 결과가 달라짐을 변형으로 확인).
- 적용 파일의 잠금은 `aif_member_scheduler` 하나다(새로 만드는 표는 잠글 것이 없다). 적용 중 그 표를 쓰는 예약 요청은 최대 10초 기다린다.

### 14-6. 판정 요청

1. 관리자 화면이 **관리자 본인의 세션으로 RPC를 부르는 방식**이 메인 사이트의 기존 관리자 API 방식(서비스 역할)과 맞는지. 안 맞으면 대안: 서비스 역할 전용 함수 + 「요청 신원」을 서버가 넘기는 방식 — 그러면 신원이 다시 인자가 된다.
2. §14-3의 ㉣ 채택과 이력 보관 기간.
3. 표·칸·함수 이름 최종, 마이그레이션 번호와 파일 위치.

### 17-1. 잠금 순서 대조와 고친 것

| 쓰는 쪽 | 4판의 순서 | 5판 |
|---|---|---|
| 관리자 지정·철회(`admin_set`) | 허용 표(행) → 이력 표 | 그대로 |
| 원복 | 실행 방식 표 → 허용 표 → 이력 표(한꺼번에) | 그대로 |
| **보관 정리(`purge_history`)** | **이력 표 → 허용 표**(엇갈림) | **허용 표 → 이력 표**로 바꿈 |

- 엇갈리면 생기는 일: 정리가 이력 표를 쥐고 허용 표를 기다리는 동안, 원복이 허용 표를 쥐고 이력 표를 기다리면 둘이 서로 기다린다(DB가 한쪽을 오류로 끊는다). 이제 모든 쓰기가 **실행 방식 표 → 허용 표 → 이력 표** 한 방향이다.
- 순서는 후보 SQL(함수 앞 주석)과 원복 머리말에 적었고, 시험이 함수 본문의 문장 순서로 고정한다.

### 17-2. 원복 전에 멈출 것(인수인계)

원복 SQL을 실행하기 전에 사람이 확인한다 — 원복 파일 머리말에도 같은 내용을 적었다.

1. **보관 정리 호출 중단**: 이 앱의 운영 정리 작업이 `aif_platform_scheduler_purge_history()`를 부르지 않게 먼저 끈다(코드를 「연결점 없음」 판으로 되돌리는 배포에 포함된다). 진행 중인 호출이 끝났는지 본다.
2. **관리자 화면의 지정·철회 중단**: 원복하는 동안 쓰지 않는다.
3. 그 뒤에 §13-3의 순서대로: 코드 되돌림 → 자료를 버릴지 판단 → 원복 SQL.

- 멈추지 않아도 자료가 깨지지는 않는다 — 원복이 세 표를 잠그고 진행 중인 호출이 끝나길 기다렸다가(최대 10초) 그 결과를 보고 판단한다. 다만 원복이 끝난 뒤에 남은 호출은 「함수가 없다」는 오류를 낸다. 그래서 먼저 끈다.
