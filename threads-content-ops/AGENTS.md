## v1.42 콘텐츠 생성에 페르소나·맞춤글·엔진 선택·다시 써줘 추가 (2026-10-06)

- v1.41은 `threads-easy-planner` 화면의 핵심 기능 대부분이 빠져 있다는 주인님 지적에 따라, 1차로 다음을 옮겼습니다: **상황별 페르소나 6종 원클릭 생성**, **맞춤글(내 경험·상품·타깃 입력)**, **AI 엔진·모델 선택(OpenAI·Gemini)**, **결과별 "다시 써줘" 7종**. 정의는 `threads-content-ops/lib/personas.ts`(화면·서버 공용, 원본의 페르소나·다시 쓰기 구성을 그대로 옮김), 생성·다시 쓰기는 `lib/attention.ts`, 서버 동작은 `web-actions.ts`의 `generateAttentionPost`/`rewriteGeneratedPost`, 화면은 `AttentionComposer.tsx`.
- **사실 원칙은 유지:** 페르소나는 시점·말투만 정하고 구체적 체험담을 지어내지 않습니다. 회원이 맞춤글에 직접 적은 "내 실제 경험"만 1인칭 경험담으로 살릴 수 있고, 상품명은 본문에 쓰지 않고 첫 댓글 멘트에서만 언급합니다.
- 페르소나 버튼은 누르면 바로 생성합니다(글감이 비어 있으면 그 페르소나의 기본 주제로, 글감이 있으면 그 글감을 그 페르소나 시점으로). 엔진은 회원 본인의 OpenAI(기본 gpt-4.1)·Gemini 키만 쓰며, 허용 목록 밖의 모델 이름은 서버에서 거부합니다. 다시 써줘는 선택한 글 한 편의 본문을 바꾸며 저장은 하지 않습니다.
- **아직 못 옮긴 것(다음 단계):** 사진(최대 5장)·동영상 첨부 분석, Claude 엔진, 오늘 뭐 쓰지 주제 추천·랜덤 픽·무드 칩, 보관함 저장. DB 변경 없음.
- 검증: 모의 응답으로 OpenAI/Gemini 호출 형식, 페르소나·맞춤글 지시문 반영(없을 때는 미포함), 다시 쓰기, 잘못된 엔진·모드 거부, 400/429 안내를 확인했습니다. 실제 키로 생성해 본 확인은 아직 못 했습니다.

## v1.41 콘텐츠 생성 = 글감 + 주목받는 글 생성기 (2026-10-06)

- 주인님 지시로 사이드바·대시보드 이름을 "콘텐츠 작성" → **"콘텐츠 생성"**으로 바꾸고, 글감을 고르면 `threads-easy-planner`(Threads AI 기획기)의 글 생성 방식을 합쳐 "사람들에게 주목받는 글"을 만들어 주도록 `?tab=create`를 새로 만들었습니다(`AttentionComposer.tsx`, 프롬프트·정리는 `threads-content-ops/lib/attention.ts`, 서버 동작은 `web-actions.ts`의 `generateAttentionPost`/`saveGeneratedDraft`).
- 흐름: ① 글감 고르기(수집한 글감 선택 또는 직접 입력, 추가 요청 선택) → ② "주목받는 글 만들기" → ③ 대표 글 1개 + **5대 훅 유형(자책형·부정 명령형·리얼 썰형·논쟁형·반전형)별 글 5개** + 댓글을 부르는 마무리 멘트(CTA) + 후속 아이디어를 보고, 본문을 고쳐 쓴 뒤 마음에 드는 글만 "이 글로 초안 저장"(검토 대기 초안, 글감은 사용 완료 처리). 저장 전에는 DB에 아무것도 쓰지 않고, 자동 발행도 하지 않습니다. 본문은 Threads 500자 제한을 글자 수로 안내합니다.
- **원본(threads-easy-planner)과 다른 점:** 원본은 1인칭 체험담을 만들어 내는 프롬프트인데, 여기서는 글감에 있는 사실만 쓰고 글감에 없는 사실·수치·개인 경험을 지어내지 않도록 바꿨습니다(뉴스·영상 글감에서 가짜 체험담이 나가는 것을 막기 위함). 상품 홍보 문구도 쓰지 않게 했습니다. 원본의 첨부 사진·영상 분석, 페르소나, 다시 써줘 7종, 보관함 저장은 옮기지 않았습니다. 원본 폴더는 다른 도구가 작업 중이라 읽기만 했고 수정하지 않았습니다.
- 엔진: 회원 본인의 OpenAI 키(`gpt-4o-mini`), 키가 없으면 설정 안내가 나옵니다. 초안·발행 관리 탭의 기존 간단 생성(`DraftComposer`)은 그대로 둡니다. DB 변경 없음.
- 검증: 모의 응답으로 5개 유형 정리, 잘못된 응답·빈 본문 처리, 글감을 `<data>`로 감싸 전달, 추가 요청 반영, 429 안내를 확인했습니다. **실제 OpenAI 키로 생성해 본 확인은 아직 못 했습니다**(회원 키·호출 비용).

- 주인님 지시로 `shorts-viral-studio`의 쇼츠 검색(키워드 → 조회수·구독자 실측 → 떡상 등급·점수)을 "떡상 콘텐츠 수집" 화면의 별도 패널로 옮겼습니다. 서버 코드는 `threads-content-ops/lib/youtubeShorts.ts`, 서버 동작은 `web-actions.ts`의 `searchViralShorts`/`saveShortAsViralCandidate`, 화면은 `app/(dashboard)/threads-content-ops/ShortsSearch.tsx`입니다.
- 회원 본인의 YouTube Data API 키(`youtube_api_key`, 설정 화면에 이미 있음)만 사용하며, 검색 1회는 약 102유닛입니다. 키가 없거나 잘못되면 설정 안내가 나옵니다. 길이·조회수·구독자 필터와 프리셋(지금 떡상·작은 채널 대박·급상승)은 가져온 결과에만 적용되어 추가 할당량을 쓰지 않습니다.
- 검색 결과는 DB에 저장하지 않고, "글감으로 저장"을 누른 영상만 `tco_viral_candidates`에 `method='http'`, `source_input=https://www.youtube.com/shorts/<id>`로 저장합니다(새 DB 변경 없음). 저장 내용은 영상 제목·채널·조회수·구독자·등급·링크와 "주제만 참고해 새로 쓰라"는 안내뿐이며 영상 내용은 복사하지 않습니다. 같은 영상 중복 저장은 막고, 후보 카드의 출처가 쇼츠 주소이면 "유튜브 쇼츠" 배지로 보입니다. 이후 "이 글감으로 작성" 흐름은 기존과 같습니다.
- 검증: 모의 YouTube 응답으로 지표 계산(구독자 대비 10배 → 초대박, 구독자 비공개 → 판정불가), 키 오류·할당량 초과 안내를 확인했습니다. 실제 YouTube 키로 검색해 본 확인은 아직 못 했습니다(회원 키 필요).

## v1.34 떡상 콘텐츠 수집 = 글감 수집 (2026-10-06)

- 주인님 지시: "콘텐츠 작성 전에 글감을 수집하는 기능을 콘텐츠 작성 위에 구현", 구현 기준은 쓰레드 자동화(`threads/`)의 글감 수집 기능. 사이드바 **1번 `떡상 콘텐츠 수집`**(`?tab=viral`)을 새로 만들고, 기존 메뉴 번호는 하나씩 밀렸다(2 콘텐츠 작성 · 3 초안·발행 관리 · 4 계정 운영정보 · 5 쇼핑제휴 상품 등록).
- **수집 방식 2가지:** ① 주소 지정(글 1건, 또는 목록 페이지에서 무작위 5건 — 네이버 뉴스 섹션은 구버전 목록 주소로 우회) ② Perplexity 화제 검색(`sonar-pro`, 최근 72시간). 결과는 회원 본인의 OpenAI 키(`gpt-4o-mini`)로 **Threads 글감 후보(제목 10자·본문 450자 이내·키워드, 반말)**로 정리해 저장한다. 원문 전체는 저장하지 않고 정리본과 출처(주소/주제)만 저장한다.
- **원본(`threads/`)과 다른 점:** NewsBlur(RSS)는 제3자 아이디·비밀번호 저장이 필요해 이번 범위에서 제외했다(필요하면 별도 보안 검토 후 추가). 카테고리 기능 없음(회원별 풀 하나). 외부 텍스트는 AI에게 `<data>`로만 전달하고 지시로 따르지 않게 했다. **주소 읽기에 SSRF 방어를 추가**했다(`threads-content-ops/lib/collector.ts`의 `assertPublicHttpUrl`/`fetchPublicHtml`): http·https와 80/443 포트만, 내부·사설·예약 주소로 해석되는 호스트 거부(IPv6는 일반 공개 대역 `2000::/3`만 허용하는 허용 목록 방식, 6to4·Teredo·문서용 대역 거부), 리다이렉트는 3번까지 매번 다시 검사, 응답 2MB·10초 제한. 알려진 한계: 검사한 DNS 결과와 실제 접속 사이의 DNS 재바인딩은 완전히 막지 못한다(서버가 접속할 IP를 고정하지 않음) — 공개 페이지 읽기 전용·응답 본문은 AI 정리용으로만 쓰고 그대로 노출하지 않으므로 위험을 낮췄지만, 더 강한 보호가 필요하면 IP 고정 접속으로 바꿀 것.
- **글감 → 콘텐츠 작성 연결:** 후보 카드의 `이 글감으로 작성`(`?tab=create&viral=<id>`) 또는 콘텐츠 작성 화면의 `수집한 글감 불러오기` 선택으로 주제 칸이 채워지고(`DraftComposer.tsx`, 1,200자 이내 프롬프트), 초안 생성에 성공하면 그 글감은 자동으로 `사용 완료` 표시된다. 초안 생성은 계속 회원이 버튼을 눌러야만 실행된다.
- **DB:** 주인님 승인으로 새 표 `tco_viral_candidates`(마이그레이션 `20261006180000_tco_viral_candidates.sql`, 운영 DB 적용·조회 확인). `user_id` 소유, RLS 4정책 모두 `authenticated` + `auth.uid() = user_id`, anon 권한 없음, 회원당 최대 300건, `status`는 `ready/used/archived`, `method`는 `http/perplexity`.
- 설정 화면에 **Perplexity API 키** 항목(`user_api_keys.provider = perplexity`, 공용 체크 제약에 이미 있음)과 매뉴얼 버튼(`1df95d8b-…` Perplexity API 키 발급받기)을 추가했다. 주소 지정 방식은 OpenAI 키만 있으면 되고, 화제 검색은 Perplexity와 OpenAI 키가 모두 필요하다. 키가 없으면 안내만 보이고 수집은 실행되지 않는다.
- 검증: 모의 응답으로 SSRF 방어 22개 경우(IPv4 사설·링크로컬·루프백·`0.0.0.0`·CGNAT·숫자/16진수/8진수 표기, IPv6 루프백·링크로컬·사설·IPv4 매핑·NAT64·6to4·Teredo, 비표준 포트·로그인 정보·`file:`/`ftp:`/`javascript:`), 리다이렉트로 메타데이터 주소 접근 시도 차단, 리다이렉트 무한 반복 중단, 2MB 크기 제한, 링크·본문 추출, 문단 보정, AI 응답 해석(450자 제한·빈 제목 제외·키워드 정리)과 오류 안내(401·429·500)를 확인했다. **실제 OpenAI·Perplexity 키로 수집해 본 확인은 아직 못 했다**(회원 키 필요).

## v1.31 검은 버튼 글자가 안 보이던 문제 수정 (2026-10-06)

- 증상: 콘텐츠 소스 화면의 `상품 검색`·`소스로 저장`·`소스 등록`·`수정 저장` 버튼과 계정 운영정보의 `운영정보 저장` 버튼이 검은 배경에 글자가 안 보였다(주인님 스크린샷). 설정 화면의 파란/빨간 버튼도 흰색이어야 할 글자가 어두운색이었다.
- 원인: 이 화면은 `app/globals.css`의 `.threads-content-ops-light .text-white { color: #171717 }`(옛 다크 테마 카드의 흰 글자를 흰 화면에서 읽히게 하려는 규칙) 범위 안에 있다. 버튼이 `bg-neutral-900 text-white`면 이 규칙이 글자를 어두운색으로 바꿔 검은 배경 위에서 사라진다. 처음 시도한 `!text-white`도 소용없었다 — Tailwind가 `@layer` 안의 `.text-white` 규칙을 `!text-white`용으로도 자동 생성(`!important` 포함, 더 높은 우선순위)해서 다시 덮였다(서버가 만든 CSS를 직접 열어 확인).
- 해결: 진한 배경(`bg-neutral-900`·`bg-sky-600`·`bg-[#e7000b]`) 위 글자는 `text-white` 대신 **`text-[#ffffff]`**를 쓴다. 이 값은 범위 규칙이 건드리지 않는 일반 클래스라 항상 흰색이다. 7개 버튼에 적용(`AccountOperations.tsx` 1, `SourceQueue.tsx` 4, `WebSetup.tsx` 2).
- **새 버튼을 만들 때:** 이 프로그램 화면에서 진한 배경 버튼에 `text-white`를 쓰지 말고 `text-[#ffffff]`를 쓴다. 글자색 때문에 `globals.css`의 범위 규칙을 고치지는 않는다(다른 화면 영향).

- 운영 DB에 `tco_operation_profiles`, `tco_content_sources`를 적용했다. 두 테이블은 `user_id`와 계정 FK를 가지며 RLS를 활성화하고, authenticated 역할에 대해서도 select/insert/update/delete 각각 `(select auth.uid()) = user_id`만 허용한다. anon 권한은 회수했다.
- `?tab=accounts`의 세 번째 번호형 흐름인 **계정 운영정보**에서 계정별 주제·성격·말투·대상 독자·금지 주제/표현·일상/홍보 비율·하루 목표·댓글 확인 주기·운영 시간·자동화 사용 선호를 실제로 저장한다.
- `automation_enabled`는 발행 권한이 아니라 회원의 선호 설정이다. 무인 실행 워커와 안전한 스케줄 정책이 구현되기 전에는 어떤 게시도 자동으로 시작하지 않는다.
- 콘텐츠 소스 큐는 다음 단계(블로그·쿠팡·네이버 브랜드 커넥트 실제 수집/등록)에 사용할 공통 회원별 기반이다. 아직 외부 결과나 성과를 임의로 생성하지 않는다.

## v1.26 웹 운영 대시보드 1단계

- AIMaster 웹 서브프로그램 표준에 따라 **흰색 배경·중성 회색 경계·어두운 본문 글자**를 유지한다. 원본 Electron의 다크 화면은 기능 흐름 참고용이며 웹 작업 화면의 색상 기준이 아니다.
- 대시보드는 실제 `tco_threads_accounts`, `tco_posts`, 회원 본인 `user_api_keys` 등록 상태만 집계한다. 계정·초안·예약·발행·실패 기록이 없으면 0 또는 안내 상태를 보이며, 가짜 성과·작업 로그·상품을 표시하지 않는다.
- 원본의 운영 구조를 웹형으로 옮겼다: 현재 운영 계정, 누적 게시/초안/실패/예약 지표, 즉시 작업 소스, 운영·API 상태, 실제 작업 이력, 예약 작업 목록. 일상·YouTube 외 블로그·쿠팡·네이버 브랜드 커넥트는 해당 회원별 소스 테이블과 실제 API 로직이 생기기 전까지 `설정·구현 필요`로 표시한다.
- 다음 구현 단계는 계정별 운영 프로필·소스 큐·댓글·성과 이력 테이블과 owner-only RLS이다. 이는 DB 스키마 변경이므로 별도 승인 뒤 마이그레이션으로 진행한다.

## v1.25 OpenAI 응답 호환

- Responses API가 `output_text` 대신 `output[].content[].text`에 본문을 주는 경우도 읽는다. 401/403, 429, 빈 응답을 구분한 안내 문구를 반환한다.

## v1.23 복수 계정 연결

## v1.22 운영 대기열과 YouTube 소재

- 원본 `threads-auto`/영상의 YouTube 공개 메타데이터 소재 흐름을 웹형으로 옮겼습니다. `loadYouTubeSource()`는 현재 회원 권한과 본인 `youtube_api_key`를 확인한 뒤 공개 제목·설명만 읽고, 1,200자 이내의 초안 소재로 돌려줍니다.
- `tco_posts` 기존 상태를 이용해 `draft → scheduled → draft`(예약/취소), `failed → draft`(재검토)를 서버 액션으로 구현했습니다. 모든 mutation에는 `user_id`, 현재 상태 조건, `checkProgramAccess()`가 함께 적용됩니다.
- 예약 시간은 5분 후~180일 이내만 허용합니다. 아직 Vercel Cron 보안 비밀값과 요금제 실행 간격이 확인되지 않았으므로 예약 무인 발행은 켜지지 않았으며, UI도 이를 자동 실행이라고 표시하지 않습니다.

## 절대 규칙

- 기존 `threads/`, `threads-comment-reply/`, `threads-affiliate-poster/`, `threads-easy-planner/`는 참고만 하고 수정하지 않습니다.
- 이 프로그램은 **웹 전용**입니다. `desktop/`은 외부 원본 참고 사본일 뿐 배포 대상이 아닙니다.
- 모든 웹 작업 화면은 AIMaster 공통 규칙대로 흰색 베이스를 사용한다. 메인 사이트·원본 설치형 앱의 다크 테마를 웹 작업 화면에 적용하지 않는다.
- 모든 회원은 자신의 OpenAI API 키와 자신이 만든 Meta Developers Threads 앱 ID/시크릿만 사용합니다. 운영자 키·공용 Meta 앱·다른 회원 토큰으로 폴백하지 않습니다.
- 계정·초안·예약·발행 이력에는 반드시 `user_id`를 두고 RLS owner-only 정책을 적용합니다.
- 페이지, Server Action, API 콜백 모두 `checkProgramAccess()` 또는 API용 권한 검사로 프로그램 이용 권한까지 확인합니다. 로그인만 확인해서는 안 됩니다.
- 권한이 관여하는 `page.tsx`/`route.ts`에는 `dynamic = "force-dynamic"`와 `fetchCache = "force-no-store"`를 함께 둡니다.
- 자동 발행과 예약은 기본 OFF입니다. 회원이 웹에서 명시적으로 실행 또는 예약한 경우에만 처리합니다.
