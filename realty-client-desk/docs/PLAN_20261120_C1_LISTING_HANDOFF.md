**공통 규칙**
- 모든 핸들러 첫 줄: 단계가 `done`이거나 기한이 지났거나 메시지 종류가 지금 단계와 다르면 즉시 무시. 단계 전환은 검사 통과 직후(비동기 작업 전) — 같은 종류 두 번째 도착(재 READY·재 후보·중복 ACK)은 자동 차단.
- 단계를 바꿀 때 직전 타이머를 반드시 해제하고, 새 기다림이 있으면 새 타이머를 둔다(타이머 A→B, C→없음).
- 단계 `done`이 되는 모든 경우(성공·검증 실패·계정 불일치·만료·페이지 이탈 `useEffect` 정리): 남은 타이머·`message` 리스너 해제, `acct`·`readyId`·`requestId`를 `null`로 버림. 보내는 쪽은 `fields`도 버림. 받는 쪽의 폼에 채운 후보 값은 등록 성공·「후보 비우기」·탭 닫기 때 버린다.

**계정 동일성**(Mac 검수 `RE-CRM-C1-DESIGN-INDEPENDENT-QA-CX-QA-01` P2-1)
- 원본 `sameOwner`(`extension/web-bridge.js`)는 **확장 연결 계정 = 확장 기록 소유 계정 = 매물 알림 웹 로그인 계정**까지만 맞춘다. **고객관리 웹 로그인 계정은 그 조건에 들어 있지 않다.** origin·source·readyId·requestId도 계정 근거가 아니다 → 위 표의 `acct` 비교(READY와 후보 양방향)로 **같은 계정만** 허용, 다른 계정으로는 넘기지 않는다.
- `acct` = 로그인 세션 `user.id`의 SHA-256 앞 16자. 두 프로그램이 같은 AIMaster 인증(같은 Supabase `auth.users.id`)을 쓰는 것은 구현 전 사전 확인 조건. 각 쪽은 버튼 클릭/READY 직전에 자기 서버 액션(예: `getHandoffAcct()`)으로 받는다 — 서버 컴포넌트 prop으로 넘기지 않음(HTML·RSC 페이로드에 남음). 원문 id·이메일은 메시지에 없음. 만들 수 없으면 미전송/미수신.
- `acct`는 핸들러 클로저 변수로만 두고 `localStorage`·`sessionStorage`·쿠키·URL·DOM 속성·화면 표시·`console`/서버 로그에 남기지 않으며, 위 「단계 `done`」 때 버린다.
- 한계: `acct` 비교는 실수로 다른 계정에 넣는 것을 막는 장치다. 저장은 어차피 받는 쪽 서버 세션 `user_id`로만 된다.

로그인 복귀: 고객관리에 로그인돼 있지 않으면 `/listings` → `/login`으로 이동한다. 같은 탭 이동이라 `window.opener`는 보통 유지되지만, 로그인에 시간이 걸리면 보내는 쪽 15초가 먼저 끝나 후보는 **보내지 않는다**(로그인 뒤 READY가 와도 보내는 쪽 리스너는 이미 해제 — 늦게 온 READY는 무시). 회원은 로그인 뒤 매물 알림에서 버튼을 다시 누른다. 로그인 화면은 READY를 보내지 않음(`/listings`에서만). 로그인 전 화면에 값이 들어가는 경로 없음.

- 저장소 검색으로는 두 프로그램 모두 `Cross-Origin-Opener-Policy` 설정 0(`next.config`·`vercel.json`·proxy)이지만, 실제 배포 응답 헤더와 로그인 리다이렉트를 거친 뒤 `window.opener` 유지는 **확인하지 않았다**.

### 3-1. 미저장 후보 → 의뢰 확인 → 등록 경계

| 단계 | 상태 | 할 수 있는 것 | 하지 않는 것 |
|---|---|---|---|
| 미저장 후보 | 고객관리 화면 메모리의 폼 기본값만 | 회원이 보고 고치기, 비우기, 닫기 | DB 저장·맞는 고객 계산 결과 저장·문자 발송·`광고 중` 표시 |
| 의뢰 확인 | 폼 안 확인란 「이 매물은 내 사무소가 직접 의뢰를 받았습니다」(후보에서 온 경우에만 보임, 기본 체크 해제) | 체크해야 「등록」 버튼이 켜짐 | 자동 체크·기억해 두기 |
| 등록 | 회원이 「등록」 클릭 → **후보 전용 서버 액션**(예: `addCandidateListingAction`, 기존 `addListingAction`은 일반 수동 등록 전용으로 그대로) | 본인 `user_id`로 「후보」 상태 저장(상태 값 승인 뒤), 광고 시작은 회원이 따로 | 확인값 없는 저장(서버가 거부), 「광고 중」으로 바로 저장, 저장과 동시에 문자 발송 |

- 서버 강제 범위(A4 보완, Mac P2-2): 후보 등록은 기존 `addListingAction`(`src/lib/actions/listings.ts:79`)이 아니라 **후보 전용 서버 액션**(예: `addCandidateListingAction`)으로만 받는다. 그 액션은 서버에서 `mandateConfirmed === "1"`이 아니면 저장하지 않고 오류를 돌려준다(화면 확인란을 우회한 요청도 거부).
  - 확인값의 의미(A5): `mandateConfirmed`는 **회원의 의사 표시**일 뿐 의뢰 사실의 증명이 아니다.
  - 보장 수준 구분: 서버가 강제하는 것은 「후보 경로로 들어온 요청에는 명시적 의뢰 확인값이 있어야 저장」까지다. 서버는 그 값이 실제 의뢰 사실과 맞는지, 일반 등록 폼(수동 입력)으로 같은 매물을 넣는 것을 구분하지 못한다 — 확인란은 회원의 자기 확인이며 법적 적합성 보장이 아니다(법률 판단은 하지 않음).
- 재제출·응답 불명(A5, 별도 정책): 「등록」 버튼은 누르는 즉시 비활성화하고, 응답이 오면 결과만 보여 준다.
  - 서버 응답이 성공/실패로 분명하지 않으면(네트워크 끊김·시간 초과) **자동 재시도하지 않고** 「저장됐는지 확인하지 못했어요. 매물 목록에서 먼저 확인한 뒤 필요하면 다시 등록해 주세요」로 안내하고 후보 값은 폼에 남겨 둔다.
  - 다시 누를 때는 §3 중복 경고(같은 거래 종류·가격·면적·단지명)가 먼저 보인다. 정확한 1회 저장 보장(제출 ID 고유 제약 등)은 DB 변경이 필요해 이번 범위 밖 — 별도 결정 항목.
- 광고 상태(코드 확인): 지금 `addListingAction`은 `status` 없이 insert → DB 기본값 「광고 중」(`20261103020000_listings_ad_sends.sql`, 허용 값 광고 중·계약·내림). 발송은 서버에서 「광고 중」만 허용(`listings.ts:133`), 발송은 회원이 매물 상세에서 고객을 골라 누를 때만이고 저장과 동시에 자동 발송되는 경로는 없다.
  - 요구: 후보 저장은 「광고 중」이 아닌 **비광고 기본 상태**여야 하고, 회원이 따로 「광고 시작」을 눌러야 광고 중으로 바뀌어야 한다.
  - **차단(기존 스키마로 불가)**: 허용 값 중 비광고는 「계약」「내림」뿐인데 둘 다 뜻이 다르다(내림 = 광고를 내린 매물). 이를 빌려 쓰면 목록·통계·회원 이해가 어긋나므로 추천하지 않는다. 정확한 비광고 상태(예: 「후보」)는 **DB 상태 값 추가(마이그레이션) 승인**이 필요하다 → 승인 전까지 C-1 구현은 **차단**으로 기록.

## 4. 결정 항목(주인님/Master)

1. **의뢰 확인과 비광고 상태(가장 중요)**: 매물 알림 행은 **다른 중개사가 올린 매물**이다. 의뢰받지 않은 매물을 내 매물로 광고하는 일이 없도록 (가) 후보 전용 서버 액션이 명시적 의뢰 확인값을 강제하고 (나) 저장 상태는 「광고 중」이 아닌 「후보」로 둔다(§3-1). (나)는 상태 값 추가 마이그레이션(운영 DB 변경) 승인이 필요하며, 승인 전까지 구현 차단. 법률 판단은 이 문서에서 하지 않음(필요하면 주인님 확인).
2. 주소 수준: 결과에 지번 주소가 없어 「시군구 동 단지명」만 채움 — 회원 보완으로 충분한지.
3. 중복 기준: 위 휴리스틱(경고만)으로 충분한지, 아니면 출처 칸(`source_ref`, 네이버 매물 번호) 추가(DB 변경)로 정확히 막을지. 추천: 경고만(매물 번호는 넘기지 않는 원칙 유지).
4. 버튼 위치: `RecentResults`의 새 매물·가격 변동 행만(`/results`·`/dashboard` 공통) vs 변동 기록 탭(`StatsDashboard`)까지.

**승인 필요 한 줄(묶음)**: C-1을 「확장 수정 없이 매물 알림 결과(`RecentResults`) → 창 사이 메시지(같은 계정 `acct` 일치만) → 고객관리 미저장 후보 폼(전화번호·중개사·원문·매물 번호 미전달) → 의뢰 확인을 서버 후보 전용 액션이 강제 → 비광고 상태 「후보」로 저장, 광고 시작은 회원이 따로」 방식으로 할지와, 이를 위한 `realty_desk_listings.status` 허용 값 「후보」 추가 마이그레이션(운영 DB 변경)·중복은 경고만을 함께 정해 주세요 — 상태 값 추가 승인 전에는 구현 차단, 구현은 로컬 시험까지 비용 0, 배포·실시험은 두 프로그램 각 빌드 1회 별도 승인.

계정: 시험 계정 `buylifemall@naver.com`(주인님 로그인), 다른 계정 확인이 필요하면 관리자 계정은 쓰지 않고 주인님이 정한 두 번째 계정. 브라우저: 검수자 지정 브라우저(Mac Codex는 Edge, Claude는 ego lite), 작업 공간 하나. 문자 발송 0, 시험 매물은 끝나면 삭제.

| # | 확인 | 합격 기준 |
|---|---|---|
| H1 | 응답 헤더: 두 운영 주소의 `/results`·`/dashboard`(매물 알림), `/listings`·`/login`(고객관리) `curl -sI` | `Cross-Origin-Opener-Policy` 없음 |
