계정 동일성(A4 보완, Mac 검수 `RE-CRM-C1-DESIGN-INDEPENDENT-QA-CX-QA-01` P2-1):
- 원본 `sameOwner`(`extension/web-bridge.js`)는 **확장 연결 계정 = 확장 기록 소유 계정 = 매물 알림 웹 로그인 계정**까지만 맞춘다. **고객관리 웹 로그인 계정은 그 조건에 들어 있지 않다.** origin·source·readyId도 계정 근거가 아니다.
- 정책: **같은 계정만 허용, 다른 계정으로는 넘기지 않는다**(다른 고객관리 계정으로 보내는 옵션 없음).
- 방법: 두 프로그램은 같은 AIMaster 인증(같은 Supabase 프로젝트의 `auth.users.id`)을 쓴다 — 구현 전 사전 확인 조건. 각 페이지는 서버에서 확인한 자기 로그인 `user.id`의 SHA-256 앞 16자(`acct`)를 클라이언트 prop으로 받는다(원문 id·이메일은 메시지에 넣지 않음).
  - 받는 쪽 READY에 `acct`를 싣는다. 보내는 쪽은 자기 `acct`와 다르면 **값을 보내지 않고** 「고객관리에 다른 계정으로 로그인돼 있어요. 같은 계정으로 로그인한 뒤 다시 눌러 주세요(저장된 것 없음)」.
  - 보내는 후보 메시지에도 보내는 쪽 `acct`를 싣고, 받는 쪽은 자기 `acct`와 다르면 버린다(이중 확인).
  - 어느 쪽이든 `acct`를 만들 수 없으면(로그인 정보 없음·해시 실패·`crypto.subtle` 없음) **미전송/미수신**.
- 한계: `acct` 비교는 「실수로 다른 계정에 넣는 것」을 막는 장치다. 저장은 어차피 받는 쪽 서버 세션 `user_id`로만 되므로 다른 회원 자료에 쓰는 경로는 원래 없다.

타임아웃·실패(모두 **명시적 미저장 실패** — 값 재시도·자동 대체 없음):

핸들러 기한·1회 소비·정리(A4 보완, Mac P3):
- 양쪽 모두 상태 `{deadline, consumed}`를 둔다. 모든 메시지 핸들러는 **처음에** `if (consumed || Date.now() > deadline) return` — 타이머가 늦게 돌더라도 기한 지난 READY·후보는 처리하지 않는다.
- 보내는 쪽: 조건에 맞는 READY를 받으면 즉시 `consumed = true` → 후보 1회 전송 → 그 뒤에는 「채움 확인(`desk-filled`)」만 기다리는 새 기한 15초를 둔다. 받는 쪽은 폼 채움 직후 `{v:1,type:"desk-filled",readyId,ok}`를 opener에 1회 보낸다(값 없음).
  - `desk-filled ok:true` → 타이머 해제·리스너 해제, 「고객관리 탭에 채워졌어요. 그 탭에서 확인하고 등록해 주세요(아직 저장 안 됨)」.
  - `ok:false`(검증 실패) → 「받는 쪽에서 값이 맞지 않아 채우지 않았어요(저장된 것 없음)」.
  - 기한 안에 응답 없음 → 「보냈지만 채워졌는지 확인하지 못했어요. 고객관리 탭을 확인해 주세요(저장된 것 없음)」 — **전송 성공으로 표시하지 않는다**(postMessage 호출만으로는 상대의 검증·반영을 알 수 없음).
- 받는 쪽: 후보 1건을 받으면 즉시 `consumed = true`, 타이머·리스너 해제, `window.opener = null`은 `desk-filled`를 보낸 뒤.
- 정리: 성공·실패·기한 만료·페이지 이탈(`useEffect` 정리 함수) 어느 경우든 타이머와 리스너를 모두 해제한다. 메모리의 후보 값은 등록 성공·「후보 비우기」·탭 닫기 때 버린다.

로그인 복귀: 고객관리에 로그인돼 있지 않으면 `/listings` → `/login`으로 이동한다. 같은 탭 이동이라 `window.opener`는 보통 유지되지만, 로그인에 시간이 걸리면 보내는 쪽 15초가 먼저 끝나 후보는 **보내지 않는다**(로그인 뒤 READY가 와도 보내는 쪽 리스너는 이미 해제 — 늦게 온 READY는 무시). 회원은 로그인 뒤 매물 알림에서 버튼을 다시 누른다. 로그인 화면은 READY를 보내지 않음(`/listings`에서만). 로그인 전 화면에 값이 들어가는 경로 없음.

COOP·창 참조 사전 확인 조건(**배포 환경에서 미검증**):
- 저장소 검색으로는 두 프로그램 모두 `Cross-Origin-Opener-Policy` 설정 0(`next.config`·`vercel.json`·proxy)이지만, 실제 배포 응답 헤더와 로그인 리다이렉트를 거친 뒤 `window.opener` 유지는 **확인하지 않았다**.
- 구현 배정 전 사전 확인(읽기만): 두 운영 주소 `/results`·`/listings`·`/login` 응답 헤더에 COOP 없음, 시험 계정으로 버튼 → 고객관리 탭에서 `window.opener !== null` 확인(로그인 상태·로그아웃 상태 각각).
- 불일치(COOP `same-origin` 등으로 opener가 끊김) 시: 후보 **미전송**(위 실패 안내), 프래그먼트(②)로 자동 대체하지 않음 — 방식 변경은 별도 결정.

남는 한계: 같은 브라우저의 다른 확장이 두 페이지의 DOM·메시지를 읽을 수 있는 것은 이 방법으로도 막지 못함(지금 결과 표 자체도 같은 화면에 있음). 전송값은 화이트리스트 최소 칸이라 화면에 이미 보이는 것보다 노출이 넓어지지 않음.

파일 범위(예정, 결정 뒤):

## 3. 확인·중복·취소·소유 검사

| 검사 | 방법 |
|---|---|
| 사용자 확인 | 버튼 클릭 → 폼 채움까지만. 저장은 회원이 기존 「등록」을 눌러야만. 자동 등록·일괄 등록 없음 |
| 취소 | 폼을 닫거나 저장하지 않으면 아무것도 남지 않음(값은 창 메모리에만, 주소·저장소에 없음). 「후보 비우기」 버튼으로 즉시 폼 초기화. 저장 뒤 취소는 기존 삭제·「내림」 |
| 중복 | DB 변경 없이: 고객관리가 폼을 채울 때 본인 매물 중 같은 거래 종류·같은 가격·면적 ±1㎡·title 포함 단지명이 있으면 「비슷한 매물이 이미 있어요」 경고와 그 매물 링크(저장은 막지 않음) |
| 소유 | **같은 계정만**(§2-1 「계정 동일성」 `acct` 양방향 비교, 불일치·확인 불가 시 미전송). 보내는 쪽 행은 원래 `sameOwner`를 통과한 것만 화면에 있음. 받는 쪽 저장은 서버 세션 `user_id`로만 |
| 위·변조 | 받는 쪽이 메시지를 신뢰하지 않음(origin 목록 + `event.source === window.opener` + `readyId` 일치 + 1회 처리 + 값 재검사, §2-1 ③ 계약) — 허용 값·길이·숫자 범위 재검사, HTML 이스케이프는 React 기본. 서버 액션의 기존 zod 검사 그대로 |
| 개인정보 최소화 | 전화번호·중개사 상호·매물 번호 미전달(시험으로 고정: 입력 행에 휴대폰·사무실 번호·중개사 상호·매물 특징·매물 주소가 있어도 메시지 객체에 그 칸이 없고 title·address에 긴 숫자 덩어리 없음) |

### 3-1. 미저장 후보 → 의뢰 확인 → 등록 경계

| 단계 | 상태 | 할 수 있는 것 | 하지 않는 것 |
|---|---|---|---|
| 미저장 후보 | 고객관리 화면 메모리의 폼 기본값만 | 회원이 보고 고치기, 비우기, 닫기 | DB 저장·맞는 고객 계산 결과 저장·문자 발송·`광고 중` 표시 |
| 의뢰 확인 | 폼 안 확인란 「이 매물은 내 사무소가 직접 의뢰를 받았습니다」(후보에서 온 경우에만 보임, 기본 체크 해제) | 체크해야 「등록」 버튼이 켜짐 | 자동 체크·기억해 두기 |
| 등록 | 회원이 「등록」 클릭 → 기존 `addListingAction` | 본인 `user_id`로 저장, 그 뒤부터 기존 매물과 똑같이 매칭·안내 | 확인란 없이 저장(서버 액션도 후보 표시가 있으면 확인값을 다시 검사), 저장과 동시에 문자 발송 |

- 서버 강제 범위(A4 보완, Mac P2-2): 후보 등록은 기존 `addListingAction`(`src/lib/actions/listings.ts:79`)이 아니라 **후보 전용 서버 액션**(예: `addCandidateListingAction`)으로만 받는다. 그 액션은 서버에서 `mandateConfirmed === "1"`이 아니면 저장하지 않고 오류를 돌려준다(화면 확인란을 우회한 요청도 거부).
  - 보장 수준 구분: 서버가 강제하는 것은 「후보 경로로 들어온 요청에는 명시적 의뢰 확인값이 있어야 저장」까지다. 서버는 그 값이 실제 의뢰 사실과 맞는지, 일반 등록 폼(수동 입력)으로 같은 매물을 넣는 것을 구분하지 못한다 — 확인란은 회원의 자기 확인이며 법적 적합성 보장이 아니다(법률 판단은 하지 않음).
- 광고 상태(코드 확인): 지금 `addListingAction`은 `status` 없이 insert → DB 기본값 「광고 중」(`20261103020000_listings_ad_sends.sql`, 허용 값 광고 중·계약·내림). 발송은 서버에서 「광고 중」만 허용(`listings.ts:133`), 발송은 회원이 매물 상세에서 고객을 골라 누를 때만이고 저장과 동시에 자동 발송되는 경로는 없다.
  - 요구: 후보 저장은 「광고 중」이 아닌 **비광고 기본 상태**여야 하고, 회원이 따로 「광고 시작」을 눌러야 광고 중으로 바뀌어야 한다.
  - **차단(기존 스키마로 불가)**: 허용 값 중 비광고는 「계약」「내림」뿐인데 둘 다 뜻이 다르다(내림 = 광고를 내린 매물). 이를 빌려 쓰면 목록·통계·회원 이해가 어긋나므로 추천하지 않는다. 정확한 비광고 상태(예: 「후보」)는 **DB 상태 값 추가(마이그레이션) 승인**이 필요하다 → 승인 전까지 C-1 구현은 **차단**으로 기록.

## 4. 결정 항목(주인님/Master)

1. **의뢰 확인과 비광고 상태(가장 중요)**: 매물 알림 행은 **다른 중개사가 올린 매물**이다. 의뢰받지 않은 매물을 내 매물로 광고하는 일이 없도록 (가) 후보 전용 서버 액션이 명시적 의뢰 확인값을 강제하고 (나) 저장 상태는 「광고 중」이 아닌 「후보」로 둔다(§3-1). (나)는 상태 값 추가 마이그레이션(운영 DB 변경) 승인이 필요하며, 승인 전까지 구현 차단. 법률 판단은 이 문서에서 하지 않음(필요하면 주인님 확인).
2. 주소 수준: 결과에 지번 주소가 없어 「시군구 동 단지명」만 채움 — 회원 보완으로 충분한지.
3. 중복 기준: 위 휴리스틱(경고만)으로 충분한지, 아니면 출처 칸(`source_ref`, 네이버 매물 번호) 추가(DB 변경)로 정확히 막을지. 추천: 경고만(매물 번호는 넘기지 않는 원칙 유지).
4. 버튼 위치: `RecentResults`의 새 매물·가격 변동 행만(`/results`·`/dashboard` 공통) vs 변동 기록 탭(`StatsDashboard`)까지.

**승인 필요 한 줄(묶음)**: C-1을 「확장 수정 없이 매물 알림 결과(`RecentResults`) → 창 사이 메시지(같은 계정 `acct` 일치만) → 고객관리 미저장 후보 폼(전화번호·중개사·원문·매물 번호 미전달) → 의뢰 확인을 서버 후보 전용 액션이 강제 → 비광고 상태 「후보」로 저장, 광고 시작은 회원이 따로」 방식으로 할지와, 이를 위한 `realty_desk_listings.status` 허용 값 「후보」 추가 마이그레이션(운영 DB 변경)·중복은 경고만을 함께 정해 주세요 — 상태 값 추가 승인 전에는 구현 차단, 구현은 로컬 시험까지 비용 0, 배포·실시험은 두 프로그램 각 빌드 1회 별도 승인.
