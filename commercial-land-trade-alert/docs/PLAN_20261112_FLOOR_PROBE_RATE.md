# 플랜 — 층 진단 호출 속도 조절 (2026-11-12) [역할: realty]

대상: 관리자 전용 진단 `src/app/api/admin/floor-probe/route.ts`(회원 수집 코드는 건드리지 않음). 근거: `docs/IMPROVEMENTS.md` 11-12 「재측정 3차」·「다음 개선 후보」.

## 문제 (3차 측정 실측, 운영 키 = 포털 키)

| 항목 | 값 |
|---|---|
| 결과 | 30건 중 찾음 3 · 없음 1 · 오류(429) 26 |
| 호출 | 210회, 지번 16곳 중 끝까지 읽은 곳 2곳 |
| 호출을 가장 많이 쓴 곳 | 고양 장항동 869 — 호실 목록 6,894줄(69쪽). 같은 지번 거래 7건 중 앞 4건이 실패하고 5번째에 성공 |

원인 3가지:
1. **5쪽씩 동시에 부름** → 공공데이터포털 초당 제한에 걸림(429).
2. **실패한 지번은 캐시에서 지우고 다음 거래 때 처음부터 다시 읽음** → 69쪽짜리 지번을 4번 다시 읽어 호출이 크게 불어남.
3. **429가 나도 다음 지번으로 계속 감** → 이미 막힌 상태에서 나머지 지번도 모두 429.

## 고칠 것

1. **쪽은 하나씩 순서대로, 호출 사이 200ms 간격**(초당 5회 이하). 재시도는 429일 때만 1회, 1초 기다린 뒤.
2. **429가 다시 나면 그 회차를 멈춤** — 남은 거래는 부르지 않고 `result: "not_tried"`로 표시. 응답에 `stoppedReason: "rate_limited"`와 멈춘 시점의 호출 수를 넣음.
3. **실패한 지번은 실패로 기억** — 같은 지번의 다음 거래는 다시 부르지 않고 같은 오류로 표시.
4. **큰 지번 상한(결정 1)** — 호실 목록이 3,000줄(30쪽)을 넘으면 `result: "too_large"`로 따로 세고 읽지 않음. 맞춤률 분모에서는 빼고 건수는 따로 보여 줌.
5. **시간 예산 240초** — 넘으면 `stoppedReason: "time"`으로 남은 거래를 `not_tried` 처리(Vercel 300초 안에서 응답 보장).
6. 응답의 `calls`는 실제로 보낸 요청 수(재시도 포함)로 셈.

예상 호출: 3차 표본 기준 큰 지번 1곳을 빼면 지번 15곳 × 평균 1~3쪽, 약 40회 이하.

## 검수

- 로컬(무료): 쪽 순서·간격·멈춤·실패 기억·큰 지번 판정을 가짜 응답(429·정상·6,894줄)으로 시험(`node --test`), `npx tsc --noEmit`, `npm run build`.
- 운영: 배포 뒤 관리자 로그인으로 `/api/admin/floor-probe?n=30` 1회(ego, `page.goto`). 429가 나면 재시도·우회하지 않고 그 결과 그대로 기록.

## 결정 항목

1. 큰 지번 상한: **3,000줄 넘으면 읽지 않고 따로 셈(추천)** / 상한까지 앞부분만 읽고 「잘림」 표시 / 상한 없음
2. 배포 시점: **다음 상가 배포 때 함께(추천, 작은 수정 모아 배포 규칙)** / 지금 바로 1회(재측정을 빨리 하려면)
