## 🛠️ 작업 과정 및 표준 워크플로우 (Development Workflow)

스레드 AI 기획기(`threads-easy-planner`)의 신규 기능 추가 또는 수정 작업 시 다음 표준 프로세스를 엄격히 준수한다:

1. **사전 점검 및 인수인계 확인**:
   - `docs/HANDOFF.md` 및 `docs/ERROR_LESSONS.md`를 먼저 확인하여 진행 중인 작업 및 과거 발생 에러를 파악한다.
   - `git status`로 깨끗한 상태를 확인한다.
2. **UI/UX 설계 및 상태 흐름 정의**:
   - 사용자가 한눈에 이해할 수 있는 직관적인 라벨링을 적용한다 (예: 모호한 명칭 지양, 실제 수행 동작이 드러나는 버튼명 부여).
   - 상태 관리는 `usePlannerStore.ts`를 중심으로 일원화하고, 로컬 캐시와 Supabase DB가 항상 동기화되도록 설계한다.
3. **핵심 기능 구현 및 자동 저장(Auto-save) 연계**:
   - AI 생성(`handleGenerate`) 완료 시 사용자가 별도 저장 버튼을 누르지 않아도 보관함(`tep_saved_plans`)에 100% 자동 영구 저장되도록 연동한다.
   - 수동 저장 버튼은 즉시 `[✅ 보관함 저장완료]` 상태로 전환되어 피드백을 제공한다.
4. **실전 사용 매뉴얼(`/guide`)과의 동기화**:
   - 새로운 버튼, 옵션, 워크플로우가 추가되면 `/guide/page.tsx` 매뉴얼에도 해당 기능의 사용 순서와 조작법을 즉시 반영한다.
5. **버전 판올림 및 DB 동기화**:
   - `src/lib/version.ts`의 `APP_VERSION`을 +0.01 올린다 (예: `v1.23` ➔ `v1.24`).
   - Supabase DB `programs` 테이블의 `version` 컬럼을 동일한 버전으로 UPDATE한다.
6. **단일 작업 세트 완결**:
   - `npm run build` 검증 ➔ `git commit` & `git push origin master` ➔ `vercel deploy --prod --yes` 배포 ➔ HTTP 응답 검증 및 보고.

## ⚠️ 개발 및 운영 시 핵심 주의사항 (Critical Caveats)

1. **상태 관리(Store)와 DB 스토리지 분리 주의**:
   - 브라우저의 `localStorage`에만 저장하고 DB INSERT를 누락하면, 브라우저가 바뀌거나 캐시가 삭제될 때 사용자의 글이 전부 유실된다.
   - 반드시 Supabase `tep_saved_plans` 테이블로 서버에 동기화하고, DB 실패 시에만 로컬 스토리지 Fallback으로 보호해야 한다.
2. **페르소나 버튼의 동작 원리 명확화**:
   - 8종 페르소나 버튼(`가전·살림 주부형`, `독신·자취생형` 등)은 **키워드가 없어도 해당 페르소나의 대표 일상 소재를 자동으로 채워 즉시 글을 생성하는 '원클릭 치트키'**이다.
   - 사용자가 "키워드도 없는데 왜 글이 써지지?"라고 오해하지 않도록, 버튼 위에 명확한 툴팁/안내 문구를 유지하고 상세 템플릿(맞춤글 생성)과 명확히 구분한다.
3. **5대 바이럴 훅 치환 상호작용 유지**:
   - 결과 카드의 5대 바이럴 훅 카드(호기심형, 손실회피형, 숫자노하우형, 공감썰형, 반전논란형)를 클릭하면 **본문의 첫 문장(후킹 문장)이 즉시 해당 버전으로 치환**되어야 한다.
   - 이 치환 동작이 인라인 본문 직접 수정(`isEditing`) 모드와 충돌하지 않도록 상태를 관리한다.
4. **자댓글 / CTA 복사 기능의 목적 보존**:
   - 스레드 알고리즘은 본문에 링크나 제품명을 넣으면 도달률을 급격히 떨어뜨린다.
   - 따라서 본문에는 호기심만 남기고, **첫 번째 자댓글로 독자 소통 질문 및 링크를 남기는 2단계 전략**을 취해야 하므로 이 구조를 절대 훼손하지 않는다.
5. **가이드 문서는 '이론'이 아닌 '프로그램 조작 매뉴얼'이어야 함**:
   - 마케팅 원론이나 알고리즘 이론만 나열하면 사용자는 프로그램을 어떻게 조작해야 할지 알 수 없다.
   - 항상 화면의 버튼 명칭, 조작 순서(STEP 0 ~ STEP 4), 실제 인터랙션 방법이 그림/카드 형태로 직관적으로 설명되어야 한다.
6. **30일 자동 삭제(TTL) 정책 일관성**:
   - 보관함 데이터는 서버 조회 시 `created_at < NOW() - INTERVAL '30 days'`를 자동 정리(Sweep)하고, 클라이언트 로컬 캐시도 30일 경과 데이터를 자동 Prune한다.
   - 각 카드에는 `🕒 N일 후 자동삭제` 배지가 정확히 계산되어 표시되어야 한다.
