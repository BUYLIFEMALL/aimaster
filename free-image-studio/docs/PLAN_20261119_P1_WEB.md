## 5-2에서 정한 것

- 엔진 주소는 `http://127.0.0.1:47821` 고정. 환경변수·설정·사용자 입력으로 바꾸지 않는다.
- 토큰과 접수 기록은 로그인 회원 번호별 칸(`fis.engineToken.v1:<회원>`·`fis.submissions.v1:<회원>`). 회원이 바뀌면 화면이 `dispose()`를 불러 늦게 온 응답을 버린다.
- 접수 번호는 보내기 전에 기록한다. 응답을 못 받으면 `unknown` — 스스로 다시 보내지 않는다. `confirm()`이 목록에서 같은 번호를 찾으면 `accepted`, 못 찾으면 `unknown` 그대로다.
- 엔진이 넣기 전에 막은 것이 확실한 응답(401·403·409·429·503, 사전 검사 문구의 400)만 `rejected`. 그 밖의 400·서버 오류·응답 유실은 `unknown` — 엔진은 작업을 목록에 넣은 뒤 파일 저장을 기다리므로 저장 실패가 400으로 올 수 있다. 자동 재시도 없음.
- 맥미니 검수(`.ai/results/IMG-P1-5-2-CX-QA-01.md`) 반례 4건 보완:
  - 접수 기록을 **연결 범위 표시(`link`)** 에 묶는다. 엔진이 「이전 범위를 이어받았다」고 답한 다시 연결에서만 표시가 유지된다. 연결 끊기·토큰 무효·다시 연결 응답 유실 뒤의 새 범위에서는 과거 접수를 확인도 다시 보내기도 하지 않는다(엔진의 중복 방지는 범위 안에서만 듣는다).
  - **목록에 없다는 것만으로는 미접수를 확정하지 않는다**(Master `msg_99ebb68cdcff`). 지금 엔진에는 「받지 않았다」를 알려 주는 응답이 없고, 끝난 작업은 100개·30일 기준으로 정리되거나 엔진 창에서 지워질 수 있다. 앞선 작업이 남아 있어도 대상 작업만 사라졌을 수 있으므로 `confirm()`은 같은 번호를 **찾았을 때만** `accepted`로 확정하고, 못 찾으면 `unknown`(`notListed`)이다. 처음 보완에서 넣었던 「앞선 작업이 남아 있으면 미접수」 기준은 이 반례로 폐기했다.
  - `resend()`는 넣기 전 거절이 확실하고 다시 해 볼 만한 접수(대기열 가득 참·잠시 뒤·엔진이 닫힘·연결 필요)만 같은 번호·같은 내용으로 보낸다. `unknown`은 다시 보내지 않는다.
  - 접수 번호마다 확인·보내기를 한 번에 하나만 하고, 결과를 적을 때 지금 상태를 다시 본다. 접수됨을 옛 응답이 되돌리지 않는다.
- 화면에서 지킬 것(5-3): `unknown`으로 남은 접수는 「엔진이 이미 그렸을 수 있습니다. 새로 맡기면 같은 그림이 두 번 나올 수 있습니다」를 보여 주고 사용자가 고르게 한다(기록 지우기는 `forget(id, { force: true })`). 자동으로 새 번호를 만들어 넣지 않는다.
- 남는 불편: 응답이 끊긴 접수는 엔진이 실제로 못 받았더라도 자동 복구되지 않고 사용자 선택이 필요하다. 엔진이 접수 번호 단건 조회나 「받지 않음」 응답을 주면 풀린다(개선 제안).
