## 2. 빌드 평가 때 DB로 나가는 진입점 (소스 읽기)

`next build`의 수집 단계는 경로 모듈을 불러온다. `src/app/api/rpc/[name]/route.ts` → `src/server/runtime.ts` → `litpage/server/api/handlers.ts`·`modules.generated.ts`(39개) 순으로 서버 모듈 전체가 평가된다.

가. **모듈 최상위 DDL** — `db.exec(...)`가 31개 파일의 최상위에 있다(`db.ts`·`scheduler.ts`·`agents/model.ts`·`api/modules/templates.ts` 등). 코드 전체의 `db.exec` 53곳은 모두 `CREATE TABLE/INDEX IF NOT EXISTS` 또는 `ALTER TABLE … ADD COLUMN`이고 트랜잭션 문(`BEGIN` 등)은 없다. 열 유무를 보는 `PRAGMA table_info`는 변환기(`pg/translate.ts:171`)가 빈 문장으로 바꿔 DB에 가지 않는다(그래서 `ALTER … ADD COLUMN IF NOT EXISTS`가 매번 나간다).

나. **웹훅 비밀값 이관** — `automations/engine.ts:519`의 최상위 `startAutomationEngine()`이 `migrateWebhookSecrets()`(`webhookSecrets.ts:157`)를 부른다. `records`의 automation·block·collection과 `snapshots`를 `LIKE`로 훑고, 평문 값이 있으면 **쓰기**(`putRecord`·`UPDATE snapshots`)까지 한다. 빌드에서도 실행된다.

다. **일정 재등록 타이머** — `agents/triggers.ts:112`의 최상위 `setTimeout(…, 1500)`이 살아 있는 workflow를 모두 읽어 에이전트마다 예약 취소 1회 + 일정마다 예약 저장 1회를 보낸다(**쓰기**). 빌드 작업 프로세스가 1.5초 넘게 살아 있으면 실행된다.

공통 관문: DB 접근은 전부 `litpage/server/db.ts`의 `db.exec`·`Statement.get/all/run`을 거쳐 `pg/bridge.ts`의 `call()`로 간다(다른 파일이 `bridge`를 직접 부르는 곳 0). 질의당 30초 제한(`AWW_DB_TIMEOUT_MS`)이 있고, 작업 실행기(`startScheduler`)는 Next 쪽에서 켜지 않는다(`main.ts`는 불러오는 곳 없음, 작업은 `/api/cron/*`가 `runDueJobs`로 실행).

### 실행 환경별 의존성

| 환경 | 지금 동작 | 의존하는 것 |
|---|---|---|
| 빌드(수집 단계) | 가·나·다가 운영 DB로 나감(쓰기 포함) | 없어야 함 — 빌드 결과물은 이 실행에 의존하지 않는다(모든 경로가 동적) |
| 운영 콜드스타트 | 첫 요청에서 모듈 평가 → 가·나 실행 → 1.5초 뒤 다 | 표가 있어야 질의가 됨(가), 재배포 뒤 일정 예약이 맞아야 함(다), 평문 비밀값 봉인(나) |
| 로컬 개발(`next dev`) | 경로를 처음 열 때 모듈 평가 → 같은 순서 | 운영과 같음 |
| 시험(vitest) | 모듈을 불러오면 로컬 시험 DB에 가·나·다 | 표가 불러오는 즉시 있어야 하는 시험이 있을 수 있음(확인 필요) |

## 3. 제안 설계 — 「첫 질의 때 초기화」(빌드 단계 표지에 기대지 않음)

핵심: 초기화를 **모듈을 불러올 때**가 아니라 **DB를 실제로 처음 쓸 때**로 옮긴다. 빌드는 모듈을 불러오기만 하고 질의를 하지 않으므로 DB에 가지 않게 된다. 빌드인지 아닌지를 묻지 않으므로 환경 판정이 틀릴 일이 없다.

1. **DDL 미루기(`db.ts` 한 곳)** — `db.exec`가 받은 문장을 바로 보내지 않고 대기 목록에 순서대로 쌓는다. `Statement.get/all/run`은 보내기 직전에 `ensureSchema()`를 불러 대기 목록을 한 번에 순서대로 실행한다. 이미 초기화가 끝난 뒤에 불리는 `db.exec`(늦게 불려온 모듈)는 다음 질의 전에 같은 방식으로 실행된다. 31개 파일의 최상위 `db.exec`는 **고치지 않는다**.
2. **시작 작업 등록점(`db.ts`)** — `onFirstUse(fn)`을 둔다. 첫 초기화가 성공한 직후 등록된 함수를 차례로 한 번씩 부른다(각각 `try/catch`, 실패해도 요청은 계속).
3. **나·다 옮기기(두 파일, 각 한 곳)** — `engine.ts`의 `migrateWebhookSecrets()` 호출과 `triggers.ts`의 일정 재등록을 `onFirstUse`에 등록한다. 재등록은 지금처럼 1.5초 늦춰 요청을 막지 않게 한다(`unref`). `onCommit`·`onBeforePersist`·`registerJobHandler` 같은 **메모리 안 등록은 최상위에 그대로** 둔다(DB에 가지 않음).

### 채택하지 않는 것과 이유

- **`NEXT_PHASE` 가드만 쓰기**: 설치된 Next 16.4.6 원본(`node_modules/next/dist/build/index.js:1232`)에서 작업 프로세스를 만들기 직전에 `process.env.NEXT_PHASE = 'phase-production-build'`를 넣는 것은 읽어서 확인했다. 그러나 실제 빌드에서 값이 보이는지는 **실행해 확인하지 않았다**. 그래서 판정 근거로 쓰지 않는다. 구현 뒤 로컬 빌드에서 값이 확인되면 「빌드 중 질의가 오면 오류로 알림」 같은 **보조 경보**로만 검토한다.
- **31개 파일을 각각 함수로 감싸기**: 수정 범위가 크고 원본(litpage)과의 차이가 커진다.
- **마이그레이션 파일로 DDL 옮기기**: 방향은 맞지만 운영 DDL 절차·권한이 걸려 범위가 크다(후속 후보).

## 4. 동시 시작·실패 처리

- **한 인스턴스 안**: 브리지가 동기라 `ensureSchema()`는 한 번에 하나만 돈다. 「진행 중」 표시를 두어 초기화 도중 다시 들어오는 호출(시작 작업이 질의를 부르는 경우)은 그대로 통과시킨다.
- **여러 인스턴스 동시 콜드스타트**: 지금도 같은 `IF NOT EXISTS` DDL이 동시에 나간다. 동작은 바뀌지 않는다(같은 문장·같은 순서).
- **초기화 실패(시간 초과·접속 실패)**: 대기 목록을 비우지 않고 오류를 그 질의에 그대로 던진다. 다음 질의가 처음부터 다시 시도한다(모든 문장이 반복 실행에 안전). 지금은 모듈 평가가 실패해 그 인스턴스의 경로 전체가 깨지므로, 실패 범위는 지금보다 좁아진다.
- **시작 작업 실패**: 요청과 분리한다. 기록만 남기고, 재등록은 다음 저장(`syncAgentSchedules` 직접 호출 경로) 때 복구되는 지금 성질을 유지한다.
- **첫 요청 지연**: 지금 모듈 평가 때 드는 DDL 시간이 첫 질의로 옮겨질 뿐 합계는 같다. 줄이는 것은 이 작업의 범위가 아니다.

## 5. 시험 항목

새 단위 시험(브리지를 모의해 보낸 문장을 기록):

1. 모듈 39개와 진입 모듈을 불러오기만 하면 브리지 호출 0회(빌드 평가 재현) — 타이머를 2초 넘겨도 0회.
2. 첫 `Statement` 호출 직전에 대기 DDL이 **불러온 순서대로 한 번** 나가고, 두 번째 질의부터는 다시 나가지 않는다.
3. 초기화 뒤에 불려온 모듈의 `db.exec`가 다음 질의 전에 실행된다.
4. 초기화 중 첫 문장이 실패하면 질의가 오류를 받고, 다음 질의에서 전체가 다시 시도되어 성공한다(문장 빠짐·중복 실행으로 인한 차이 0).
5. 시작 작업은 첫 성공 뒤 한 번만 불리고, 하나가 던져도 나머지와 질의는 계속된다.
6. 초기화 도중 재진입(시작 작업 안의 질의)이 교착 없이 지나간다.
7. 일정 재등록: 합성 workflow로 첫 질의 뒤 1.5초에 예약이 만들어지고, 불러오기만으로는 만들어지지 않는다.
8. 웹훅 비밀값 이관: 평문 값이 든 합성 레코드가 첫 질의 뒤 봉인되고, 불러오기만으로는 그대로다.

회귀(기존 시험 전체 + 아래 확인):

- 표가 불러오는 즉시 있다고 가정한 시험·코드가 있는지(`db.exec` 직후 최상위에서 `prepare(...).run/get/all`을 바로 부르는 곳) 전수 확인.
- 평상시 API: 로그인 뒤 페이지 열기·저장·검색·가져오기·템플릿 추가.
- 작업: `/api/cron/jobs`·`/api/cron/member`가 예약 작업을 실행, 리마인더·반복 자동화·예약 링크 정리.
- 에이전트 반복 일정: 저장하면 예약이 갱신되고 재배포(콜드스타트) 뒤에도 예약이 유지된다.
- 로컬 전용 DB로 `next build`: 수집 단계에서 DB 접속 0(접속 주소를 닫힌 포트로 두어도 빌드가 끝나는지로 판정) — 이때 `NEXT_PHASE` 값도 함께 기록한다.

## 6. 범위·순서

- 수정 파일(예상): `litpage/server/db.ts`, `litpage/server/automations/engine.ts`, `litpage/server/agents/triggers.ts`, 새 시험 1~2개. DB 스키마·API·권한 변경 0.
- 순서: 시험 먼저(1·2번이 지금 코드에서 실패하는 것 확인) → 구현 → 로컬 전용 DB 빌드 확인 → 독립 검수 → 배포(빌드 1회, 승인).
- 이 설계로도 빌드가 멈추면 원인은 원격 빌드 캐시 쪽으로 확정되므로, 그때 캐시 없는 빌드 1회를 별도 승인으로 진행한다.
