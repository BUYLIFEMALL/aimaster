## 2. 빌드 평가 때 실행되는 진입점 (구문 분석 전수 조사)

`next build`의 수집 단계는 경로 모듈을 불러온다. `src/app/api/rpc/[name]/route.ts` → `src/server/runtime.ts` → `litpage/server/api/handlers.ts`·`modules.generated.ts`(39개) 순으로 서버 모듈 전체가 평가된다.

`src/litpage/server`·`src/server`·`src/litpage/shared` 263개 파일의 **모듈 최상위(함수·클래스 본문 밖) 호출 588건**을 TypeScript 구문 분석으로 모아 분류했다(scratchpad `toplevel.cjs`, 읽기 전용).

1차 문서에는 가·나·다만 있었다. **라·마·바는 이번 전수 조사에서 추가로 확인한 것**이며, 이 때문에 1차 설계(「첫 질의가 초기화를 부른다」만으로 충분)는 성립하지 않는다 — 라·마가 모듈을 불러오는 중에 스스로 질의를 내기 때문이다. 3절 설계를 이에 맞게 고쳤다.

공통 관문: DB 접근은 전부 `litpage/server/db.ts`의 `db.exec`·`Statement.get/all/run`을 거쳐 `pg/bridge.ts`의 `call()`로 간다(다른 파일이 `bridge`를 직접 쓰는 곳 0). 질의당 30초 제한(`AWW_DB_TIMEOUT_MS`). 작업 실행기(`startScheduler`)는 Next 쪽에서 켜지 않는다(`main.ts`를 불러오는 곳 0) — 작업은 `/api/cron/jobs`·`/api/cron/member` 등이 `runDueJobs`로 실행한다.

## 3. 제안 설계 — 「시작 작업을 첫 질의 때 실행」(빌드 단계 표지에 기대지 않음)

핵심: 모듈을 불러올 때 하던 DB 작업을 **등록만 해 두고**, DB를 실제로 처음 쓰는 순간에 **지금과 같은 순서로** 실행한다. 빌드는 모듈을 불러오기만 하고 요청을 처리하지 않으므로 DB에 가지 않는다. 빌드인지 묻지 않으므로 환경 판정이 틀릴 일이 없다.

1. **DDL 미루기(`db.ts`)** — `db.exec`는 문장을 대기 목록에 순서대로 쌓는다(31개 파일 무수정).
2. **시작 작업 등록점(`db.ts`)** — `atStartup(fn)`. 시작 전에는 대기 목록에 쌓고, 시작이 끝난 뒤에 불리면 **그 자리에서 바로** 실행한다(지금의 「불러오는 즉시 실행」과 같음).
3. **시작 실행(`db.ts`)** — `Statement.get/all/run`이 보내기 직전에 `ensureStarted()`를 부른다: 대기 DDL을 순서대로 실행 → 등록된 시작 작업을 등록 순서대로 **동기로** 실행 → 원래 질의 진행. 이후에도 호출마다 「대기 DDL이 있으면 먼저 실행」을 확인한다(값 하나 비교).
4. **호출 지점 감싸기(각 한 줄)** — 나(1)·다(1)·라(5)·마(1)·바(1) 아홉 곳을 `atStartup(() => …)`으로 감싼다. 다는 지금처럼 그 안에서 1.5초 타이머를 건다. 메모리 등록(자)과 `db.prepare`(아)는 최상위에 그대로 둔다.

### 다섯 경계 상황에서 언제 실행되는가

| 상황 | 실행 시점(설계 적용 뒤) | 근거 |
|---|---|---|
| cron 첫 호출(`/api/cron/jobs`·`/api/cron/member`) | 인증은 환경변수 비교라 DB 없음 → `runDueJobs`의 첫 문장(기한 된 작업 조회) 직전에 DDL → 나·라·마 동기 실행 → 조회 진행 → 작업 실행. 작업 처리기는 불러올 때 이미 메모리에 등록돼 있다 | `app/api/cron/jobs/route.ts:33`, `scheduler.ts` `registerJobHandler`(최상위, 메모리) |

### 채택하지 않는 것과 이유

- **`NEXT_PHASE` 가드만 쓰기**: 설치된 Next 16.4.6 원본(`node_modules/next/dist/build/index.js:1232`)에서 작업 프로세스를 만들기 직전에 `process.env.NEXT_PHASE = 'phase-production-build'`를 넣는 것은 읽어서 확인했다. 실제 빌드에서 값이 보이는지는 **실행해 확인하지 않았다**. 그래서 판정 근거로 쓰지 않는다. 구현 뒤 로컬 빌드에서 값을 기록하고, 「빌드 중 질의가 오면 알림」 같은 보조 경보로만 검토한다.
- **31개 파일을 각각 함수로 감싸기**: 수정 범위가 크고 원본(litpage)과의 차이가 커진다.
- **마이그레이션 파일로 DDL 옮기기**: 방향은 맞지만 운영 DDL 절차·권한이 걸려 범위가 크다(후속 후보).

## 4. 동시 시작·실패 처리

- **한 인스턴스 안**: 브리지가 동기라 `ensureStarted()`는 한 번에 하나만 돈다. 「진행 중」 표시를 두어 시작 작업 안에서 나오는 질의(이관의 조회·저장)는 그대로 통과시킨다.
- **여러 인스턴스 동시 콜드스타트**: 3절 표 — 지금과 같은 내용이 지금과 같은 순서로 난다.
- **DDL 실패(시간 초과·접속 실패)**: 대기 목록을 비우지 않고 오류를 그 질의에 던진다. 다음 질의가 처음부터 다시 시도한다. 지금은 모듈 평가가 실패해 그 인스턴스의 경로 전체가 깨지므로 실패 범위는 좁아진다.
- **시작 작업 실패**: 작업마다 `try/catch`. 지금 나는 이미 `try/catch` 안이고(`engine.ts:512`), 라·마는 지금 실패하면 모듈 평가가 깨진다 — 적용 뒤에는 기록만 남기고 요청은 계속한다. 실패한 시작 작업을 다음 질의에서 다시 돌릴지는 **구현 전에 정할 결정 항목**이다(다시 돌리면 이관·예약이 반복 실행에 안전한지 항목별 확인이 필요하다. 1차 제안: 다시 돌리지 않고 기록 — 지금의 「불러올 때 한 번」과 같음).
- **첫 요청 지연**: 지금 모듈 평가 때 드는 시간(DDL 약 50문장 + 이관 조회 + 예약 5건)이 첫 질의로 옮겨질 뿐 합계는 같다. 줄이는 것은 이 작업의 범위가 아니다.
- **응답 뒤 타이머**: 서버리스 인스턴스는 응답 뒤 멈출 수 있어 1.5초·15초 타이머가 다음 호출 때 실행될 수 있다 — 지금도 같다(변경 없음).

## 5. 시험 항목

새 단위 시험(브리지를 모의해 보낸 문장을 기록):

1. 서버 기능 모듈 39개와 진입 모듈을 **불러오기만** 하면 브리지 호출 0회, 16초 뒤(가짜 시계)에도 0회 — 감싸지 않은 최상위 질의가 새로 생기면 이 시험이 실패한다.
2. 첫 `Statement` 호출 직전에 대기 DDL이 불러온 순서대로 한 번, 이어서 시작 작업이 등록 순서대로 한 번 실행되고, 두 번째 질의부터는 다시 실행되지 않는다. 문장 목록이 지금 구현의 불러올 때 문장 목록과 같다(순서 포함).
3. 시작 뒤에 불려온 모듈: `db.exec`는 다음 질의 직전에, `atStartup`은 등록 즉시 실행된다.
4. DDL 첫 문장이 실패하면 질의가 오류를 받고, 다음 질의에서 전체가 다시 시도되어 성공한다.
5. 시작 작업 하나가 던져도 나머지 작업과 질의는 계속된다.
6. 시작 작업 안의 질의(재진입)가 교착·중복 시작 없이 지나간다.
7. 일정 재등록: 합성 workflow로 첫 질의 뒤 1.5초에 예약이 만들어지고, 불러오기만으로는 만들어지지 않는다.
8. 웹훅 비밀값 이관: 평문 값이 든 합성 레코드가 **첫 질의의 결과가 돌아오기 전에** 봉인되고, 불러오기만으로는 그대로다.
9. 주기 작업 예약 5건과 `api_webhooks` 버전 맞춤이 첫 질의 때 한 번 실행된다.
10. cron 경로: 첫 호출에서 기한 된 합성 작업이 처리기로 실행된다(등록이 시작보다 먼저임을 확인).

회귀(기존 시험 전체 + 아래 확인):

- 표가 불러오는 즉시 있다고 가정한 시험·코드가 있는지 전수 확인.
- 평상시 API: 로그인 뒤 페이지 열기·저장·검색·가져오기·템플릿 추가.

## 7. 구현 결과와 설계에서 달라진 점 (`5efdefd22`, 2026-11-19)

- **늦은 DDL은 미루지 않는다(설계 3절 3번 정정)**: 처음 구현은 `db.exec`를 언제나 대기시켰는데, `src/server/booking.ts`의 `ensureTables()`(트랜잭션 안에서 잠금 조회 뒤 표 생성)가 그 자리 실행에 기대고 있어 기존 시험 27개가 실패했다. 그래서 **DB를 처음 쓰기 전의 `db.exec`만** 대기시키고, 한 번 시작된 뒤에는 예전처럼 그 자리에서 바로 실행한다. 늦게 불려온 모듈(`runtime.ts:196·200` 등)의 DDL·시작 작업도 예전과 같은 시점이다.
- **실패 처리(결정 항목 1 확정 — 자동 재시도 없음)**: DDL이나 시작 작업이 던지면 그 질의가 오류를 받고, 같은 인스턴스의 이후 질의도 **같은 오류**를 받는다(DDL을 다시 보내지 않음). 예전에는 모듈 평가가 깨져 그 인스턴스의 경로가 계속 실패했으므로 범위가 같다. 차이: 예전에는 그 모듈을 불러오는 경로만 깨졌고, 지금은 DB를 쓰는 모든 경로가 같은 오류를 받는다(실패가 더 넓게 보이지만 숨겨지지 않는다).
- **웹훅 비밀값 이관 실패**: 예전처럼 요청은 계속된다. 기록은 오류 객체 전체 대신 **오류 종류(코드·이름)만** 남긴다 — 오류 문구에 헤더 값이 섞일 수 있어서다(예전 코드는 오류 객체를 그대로 기록했다).
- **주기 예약 5건**: 설계대로 동기 순서 유지.
- **`Statement`를 거치지 않는 경로**: `db.ts` 안의 `getRecords`·`putRecord`·`tx()`(`BEGIN`·`COMMIT`)는 브리지를 직접 불렀다. 브리지 호출을 `db.ts` 안의 경계 함수로 바꿔 모두 같은 경계를 지난다.
- **수정 파일**: `db.ts` + 한 줄 감싸기 9곳(설계와 같음) + `tests/setup-local-db.mjs`(전용 DB 주소를 환경변수 `AWW_LOCAL_APP_URL`로도 받게 한 줄 — 없으면 예전 그대로).
