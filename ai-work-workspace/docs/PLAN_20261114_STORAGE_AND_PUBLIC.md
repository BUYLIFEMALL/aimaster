## A. 큰 파일 저장소 옮기기

### A-1. 지금 (코드 조사)
| 항목 | 지금 |
|---|---|
| 저장 위치 | 이식판 자체 DB 표 `files.content`(BLOB) — `src/litpage/server/content/files.ts` `storeFile` |
| 올리기 | `/api/upload` → 서버가 본문을 받아 DB에 넣음. **파일당 4MB**(Vercel 요청 본문 한도 4.5MB) |
| 내려받기 | `/files/<id>/<이름>` → 서버가 DB에서 읽어 보냄 |
| 보관 | 음악·영상 30일, 그 밖 1년(주인님 지정 예외, `mediaRetention.ts`), 관리자·시험 계정 제외 |
| 회원 저장 용량(💾 500MB 등) | **잡히지 않음** — 메인 사이트는 Supabase Storage 파일만 셈(경로 안 회원 번호로 주인 판정, `supabase/migrations/0063`) |

문제: ① 4MB 넘는 파일(PDF·영상·디자인 파일)을 못 올림 ② 파일이 DB를 키움(백업·속도) ③ 회원 저장 용량 규칙(최상위 규칙 「💾 저장공간」)에서 빠져 있음.

### A-2. 제안
1. **새 파일은 Supabase Storage**(비공개 버킷 `workspace-files`, 경로 `<회원 id>/<파일 id>/<이름>` — 메인 사이트 용량 계산이 그대로 셈).
2. **올리기는 브라우저 → Storage 바로**(서버가 「서명된 올리기 주소」만 발급) — 4.5MB 한도가 사라짐. **파일당 한도 50MB**(권장, 결정 항목).
3. **올리기 전에 회원 저장 용량 확인**(공용 `storageQuota.ts` 사본 `checkStorageQuota`) — 가득 차면 「저장공간 늘리기」 안내.
4. **내려받기**는 지금 주소(`/files/<id>/<이름>`) 그대로 두고, 권한 확인 뒤 Storage의 짧은 서명 주소(5분)로 넘김 — 페이지 안 링크가 바뀌지 않음.
5. **기존 파일**: DB에 있는 것은 그대로 읽히게 두고(두 곳 모두 읽기), 정리 스크립트로 Storage로 천천히 옮김(결정 항목).
6. **보관 정리**: 지금 규칙(음악·영상 30일, 그 밖 1년)을 Storage 파일에도 똑같이 적용(지울 때 Storage 파일도 함께 지움).

### A-3. 걸리는 점
- **메인 중앙 정리와 충돌 가능**: 메인 사이트 `storage-retention`은 「보관 연장 회원」의 기간 지난 Storage 파일을 지움. 워크스페이스는 주인님 지정으로 일반 자료 1년이라, 예를 들어 90일 연장 회원의 첨부가 90일에 지워질 수 있음(페이지에는 깨진 첨부가 남음) → 결정 항목 A-3.
- 버킷 생성·DB 함수 변경은 운영 작업(승인 필요).

### A-5. 구현 기록(2026-11-14, 미배포)
- `src/server/fileStorage.ts`(서명 올리기 주소·완료 확인·서명 내려받기·Storage 삭제·하루 넘은 대기 정리, 버킷 `workspace-files` 비공개·50MB를 처음 쓸 때 서버 키로 만듦), 라우트 `src/app/api/upload/large/route.ts`, 화면 `src/litpage/web/lib/api.ts` `uploadLargeFile`(4MB 초과면 Storage로 바로), 파일 표 칸 `storage_path`·`pending`, 내려받기는 기존 주소에서 권한 확인 뒤 5분 서명 주소로, 30일 음악·영상 정리 때 Storage도 함께 지움. 용량 확인은 공용 `storage-quota-client` 사본(`src/lib/storage/storageQuota.ts`, 등록 `scripts/check-shared-modules.mjs`).
- 한계: Storage에 둔 큰 파일은 AI 첨부 읽기·내보내기 묶음·가져오기에 쓰이지 않음(내려받기·보기만). 기존 DB 파일은 옮기지 않음.
- **메인 사이트 담당께 요청(A-3)**: 메인 DB 함수 `member_storage_expired_files`(0063·0068)가 `workspace-files` 버킷을 건너뛰게 한 줄(`and o.bucket_id <> 'workspace-files'`) — 보관 연장 회원의 워크스페이스 큰 파일이 워크스페이스 지정 기간(일반 1년·음악/영상 30일)보다 먼저 지워지지 않게. 워크스페이스가 자체 정리를 함.

## B. 공개 페이지·사이트·폼

### B-1. 원본에 있는 것(지금은 닫힘 — `src/server/stagePolicy.ts`)
| 기능 | 원본 명령 | 하는 일 |
|---|---|---|
| 웹에 페이지 공개 | `getPublishedPage`·`getPublicPages`·`duplicatePublicPage` | 로그인 없이 누구나 보는 주소, 「복제 허용」 선택 |
| 사이트 | `setSiteSettings`·`getSite`·`getSiteHome`·`searchSite` | 여러 공개 페이지를 묶은 미니 사이트(제목·파비콘·검색) |
| 공개 폼 | `getPublicForm`·`submitFormResponse`·`emailFormResponse` | 데이터베이스 폼을 바깥 사람이 채움(응답 → 표의 행) |
| 원본 보호 장치 | 검색엔진은 기본 `noindex`(사이트 설정에서 켜야 색인), 폼 제출 분당 30·보기당 분당 600, 응답 메일 시간당 제한 |

### B-2. 열 때의 위험(보안 검토)
1. **우리 도메인에서의 악용**: 회원이 공개 페이지로 피싱·사칭·불법 광고를 올리면 `buylife.xyz` 이름으로 퍼짐(도메인 평판·검색엔진 경고).
2. **개인정보 수집**: 공개 폼으로 바깥 사람의 이름·연락처를 받으면 회원이 개인정보 수집자가 됨(동의 문구·보관 기간 필요).
3. **비공개 자료 유출**: 공개로 바꾼 페이지 안의 하위 페이지·연결 표·첨부가 함께 보이는지(원본 규칙 확인 필요).
4. **로그인 없는 경로**: 지금 화면·명령은 모두 AIMaster 로그인 + 이용 권한을 확인함 → 공개용은 로그인 없이 도는 **별도 좁은 주소**가 필요(공개 명령만 허용).
5. **이용 기간이 끝난 회원**의 공개 페이지가 계속 보이는 문제.

### B-3. 제안(단계)
- **1단계 — 공개 페이지(보기 전용)만**: 로그인 없는 전용 주소 `/p/<공개 번호>`(공개 명령 3개만 허용), 검색엔진 기본 `noindex`(회원이 켜면 색인 — 0번 규칙: 검색엔진 허용), 「복제 허용」 끔, 이용 기간이 끝난 회원의 공개 페이지는 자동으로 닫힘, 화면 아래 「신고하기」 → 관리자 요청함, 관리자가 공개를 즉시 내리는 기능.
- **2단계 — 공개 폼**: 폼 위에 개인정보 수집 동의 문구(필수 체크), 응답 보관 기간 표시, 기존 제출 한도 유지 + 회원당 하루 응답 수 상한.
- **사이트(여러 페이지 묶음·사용자 도메인)**: 이번에는 하지 않음 — 수요 확인 뒤.

### B-5. 구현 기록(2026-11-14, 미배포 — 주인님 「진행해」 권장안)
- 주소는 원본 그대로 **`/public/<번호>`**(플랜의 `/p/` 대신 — 원본 공유 메뉴·화면 길찾기가 이미 이 주소를 씀, B-3 정정).
- 로그인 없는 입구 `/api/public/<명령>` + `src/server/publicPages.ts`: 허용 명령 4개(getSite 번호만·getPublishedPage·loadPage·loadPageCached), 「웹에 게시」된 페이지와 그 아래만, 관리자가 내린 페이지 닫힘(`aww_public_takedowns`), **게시한 회원 이용 기간이 끝나면 자동 닫힘**(5분 기억), 복제 끔, IP당 분당 120회. 회원 로그인 입구(/api/rpc)와 분리.
- 화면: 공유 메뉴 「게시」 탭 엶(복제·사이트 꾸미기·전체 관리는 숨김, 안내 문구 추가), 공개 화면 아래 안내 + 「🚩 이 페이지 신고하기」(IP당 시간당 5건, `aww_public_reports`), 원본 「무료로 시작」 버튼 숨김.
- 검색엔진: 서버가 화면 머리에 noindex를 기본으로 넣고, 회원이 「검색 엔진에 표시」를 켠 게시 페이지만 index(0번 규칙 — 공개 페이지 검색 허용). 입구 API는 항상 noindex.
- 파일: 로그인 없는 방문자는 열린 게시 페이지 안 블록에 붙은 파일만 내려받음(비공개 내보내기 파일은 제외).
- 서버 보호: 화면 저장(applyChanges)은 게시(읽기 전용·복제 끔)만 허용 — 게시 아닌 「링크가 있는 누구나」·편집 권한·복제 허용은 계속 거절(`src/server/collab.ts`).
- 관리자: `/settings/public-pages`(관리자만) — 게시 페이지 전체, 신고 많은 순, 게시한 회원 이메일, 「내리기/다시 열기」. API `/api/admin/public-pages`.
- 한계: 로그인한 다른 회원이 워크스페이스 안 화면으로 남의 게시 페이지를 직접 열면 원본 권한 규칙대로 보일 수 있음(관리자 내리기는 방문자 입구에만 적용). 공개 폼·사이트(여러 페이지 묶음·별칭 주소)는 하지 않음. 공유 탭의 「링크가 있는 누구나」 선택지는 화면에 남아 있고 저장 때 서버가 안내 문구로 거절.
- 시험: `tests/integration/publicPages.test.ts` 8개(게시 켜기 거절·허용, 방문자 보기·404, 색인 기본 꺼짐, 내리기·다시 열기, 이용 기간 종료, 신고). 전체 155 통과, 로컬 빌드 통과.
