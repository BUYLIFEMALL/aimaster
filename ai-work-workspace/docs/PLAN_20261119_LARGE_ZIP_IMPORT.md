## 3. 권장안(나) 설계

1. **브라우저 ZIP 읽기**: 파일을 통째로 메모리에 올리지 않고 `File.slice`로 끝부분 목록(중앙 디렉터리)만 읽은 뒤, 항목마다 필요한 구간만 읽어 브라우저 내장 `DecompressionStream('deflate-raw')`로 푼다. 새 라이브러리 없음.
2. **분류**: 글 파일(`.html`·`.md`·`.csv` 등)과 그 밖(그림·첨부)으로 나눈다. 숨김 파일은 지금처럼 제외.
3. **그림·첨부 올리기**: 하나씩(동시에 3~4개) 기존 큰 파일 올리기 경로로 저장소에 올린다. 회원 저장 용량 확인(`STORAGE_FULL`)은 기존 그대로 적용된다. 올리기 전에 합계 크기를 먼저 계산해 용량이 모자라면 시작 전에 알린다.
4. **글 파일 보내기**: 글 파일만 모은 작은 ZIP(또는 목록)과 경로 표를 `importFiles`에 보낸다. 서버의 `resolveImage`는 표에 있으면 그 주소를 쓰고, 없으면 지금처럼 ZIP 안에서 찾는다(작은 ZIP은 기존 경로 그대로 — 50MB 이하 동작은 바꾸지 않는다).
5. **넘는 파일 처리**: 파일 하나가 50MB를 넘으면(주로 동영상) 건너뛰고, 끝난 뒤 「가져오지 못한 파일 ○개」 목록을 보여 준다.
6. **겹친 ZIP**: 노션 내보내기는 ZIP 안에 `Export-….zip`이 한 번 더 들어 있는 경우가 있다. 안쪽 ZIP이 압축 없이 들어 있으면 구간 그대로 다시 읽고, 압축돼 있으면 한 번 풀어 임시로 들고 처리한다(이 경우 브라우저 메모리를 그만큼 쓴다).
7. **실패·중단**: 도중에 실패하면 이미 올라간 그림은 남는다. 페이지를 만들기 전 단계에서 실패한 경우 올린 파일을 지우는 정리를 넣는다. 결과가 불확실하면 자동으로 다시 시도하지 않는다.
8. **화면**: 안내 문구를 「ZIP 전체 ○GB까지 · 안에 든 파일 하나는 50MB까지」로 바꾸고, 진행 표시에 「그림 37 / 212」처럼 수를 보여 준다.

바꿀 파일(예상): `web/features/import/ImportPanel.tsx`, 새 `web/features/import/zipReader.ts`, `server/api/modules/import.ts`(경로 표 받기), 문구 `i18n.ko-KR.json`, 시험 2개(브라우저 ZIP 읽기·서버 경로 표).

| 확인 | 결과 | 근거 |
|---|---|---|

| 거절 문구와 일치 | 「파일은 50MB까지 올릴 수 있습니다.」와 같은 숫자 | `fileStorage.ts:59`, `:97` |
| 요금제별 차이 | ZIP에는 없음. 무료 5MB·유료 50MB(PDF 20MB) 제한은 ZIP을 빼고 적용된다 | `import.ts` `maxBytesFor`, `uploadOf`의 `!/\.zip$/i` |
| 키 이름 | `lp.import.zip_files_must_be_5gb_or` 그대로 둠(값만 바꿈) | 키를 바꾸면 고칠 곳이 늘어 최소 수정으로 둠. 이름과 값이 어긋난 것은 알려 둔다 |

문구가 말해 주지 않는 것(문구는 틀리지 않지만 충분 조건은 아님):

1. 50MB 이하 ZIP도 **풀린 크기 합계가 256MiB를 넘거나 항목이 5,000개를 넘으면** 「Archive too large」·「Too many files in archive」로 실패한다(`zip.ts` `readZip`).
2. 블록 20,000개를 넘으면 「Import is too large」로 실패한다(`import.ts` `MAX_BLOCKS`).
3. 표기는 「MB」지만 실제 기준은 MiB다. 윈도우 탐색기의 「50.0MB」는 MiB 기준이라 화면 숫자와 판정이 맞는다.

화면 확인은 하지 않았다(미배포).

## 9. 올린 파일의 소유권과 「가져오기 작업」 범위 검증

지금 구조에서 큰 ZIP 경로에 그대로 쓸 수 없는 것(코드 확인):

- 큰 파일 올리기는 회원당 10분에 30번으로 막혀 있다(`upload-large:user:<id>`). 그림 수백 장을 낱개로 올리면 바로 걸린다.
- 4MiB 이하 파일은 큰 파일 경로가 거절하고(「4MB 이하 파일은 일반 올리기를 씁니다」), 일반 경로는 내용을 DB에 넣는다. 작은 그림 수백 장이 DB로 들어가게 된다.
- 요청 본문 한도 때문에 글 파일 묶음도 호출 인자로 직접 보낼 수 없다. 파일로 올린 뒤 식별자로 가리켜야 한다.
- 올린 파일에는 「어느 가져오기에서 올린 것인지」 표시가 없다. 지금의 확인은 「올린 사람만 가져올 수 있다」(`uploadOf` → `readStoredFile(url, uid)`) 하나다.

그래서 **「가져오기 작업」 단위**를 둔다.

| 단계 | 서버가 하는 일 | 검증 |
|---|---|---|
| 1. 작업 열기 `importBegin` | 작업 줄을 만든다(작업 id·회원·워크스페이스·대상 부모·신고한 파일 수와 합계 크기·상태 `open`·만든 시각) | 워크스페이스 구성원인지(`spaceOrThrow`), 대상 페이지 쓰기 권한, 합계가 상한 이하인지, 회원 저장 용량이 합계만큼 남았는지, 같은 회원의 열린 작업이 1개 이하인지 |
| 2. 올리기 주소 받기(묶음) | 한 번에 최대 50개씩 주소를 내주고 파일 줄을 `pending`으로 만든다. 줄마다 **작업 id를 기록** | 작업이 그 회원 것이고 `open`인지, 작업의 누적 파일 수·누적 크기가 신고값과 상한을 넘지 않는지, 파일 하나가 50MiB 이하인지. 이 경로만 4MiB 이하도 저장소로 받는다 |
| 3. 올리기 끝 알림(묶음) | 저장소에 실제로 있는지·실제 크기를 확인하고 `pending`을 푼다(기존 `finishLargeUpload`와 같은 확인) | 실제 크기가 50MiB를 넘으면 지우고 거절(기존과 같음), 누적 실제 크기를 작업 줄에 더함 |
| 4. 가져오기 `importFiles`(작업 id 포함) | 글 파일 묶음과 경로 표를 받아 페이지를 만든다. 작업 상태를 `importing` → `done` | 아래 「경로 표 검증」 전부 |

**경로 표 검증**(하나라도 어긋나면 전체 거절, 페이지를 만들지 않음):

1. 표의 값은 **파일 식별자만** 받는다. 주소(URL)는 받지 않고 서버가 식별자로 주소를 만든다.
2. 식별자마다 파일 줄이 있고, `user_id`가 부른 회원과 같고, **작업 id가 이 작업과 같고**, `pending = 0`이며, 워크스페이스가 작업의 워크스페이스와 같다.
3. 표의 항목 수가 작업에 기록된 올린 파일 수 이하이고 5,000개 이하다.
4. 표의 키(ZIP 안 경로)는 서버가 다시 정규화한다(11절 규칙). 정규화 뒤 같은 키가 둘이면 거절.
5. 글 파일 묶음도 같은 작업 id로 올린 파일이어야 한다.
6. 작업은 그 회원 것이고 상태가 `open`이며 만든 지 24시간 안이다. `done`인 작업으로 다시 부르면 **새로 만들지 않고 처음 결과를 돌려준다**(결과가 불확실할 때 다시 눌러도 페이지가 두 번 생기지 않게).

다른 회원의 식별자, 다른 작업의 식별자, 작업 밖에서 올린 본인 파일을 표에 넣는 경우를 각각 시험으로 막는다.

**DB 변경이 필요하다**(결정 항목 6): 작업 줄을 담을 표 하나와 `files`에 작업 id 열 하나. 운영 DB 변경은 Master·주인님 승인 뒤에만 한다.

## 10. 실패했을 때의 정리 — 그 작업이 올린 것만

| 상황 | 정리 대상 | 하지 않는 것 |
|---|---|---|
| 올리는 중 실패·취소 | `작업 id = 이 작업` 이고 `user_id = 그 회원`인 파일 줄과 그 저장소 파일 | 작업 id가 없는 파일, 다른 작업의 파일, 같은 회원의 다른 파일은 건드리지 않는다 |
| 경로 표 검증 실패 | 위와 같음 | 페이지를 만들지 않았으므로 블록 정리는 없다 |
| 페이지 만들기 도중 오류 | 페이지 만들기는 지금처럼 한 번에 적용되거나 전부 실패해야 한다(구현 때 `importFiles`의 저장 단위를 확인해 문서에 적는다). 실패로 확정되면 위와 같이 작업 파일을 정리 | 결과가 불확실하면(응답을 못 받음) **정리하지 않고** 작업 상태를 조회해 `done`이면 결과를, `open`이면 다시 시도 여부를 회원에게 묻는다. 자동 재시도 없음 |
| 성공 | 표에 있지만 어느 페이지에서도 쓰이지 않은 작업 파일만 지운다(용량 회수) | 페이지가 쓰는 파일은 그대로 |
| 브라우저를 닫음 | 24시간 지난 `open` 작업을 기존 대기 파일 정리(`fileStorage.ts` 24시간 규칙)와 같은 자리에서 정리. 조건은 같은 「작업 id + 회원」 | 30일 열외 계정(`retention_exempt`)도 이 정리는 받는다 — 쓰이지 않은 올리기 찌꺼기이지 보관 자료가 아니다 |

정리는 여러 번 불러도 결과가 같아야 하고, 지우는 질의에는 항상 작업 id와 회원 id 두 조건을 함께 건다. 저장소 삭제가 실패하면 파일 줄을 남겨 다음 정리에서 다시 시도한다(줄만 지우고 저장소에 파일이 남는 일을 막는다).

## 11. 압축 풀기 제한

브라우저 값은 믿지 않는다. 브라우저 제한은 회원에게 일찍 알리기 위한 것이고, 서버가 9절 단계마다 같은 숫자를 다시 센다.

| 제한 | 값(권장) | 어디서 | 넘으면 |
|---|---|---|---|
| ZIP 전체 크기 | 1GiB | 브라우저(파일 크기), 서버(작업 누적 크기) | 시작 전에 거절 |
| 항목 수(겹친 ZIP 포함 누적) | 5,000 | 브라우저, 서버(작업 누적 파일 수·표 항목 수). 기존 `readZip` 값과 같음 | 시작 전에 거절 |
| 낱개 파일 풀린 크기 | 50MiB | 브라우저가 **푸는 동안 나온 바이트를 세어** 넘는 순간 중단(목록에 적힌 크기를 믿지 않음), 서버는 저장소의 실제 크기로 확인 | 그 파일만 건너뛰고 목록에 적음 |
| 풀린 크기 누적 | 2GiB | 브라우저(푸는 동안 누적) | 중단하고 그 작업 정리 |
| 글 파일 묶음 | 기존 값 그대로: 풀린 합계 256MiB, 항목 5,000 | 서버 `readZip`(이미 푸는 중에 `maxOutputLength`로 막음) | 전체 거절 |
| 겹친 깊이 | 1단계까지(지금 서버와 같음). 안쪽 ZIP 안의 ZIP은 풀지 않고 목록에 적음 | 브라우저 | 건너뜀 |
| 압축된 안쪽 ZIP 크기 | 256MiB | 브라우저(메모리에 풀어야 하므로) | 「바깥 ZIP을 풀어 안쪽 ZIP을 직접 넣어 주세요」 안내 |
| 경로 길이·깊이 | 1,024바이트, 32단계 | 브라우저, 서버(표의 키) | 그 항목 건너뜀 |
| 블록 수 | 기존 20,000 | 서버 | 전체 거절 |
| 동시에 올리는 수 | 4 | 브라우저 | — |

풀지 않는 것: 암호가 걸린 항목, deflate·무압축이 아닌 방식, ZIP64 형식(지금 서버 `readZip`도 읽지 못한다 — 항목 수 16비트·위치 32비트만 읽음). 만나면 조용히 넘어가지 않고 사유와 함께 목록에 적는다.

**경로 정규화와 충돌**:

1. 정규화는 서버 `readZip`과 같은 규칙을 한 함수로 만들어 브라우저와 서버가 함께 쓴다: `\` → `/`, 빈 조각·`.`·`..` 제거, 숨김 파일(`.`으로 시작)·`__MACOSX/`·`.DS_Store` 제외.
2. 항목 이름은 자료로만 쓰고 저장 경로로 쓰지 않는다. 저장소 경로는 지금처럼 `회원 id/파일 id/이름`으로 서버가 만든다.
3. 정규화 뒤 이름이 같은 항목이 둘 이상이면 **첫 항목만 쓰고 나머지는 건너뛴 목록에 적는다.** 덮어쓰지 않는다.
4. 알려 두는 기존 동작: 지금 작은 ZIP 경로는 같은 이름이 둘이면 **뒤 항목이 조용히 이긴다**(`import.ts`의 `new Map(entries.map(...))`). 이번 작업에서 작은 ZIP 경로는 바꾸지 않으므로 그대로 둔다(바꾸려면 별도 결정).
5. 한글 이름의 조합형·완성형 차이(맥에서 만든 ZIP)는 지금 경로가 어떻게 처리하는지 확인하지 않았다. 구현 전에 시험으로 먼저 고정한다.

## 14. 구현 중 발견·보완 기록 (2026-11-19)

### 14-1. 기존 결함: 4MiB 넘는 가져오기 파일은 읽지 못했다
- 4MiB 초과 파일은 내용이 Storage에 있고(`files.storage_path`, `content` NULL) 가져오기는 DB 내용만 읽었다 → ZIP·HTML·PDF·CSV 모두 올리기는 되고 변환에서 `Upload not found: <이름>`(404). 재현 `c2816bf0f`(6MiB ZIP). 그래서 8절의 「50MB」는 올리기 한도였고, 가져오기가 실제로 되는 크기는 4MiB였다.
- 수정 `7298b1dbf`: 가져오기 세 명령(`importFiles`·`previewCsv`·`mergeCsv`)이 기존 확인을 마친 뒤 가져오기 전용 로더로 하나씩 읽는다(Master `msg_b6590eaaaee8` 방식 — 런타임 선행 다운로드·공용 보관 없음).
  호출 경로: `runtime.ts runRpc`(세 명령일 때만 `ctx.loadStoredUpload` 연결) → `import.ts uploadOf` → `storedUpload`(줄 존재·본인·`pending 0`·경로 `<본인>/<파일 id>/<이름>`·기록 크기 한도 이하) → `fileStorage.ts readImportUpload`(서버 고정 버킷, 60초 서명 주소, 받은 바이트를 세며 한도 초과 순간 중단).

### 14-2. 대기(await) 사이의 동시 변경 — 잠금 순서와 조건 (`c81384d50` + 후속)
Storage에서 파일을 읽는 동안 요청은 멈춰 있고, 그사이 다른 요청·다른 서버 인스턴스가 같은 대상을 바꿀 수 있다. 요청 캐시는 대기 전에 읽은 값을 계속 돌려준다.

| 명령 | 대기 전(트랜잭션 밖) | 대기(트랜잭션 밖) | 대기 뒤(한 트랜잭션) |
|---|---|---|---|
| `mergeCsv` | 표 편집 권한(`databaseOrThrow`)·구성원·횟수 | `await uploadOf`, CSV 해석·줄 수 한도 | `tx` 시작 → `lockRecords([block, collection, 그 표의 collection_view 전부])` → 권한·대상 재확인 → 잠근 대상과 지금 표의 컬렉션·보기 목록 대조(다르면 409) → **잠근 뒤의 최신 스키마**에 열·옵션 병합 → `applyTransactions` |
| `importFiles` | 구성원·횟수·대상 페이지 쓰기 권한 | 파일마다 `await uploadOf` → 변환(하나씩) | `tx` 시작 → `lockRecords([대상 page 블록 또는 space])` → 구성원·대상 쓰기 권한·`alive`·`afterBlockId` 재확인 → `applyTransactions` → (큰 ZIP 작업이면) 작업 줄 `done` 표시 |
| `previewCsv` | 구성원·(표를 지정했으면) 표 편집 권한 | `await uploadOf` | 쓰기 없음. `withoutRequestCache`로 구성원을 다시 확인하고, 표를 지정했으면 표도 다시 읽어 최신 열 목록을 돌려준다 |

- **잠금 순서**: `lockRecords`는 받은 대상을 `표 이름\0id`로 정렬해 그 순서로 `SELECT … FOR UPDATE` 한다(교착 방지, 기존 U13 장치). 한 명령은 필요한 줄을 **한 번의 호출로** 모두 잠근다(나눠 잠그지 않음). 잠근 뒤 요청 캐시를 비우므로 이후 `getRecord`는 최신 값이다.
- **트랜잭션 재진입**: `tx`는 이미 트랜잭션 안이면 새로 열지 않고 바깥에 합류한다. 그래서 명령이 연 트랜잭션 안에서 부른 `applyTransactions`의 `tx`·`lockRecords`는 같은 트랜잭션에서 실행되고, 이미 잡은 줄을 다시 잠그는 것은 같은 연결이라 기다리지 않는다. 새로 만드는 줄(가져온 페이지·행)은 잠글 것이 없다.
- **네트워크 대기는 항상 트랜잭션 밖**: 세 명령 모두 `await`는 `tx` 앞에만 있다. `tx` 안은 동기 코드뿐이다(DB 다리가 동기라 한 프로세스 안에서는 끼어들지 않고, 다른 인스턴스와는 행 잠금으로 차례가 정해진다).
- **직접 고른 열**(`mergeCsv`의 `mapping`): 대기 전에 있던(넣을 수 있던) 열이 잠근 뒤에 없거나 넣을 수 없는 종류면 같은 이름의 새 열을 만들지 않고 409로 멈춘다(줄·열 변화 없음). 처음부터 없던 id를 넘긴 경우는 예전 동작(머리글 이름의 새 열) 그대로.

검증(`tests/integration/importStoredUpload.test.ts`, 전용 fixture `aww_zip1119_wf`):
- 같은 표 두 요청(한쪽이 Storage를 기다리는 사이 다른 쪽 완료, 역순 포함) → 열·select 옵션 유실 0.
- **서로 다른 DB 연결**: 두 번째 연결이 컬렉션 줄을 `FOR UPDATE`로 잡고 열·옵션을 더한 뒤 2초 뒤 커밋 → 세 번째 연결의 `SKIP LOCKED` 조회가 0줄(잠금 보유 확인), 커밋 전에는 새 열이 보이지 않음 → `mergeCsv`가 약 1.4초 이상 기다린 뒤 끝나고 두 쪽의 열·옵션이 모두 남음.
- 대기 중 권한 제거·보기 목록 변경·대상 페이지 삭제·직접 고른 열 삭제/종류 변경 → 거절, 줄·열 변화 없음. 표 지정 없는 미리보기도 권한 제거 시 내용 미반환.
- 각 사례는 수정 전 코드에서 실패함을 확인했다(붉은 단계).

### 14-3. 큰 ZIP 작업의 상태 전환과 정리 (Master `msg_2e22cd4b41c3` 보완)
상태: `open` → `done` → `closed`, 또는 `open` → `cancelled`. **지우기는 상태 전환이 실제로 성공한 쪽만 한다.**

| 일 | 전환(조건부 UPDATE) | 전환 성공 | 전환 0줄 |
|---|---|---|---|
| 가져오기 완료(`importFiles`) | `open → done`, 페이지 적용과 **같은 트랜잭션** | 결과와 쓰인 그림 id를 작업 줄에 기록 | 만든 것을 되돌리고, 그사이 끝난 작업이면 처음 결과를 돌려줌(취소된 작업이면 409) |
| 직접 취소(`import-cancel`) | `open → cancelled` | 그 작업의 파일을 모두 지움 | 409 — 아무것도 지우지 않음(가져오기가 먼저 끝난 경우 쓰인 그림 보존) |
| 만료 정리(열린 지 24시간 넘음) | `open → cancelled` | 그 작업의 파일을 모두 지움 | 건너뜀(다음 정리에서 `done`으로 다룸) |
| 마무리(`import-finish`)·끝난 작업 정리 | 먼저 쓰이지 않은 그림을 지우고, 남은 것이 없을 때만 `done → closed` | — | `done`은 「무엇이 쓰였는지」가 굳은 상태라 여러 번 해도 결과가 같다 |
| 새로 시작(`import-begin`) | 줄 추가(`open`) | 새 작업 | 열린 작업이 있으면 **409 `IMPORT_JOB_OPEN`**(그 작업 id 포함) — 서버가 대신 지우지 않는다 |

- **회원당 열린 작업 하나**: 부분 고유 색인 `import_jobs_one_open (user_id) WHERE state = 'open'`. 동시에 두 번 시작해도(다른 서버 인스턴스 포함) 두 번째 줄 추가가 실패하고 409가 된다.
- **열린 작업이 있을 때**: 24시간 넘은 것만 시작할 때 만료로 정리한다. 그 밖에는 화면이 「끝나지 않은 큰 가져오기를 취소하고 새로 시작할까요?」를 묻고, 회원이 동의했을 때만 `import-cancel` 뒤 한 번 다시 시작한다.
- **실패한 정리의 재처리**: Storage 삭제가 확인된 줄만 지운다. 취소된 작업에 줄이 남아 있으면 주기 정리(`cleanupStaleImportJobs`)와 다시 부른 `import-cancel`이 지운다. 마무리에서 실패하면 `done`으로 남겨 두어 다시 부른 마무리·주기 정리가 이어서 한다.
- 지우는 질의는 모두 「작업 id + 회원 id」 조건이다.

- **글 파일 묶음도 작업 파일이다**(Mac 검수 P2 — 플랜 §9-5 그대로): `import-pages`로 작업당 하나만 올리고 작업 줄의 `pages_file_id`에 기록한다. `importFiles`는 요청이 가리키는 파일이 그 id이고 본인·이 작업·같은 워크스페이스·올리기 완료일 때만 받는다(읽기 전에 확인). 같은 회원의 다른 ZIP·작업 밖 파일·다른 작업의 묶음은 붙일 수 없다. 알린 개수·합계에 포함되고, 가져온 뒤 마무리에서 지워진다. 그림이 하나도 없는 ZIP만 작업 없이 기존 올리기 경로를 쓴다.
- **크기 초과로 올라온 파일**: Storage 삭제가 확인된 뒤에만 줄을 지운다. 실패하면 대기 줄로 남아(가져오기에는 쓸 수 없음) 작업 정리가 지운다.
- **응답이 불확실한 오류**(응답 없음·5xx·408·429): 브라우저는 취소하기 전에 작업 상태를 한 번 조회한다. 끝났으면 그 결과를 쓰고, 아니면 지우지도 다시 보내지도 않는다. 분명한 거절(그 밖의 4xx)만 바로 취소한다.

6·7절 플랜과 달라진 점: (가) 큰 ZIP 경로는 겹친 ZIP 안에서도 숨김 항목을 항상 제외한다(통째 경로의 기존 동작은 그대로). (나) 같은 이름이 둘이면 첫 항목(11절).

검증(`tests/integration/importLargeZip.test.ts` 45개 — 아래에 더해 글 묶음 연결 반례, 크기 초과 삭제 확인, 504 처리, **별도 DB 연결**로 만든 완료↔직접 취소(커밋·되돌림)·완료↔만료 정리·취소↔가져오기·동시 시작 5건. 전체 묶음 69파일 1,002개 통과): 통째 경로와 결과 동일 6종 · 쓰인 그림만 남음 · 재호출·동시 재호출에 페이지 1번 · 표 검증 반례 · 정리 범위 · 취소/마무리 실패 재처리 · 정리가 목록을 읽은 뒤 가져오기가 끝난 작업의 그림 보존 · 취소가 먼저면 페이지 미생성 · 동시 시작 1개 · 만료 시작 정리 · 서버 한도 · 브라우저 ZIP 읽기. 보완 전 코드에서 경합·재처리 4건 실패 확인.

### 14-4. 주기 정리의 책임 분리 (Mac 재검수 P2, Master `msg_547f81d99092`)
- 일반 「대기 파일 정리」(`cleanupPendingUploads`)는 **작업 파일(`import_job_id` 있음)을 다루지 않는다.** 작업 파일은 작업 정리(취소·마무리·만료)만 지운다. 예전에는 작업 정리의 Storage 삭제가 실패한 같은 회차에 일반 정리가 그 대기 줄을 지워, Storage에 남은 파일을 다시 지울 길이 없어졌다.
- 줄을 지우는 조건은 어디서나 같다(`removeConfirmed`): Storage가 **지웠다고 답한 경로**이거나, 답에 없어 다시 찾아봤더니 **실제로 없는 경로**(올리기를 끝내지 못해 애초에 없던 것). 삭제 호출이나 확인 조회가 실패하면 줄을 남기고 다음 회차가 다시 한다.
- 검증: 같은 회차에서 Storage 삭제 실패 → 작업 파일 3개(대기 줄 포함)와 일반 대기 파일이 모두 남음 → 삭제는 되고 확인 조회만 실패한 회차 → 있던 것만 정리 → 정상 회차 → 나머지 정리. 다른 회원의 최근 대기 파일과 진행 중 작업은 그대로. 보완 전 코드에서 3건 실패 확인. 전체 묶음 69파일 1,005개 통과.

### 14-5. 취소 뒤 늦게 도착하는 올리기 (Mac 재검수, Master `msg_41ae6dc0d449`)
문제: 올리기 주소를 내준 뒤 다른 탭에서 취소하면, 정리가 「Storage에 없음」을 확인하고 파일 줄을 지운다. 그 뒤 먼저 받아 둔 주소로 올리기(PUT)가 도착하면 그 파일은 줄이 없어 다시 지울 길이 없다. 지운 것이 확인된 파일도 같은 주소로 다시 올라올 수 있다.

- **줄은 경로 표식이다**: 작업 파일 줄은 ① Storage에서 없어진 것이 확인됐고 ② **주소를 내준 지 3시간이 지났을 때만** 지운다. 그 전에는 Storage 쪽만 지우고(용량은 바로 회수) 줄은 남긴다. 다음 정리가 다시 보고, 그사이 올라온 파일이 있으면 그때 지운다. 취소·마무리·만료 정리·크기 초과 삭제 모두 같은 기준이다.
- **3시간의 근거**: 주소 유효 2시간은 설치된 `@supabase/storage-js` 2.117.3의 `createSignedUploadUrl` 설명(「They are valid for 2 hours.」). 나머지 1시간은 유효 시간이 끝나기 직전에 시작된 올리기가 끝날 때까지의 여유로 **가정한 값**이다 — Storage가 올리기 요청을 얼마나 오래 받는지는 보장된 값을 확인하지 못했다. 이 가정보다 늦게 도착한 파일은 남을 수 있다(운영에서 실측하지 않음).
- **줄 먼저, 주소 나중**: `import-sign`·`import-pages`는 셈 올리기와 줄 넣기를 한 트랜잭션(작업 줄 잠금)으로 먼저 하고, 그다음에 주소를 만든다. 내준 주소에는 반드시 줄이 있다. 그사이의 취소는 잠금을 기다렸다가 그 줄까지 본다. 취소가 먼저면 줄도 주소도 만들지 않는다(409).
- 영향: 취소·마무리 직후에는 줄이 남아 있으므로 `removed`가 0일 수 있고, 마무리한 작업은 남은 줄이 지워질 때까지 `done`으로 있다가 주기 정리가 닫는다. 본문에 쓰인 그림은 처음부터 정리 대상이 아니다. 일반 대기 파일(작업 밖)은 예전처럼 하루 기준이다.
- 검증(실제 3시간 값으로): 취소 → 늦은 올리기 → 정리(여유 안: Storage만 지움, 2시간 59분에도 줄 유지 → 3시간 1분 뒤 줄까지 정리) · 삭제 확인 뒤 재도착 · 마무리 뒤 줄 유지와 닫기 · 크기 초과 · 발급 중 취소(내준 주소마다 줄 있음) · **별도 DB 연결**이 줄 추가를 커밋하는 중의 취소(대기 후 그 줄 확인) · 일반 대기 파일 회귀. 어느 사례에서도 줄 없는 파일이 남지 않는다. 보완 전 코드에서 6건 실패 확인. 전체 묶음 69파일 1,013개 통과.
