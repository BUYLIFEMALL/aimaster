## 1. F03 — 「회원당 Gmail 연결 1개」를 DB가 보장
### 안 A(권장): Gmail 전용 부분 고유 인덱스만 추가, 공용 저장 함수는 그대로
```sql
create unique index if not exists member_platform_accounts_gmail_one
  on public.member_platform_accounts (user_id) where platform = 'google_gmail';
```
- 같은 계정 다시 연결: 기존 upsert가 3칸 고유 조건으로 **갱신**(refresh_token 보존 규칙 그대로).
- 다른 계정: upsert가 새 줄을 넣으려다 부분 인덱스에 걸려 **23505 오류 → 기존 계정 줄·토큰은 그대로**(갱신 0). `saveMemberAccount`가 돌려준 오류 문구에 인덱스 이름(`member_platform_accounts_gmail_one`)이 있으면 409로 바꿈.
- 동시 콜백 두 개(서로 다른 계정): DB가 한 줄만 받아들임 → 하나는 성공, 다른 하나 409. 한 문장(upsert)이라 저장과 확인 사이 중단 문제 없음.
- 코드 변화(Gmail 전용 `gmailInbox.ts`만): 저장 뒤 재확인·자기 줄 조건부 삭제·인스턴스 직렬화는 필요 없어져 제거, 저장 전 미리 확인(친절한 409)과 읽기 때 줄 2개 409(방어)는 유지.
- 약점: 오류 구분이 오류 **문구**에 기대게 됨(공용 함수가 오류 코드를 안 돌려줌). 문구가 바뀌면 409 대신 「저장 실패」로 보일 뿐 데이터는 안전(줄이 늘지 않음).
### 안 B: Gmail 전용 조건부 저장 함수(RPC)
```sql
create or replace function public.gmail_account_save(p jsonb) returns text
language plpgsql security definer set search_path = public as $$
declare r_id uuid;
begin
  insert into member_platform_accounts (user_id, platform, external_id, username, access_token, refresh_token, token_expires_at, granted_scopes, auth_method, app_ref, connected_via)
  values ((p->>'user_id')::uuid, 'google_gmail', p->>'external_id', p->>'username', p->>'access_token', p->>'refresh_token', (p->>'token_expires_at')::timestamptz,
          array(select jsonb_array_elements_text(p->'granted_scopes')), 'oauth', p->>'app_ref', 'ai-work-workspace')
  on conflict (user_id) where platform = 'google_gmail'
  do update set access_token = excluded.access_token,
                refresh_token = coalesce(excluded.refresh_token, case when member_platform_accounts.app_ref = excluded.app_ref then member_platform_accounts.refresh_token end),
                token_expires_at = excluded.token_expires_at, granted_scopes = excluded.granted_scopes, app_ref = excluded.app_ref,
                username = excluded.username, needs_reconnect = false, updated_at = now()
    where member_platform_accounts.external_id = excluded.external_id
  returning id into r_id;
  return case when r_id is null then 'other_account' else 'ok' end;
end $$;
revoke all on function public.gmail_account_save(jsonb) from public, anon, authenticated;
grant execute on function public.gmail_account_save(jsonb) to service_role;
```
- 장점: 결과가 명시적(`ok`/`other_account`), 문구 의존 0. 단점: 공용 DB에 새 함수(보안 정의자) — 검토·롤백 대상이 늘고, refresh_token 보존 규칙을 공용 함수와 따로 유지해야 함.
- **권장 = 안 A**(인덱스 1개, 공용 함수 그대로). 오류 문구 의존이 걱정되면 안 B.

## 2. A2 — 고른 메일을 받은 업무로(원자성·응답 유실·보관 경계)
### 안 A2-1(권장): 같은 DB에서 한 거래로 — Gmail 전용 함수
- 새 표 `public.gmail_inbox_claims(user_id uuid, account_hash text, message_id text, inbox_id uuid references public.work_inbox(id) on delete cascade, created_at timestamptz default now(), primary key (user_id, account_hash, message_id))` — `account_hash` = 구글 계정 번호(sub)의 sha256(개인 식별자 원문 저장 0), RLS 켜고 회원 정책 없음(서버 키만).
- 함수 `public.gmail_inbox_add(user_id, account_hash, message_id, title, source_url) returns (status text, inbox_id uuid)` — 한 거래 안에서 ① 클레임이 이미 있으면 `('existing', 그 inbox_id)` ② 없으면 `work_inbox` insert(검사는 `sendToWorkInbox`와 같은 조건: 제목 1~200자, https 원본) → 클레임 insert → `('added', id)`. 동시 요청은 기본 키 충돌로 하나만 넣고 나머지는 `existing`.
- **응답 유실**: 화면이 응답을 못 받아 다시 눌러도 `existing`과 같은 받은 업무 번호를 돌려줌(멱등) → 중복 0, 「불확실」 상태가 생기지 않음. 자동 재전송 0(회원이 다시 누를 때만).
- 공용 `sendToWorkInbox`·`work_inbox` 표 구조 변경 0(함수가 같은 표에 직접 넣음 — 넣는 칸·검사를 공용 함수와 맞춤).
### 안 A2-2(새 함수 없이): 상태 3가지
- `aww` 스키마 클레임 표에 `state pending|done|unknown`. 클레임 pending insert(고유 조건) → `sendToWorkInbox` → done+inbox_id. `sendToWorkInbox`가 오류·시간 초과면 **unknown**(넣어졌을 수도 있음) — 자동 재전송·클레임 삭제 0. 재조정: unknown은 `work_inbox`에서 같은 회원·`source_url`을 찾아 있으면 done, 없으면 회원이 「다시 넣기」를 직접 누를 때만 재시도. 확실한 실패(검사 오류 등 insert 전)만 클레임 삭제.
- 약점: 두 연결(aww·supabase-js)이라 원자 보장 없음, 상태·재조정 코드가 늘어남.
- **권장 = A2-1**(같은 DB 한 거래, 멱등).

### 보관·중복 기간(기존 1년 정책 변경 0)
- 받은 업무 줄: 회원이 쓴(또는 직접 넣기로 고른) 제목 + 원문 링크 `https://mail.google.com/mail/u/0/#all/<message_id>` — 보낸 사람·본문·snippet·이메일 0. 보관은 기존 받은 업무 규칙(1년, 관리자·시험 계정 열외) 그대로.
- 클레임: **받은 업무 줄이 살아 있는 동안만**(`on delete cascade`) → 「같은 메일 중복 방지 = 그 받은 업무가 남아 있는 동안(최대 1년)」. 회원이 받은 업무를 지우면 다시 넣을 수 있음(의도). 따로 30일 정리 작업이 필요 없음.
- 대안(30일 클레임 정리): 30일 뒤엔 같은 메일을 다시 넣을 수 있음 → 화면에 「30일이 지나면 같은 메일이 다시 들어갈 수 있습니다」 명시 필요. 권장하지 않음.
- 링크 주의: `u/0`은 브라우저의 첫 구글 계정으로 열려 다른 계정에서 열릴 수 있음 → 받은 업무 화면에 「연결 계정으로 로그인한 Gmail에서 여세요」 안내, 이메일 자동 추가 0. Gmail API 메시지 번호와 Gmail 화면 주소 번호의 호환은 **실확인 전 보장하지 않음**(실계정 1회 확인 항목).
